### 4.3 caps：token 流不等价与 A1U1 头 X

自写解析器直接读 `.frm` 的 44 字节 header（88 hex chars），按小端解码字段；A 的 `header=` 末 16 字符为 `x`，故字节 36..43 记为 None，其余字段正常解码。

| 项 | N（A） | N（H-only r1） | L（A） | L（H-only r1） |
|---|---:|---:|---:|---:|
| f1 stream_len | 1,665,923 | 1,677,912 | 2,153,391 | 2,156,868 |
| f2–f4 stream_len | 1,665,923 | 1,677,336 | 2,154,993 | 2,156,300 |
| exp_bytes（4 帧和） | 6,663,692 | 6,709,920 | 8,618,370 | 8,625,768 |
| raw_crc | 3,665,401,424 | 3,665,401,424 | 707,927,594 | 707,927,594 |
| xform_crc | 2,597,442,251 | 2,597,442,251 | 2,647,552,023 | 2,647,552,023 |
| 头 0..23 字节 | 与基准相同 | — | 与基准相同 | — |
| 头 24..27（长度字段） | = stream_len | = stream_len | = stream_len | = stream_len |
| 头 28..35（raw/xform CRC） | 与 `.frm` 十进制字段一致 | 一致 | 一致 | 一致 |
| 头 36..43 | **`xx`×8（X）** | 有效整数 | **`xx`×8（X）** | 有效整数 |
| `.frm` SHA | `7d6c6d05…2116` | `b9cb5359…567c` | `7565dc64…d59b` | `8aad9099…8564` |
| `.hdr` SHA | `4fc480a4…b649` | `c7fe281c…fe4e` | `999782f2…77d9` | `864d2fba…3e47` |
| 整文件 SHA 相等？ | **否** | — | **否** | — |

- **头字段自洽**：A 的头 magic `41315531`（A1U1）、frame no 1..4、长度字段 = `stream_len`、raw/xform CRC 字段 = `.frm` 十进制字段；**只有 36..39（stream_crc）与 40..43（header_crc）为 X**。这不是“整个头都读错”，而是两个 CRC 累加器路径的定向回归。
- **4/4 整文件 SHA 不等**：N/L 的 `.frm` 与 `.hdr` 全部不等；N `.frm` 888 B vs 基准 958 B，L 884 B vs 956 B，差异正是 X 文本比 10 位十进制短，但 **stream_len 本身也已改变**，不是仅表示法差异。
- **`exp_bytes = 4 × stream_len` 自洽**：N 4×1,665,923 = 6,663,692；L 2,153,391+3×2,154,993 = 8,618,370；`cap_bytes − exp_bytes = 176 = 4×44`（4 帧头），与 TB 语义一致。
- **stats 关键计数与基准相同**：`cap=enc=exported=4`、`read=518400`、`dup=3896/568`、`raw_bad=0`、`vec_bad=0`、`err=0`、`geom=0`；差异只在 core 的 token/packer/CRC 路径，不在前端。

### 4.6 A1U1 头 36..43 = X 是 DUT 输出，不是 TB 伪影

- `tb_ss_4run_wd.v` 236–263 行：`mon_hdr[mon_hcnt] = dbg_byte`（DUT 导出的 UART 字节流），44 字节到齐后 `mon_strc = {mon_hdr[39..36]}`、`mon_hdrc = {mon_hdr[43..40]}`；`.frm` 只是把这些字节打印出来。TB 不生成 CRC，也不改写 DUT 字节。
- 同一帧的 raw_crc/xform_crc（字节 28..35）有效且与 `.frm` 十进制字段一致，magic/长度/frame no 也有效；只有 36..43 为 X。若是 TB 采样时序问题，不会只坏这两个 32-bit 字段而其余字段全对。
- **独立单进程 probe**（`p-n-probe`，Start 06:33:47、End 06:44:05、Elapsed 0:10:18、Errors 0）早于两次 4 帧运行，给出同一 `stream_len=1,665,923`、同一 `header=…xxxxxxxxxxxxxxxx`、同一 `core_interval=6,104,479`。两次 4 帧进程的并发写不可能解释这个更早的单进程结果。
- 结论：X 是 A core 的 stream/header CRC 路径在 DUT 输出上驱动的 X；具体 RTL 行未定位（开发已声明为未验证假设），但不影响“头字节 36..43 = X”这一事实。

#### 审计判定

- **n-4f 的两个进程是真实的**（两条 rc=0、两个不同墙钟、两个不同启动/结束时间可由 07:14:05/07:14:59 反推）；冻结的 n-4f 证据来自后结束的 1777.7 进程，其 log/caps/evt/stats 完整且自洽。**先结束的 1743.7 进程的 log/caps 已被覆盖，无法单独检查**；这解释了为什么 `n-4f.log` 只有一个 Start/End，也说明 result §4 / r0-ruling 的“两个 End time”叙述与冻结文件不符。
- **l-4f 只有一次运行**：`run_4f.ps1` 只启动一个 L job；`commands-r0.jsonl` 没有 l-4f 命令；l-4f 日志只有一个 Start/End。被删的 l-4f rc=null 记录不可能是第二个 L 进程。
- **probe 只有一次运行**：`commands-r0.jsonl` 只有一条 probe 命令；probe 日志只有一个 Start/End；时间线上也没有第二次 10 min probe。被删的 probe rc=null 记录不可能是第二个 probe 进程。
- **删除记录的性质**：内容不可恢复（无法直接验证），但“没有第二个 l-4f/probe 进程”由命令清单 + 单日志 + 时间线共同支持；删除属于**记账违规（应标注而非删除）**，不是隐藏进程。若强行把两条被删记录当作独立进程，vsim 墙钟会变成约 8,299 s >7,200 s；但该假设与“l-4f 无第二命令、probe 无第二日志”矛盾。因此本审计采用 19 条/9 vsim/5,921 s 口径。
- **对 kill 的影响**：无。n-4f 的幸存 run 是确定性的完整 run；probe 是更早的独立单进程复现；L4 是单进程；两条 kill 事实均可由幸存证据直接判定。并发/删除只影响“manifest provenance 的叙述可信度”，不影响“caps ↔ 幸存 log ↔ evt/stats ↔ 候选”的哈希/数值绑定。
