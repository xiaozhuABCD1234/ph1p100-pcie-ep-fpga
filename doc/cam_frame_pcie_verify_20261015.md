## 1. 抓帧与寄存器原始证据（实测）

板子 `orangepi-5-max`，19:23–19:30，PCIe EP BDF `0000:01:00.0`（`1edb:abcd`），全程**没有**下 bit / 重启 / insmod。

### 1.1 相机源抓帧（`/root/cam_grab <out> cam`）

```
cd /tmp && /root/cam_grab /tmp/cam_a.pgm cam
MAGIC=0x50434946  OK
WIDTH=640 HEIGHT=480 DATA_LEN=307200 帧数=1249
CTRL=0x00000015（写源=相机）
cam_stat[31:0]=0xcfee7cb1 [63:32]=0xcfee0020 tap=110
帧号 1254 -> 1255（在递增）
已写出 /tmp/cam_a.pgm（307200 字节像素，宽 640 高 480，读到全 F 次数 0）
rc=0
```
（共抓 3 帧：cam_a 帧号 1255 / cam_b 3243 / cam_c 7553；工具每次都等到"缓存字 0 变了"才写盘，即缓存确实在被相机源写入。）

紧接的只读寄存器快照（`/root/pcitest/regdump`，无写操作）：

```
+0x40: 50434946 00000015 00000001 00000e82     MAGIC CTRL STATUS FRAME_CNT=3714
+0x50: 00000280 000001e0 0004b000 00000000     W=640 H=480 DATA_LEN=0x4B000 PTR
+0x80: cfee7ca1 cfee0020 00002aa6 00000000     A-stat  B-stat  A-vsync=10918
+0x90: 5ef9cb66 00000000 fffffe34 0000006e     A-pix   B-pix   0x98    0x9C=0x6E
+0x74: 00000010  ...                            (写口调试)
```
解码（依据 `rtl/ep_side/ph1p_pcie_ep_top.v:1036-1044` 拼接）：
- A-stat `0xcfee7ca1`：bit0 字节时钟在跳=1、bit[4:1] lane_valid、cfg_done=1、bus_err=0、auto_delay_done=1、收到过像素=1、tap=46（bit[21:16]）、XCLR 已放开=1、CSI rst_n=1、SCL/SDA=1、标签 `0b110011`✓。
- `0x98=0xfffffe34`：`r_mclk_sel_f`(bit4)=**1** → 当前 MCLK 源 = `sys_clk 50MHz ÷ 4 = 12.5MHz`（50% 占空）；`r_reinit_cnt`[8:5]=1（发生过 1 次"配置重触发"）；XCLR=1。
- `0x9C=0x6E` = `{manual_en=1, tap=46}` → 手动 tap 配置未被扰动。
- 全程没有读到 `0xffffffff`，没有 `0xdeadbeef` 之外的异常，工具退出码 0/读全 F 次数 0。

> 说明：板上那个旧版 cam_grab 打印的 `tap=110` 是 `0x9C` 的裸值（0x6E=110，=manual_en|tap=46），不是状态字的 tap；真 tap=46（`cam_stat[21:16]`）。它某一版的"帧数=26594"是抓帧前 `cam_sel` 还是 0 时读到的**测试图源**帧计数，不是相机帧数。所有计数我以 regdump 的 0x4C/0x88/0x90 为准。

## 2. 判据与数值结果：这一帧是真实相机像素

PGM 布局校验：PGM 头 4 字节 = 缓存字 0 = 帧号（`cam_a` 头 4 字节 `E7 04 00 00` = **1255**，与工具打印的"帧号 1254→1255"一致 ⇒ 像素 (x,y) 在 PGM 扁平流里的下标 = 4+640y+x，下面所有统计都先扣掉这 4 字节）。

### 判据 1：与测试图源公式无关（**实测**）
`img_frame_src.v:131` 的公式是 `pix = (x + y + lane + frame_cnt) & 0xff`（斜向渐变）。检验：

| 检验 | cam_a | pattern 源 |
|---|---|---|
| `(im - x - y) mod 256` 的不同取值数 | **256**（完全无梯度关系） | 每行只有 1 个值 |
| 与 pattern 图逐字节相同率 | **0.41%** | — |

### 判据 2：不是空帧 / 全 0 / 全 F（**实测**）

| 图 | mean | std | min/max | 唯一值 | 0 值 | 255 值 |
|---|---|---|---|---|---|---|
| cam_a | **21.28** | 9.19 | 0/255 | 187 | 135 (0.04%) | 10 |
| cam_b | 21.06 | 9.67 | 0/255 | 178 | 131 (0.04%) | 10 |
| pattern | 126.88 | 73.95 | 0/255 | 256 | 1211 | 1206 |

帧偏暗（88.5% 像素 <32），但**不是常量场**：187 个灰阶、有 255 饱和点、有 2-D 结构（见判据 4）。合理成因：取的是 4K 帧左上角（含传感器顶部 dummy/光学黑行），且环境暗/曝光低——这一点标为**未确认**（没查寄存器表里的曝光/增益设定）。

### 判据 3：2×2 Bayer 周期性 + 颜色通道序（**实测，最强判据**）

对 20×20（下表最后一行 60×60）块做 2×2 象限均值（q00/q01/q10/q11）：

| 区域 | q00(R) | q01(G) | q10(G) | q11(B) | \|G01−G10\| |
|---|---|---|---|---|---|
| y=0 x=0（疑光学黑/暗行） | 13.18 | 14.65 | 13.63 | 13.12 | 1.02 |
| y=80 x=80 | 19.36 | 29.27 | 29.54 | 24.42 | 0.28 |
| y=200 x=0（左中亮区） | 23.97 | **40.45** | **40.68** | 29.07 | **0.23** |
| y=200 x=360（竖亮线） | 18.70 | 26.47 | 26.45 | 21.04 | **0.02** |
| y=400 x=560 | 15.46 | 20.33 | 20.17 | 16.09 | 0.16 |
| 对照 pattern 同块 | 120.10 | 121.10 | 121.10 | 122.10 | — |

特征：**两个对角位置（G/G）统计上完全相等（Δ<0.25），且恒为最亮；一个角最低（R）、另一个居中（B）**，三个亮区里这个"序"完全一致 —— 这是彩色滤波阵列传感器（RGGB）的教科书特征，任何测试图/垃圾数据都造不出这个固定的颜色序。另外，在疑似光学黑区（y=0）象限差异塌缩到 ~1，符合"光学黑处各颜色都只有暗电流偏置"。

相邻像素差（`d1/d2` = 1 像素差 / 2 像素差）：

| 图 | mean\|dx\| | mean\|dx2\| | d1/d2 | mean\|dy\| | mean\|dy2\| |
|---|---|---|---|---|---|
| cam_a | 5.82 | 1.18 | **4.9** | 5.85 | 1.13 |
| cam_b | 5.92 | 1.12 | 5.3 | 5.95 | 1.10 |
| pattern | 2.00 | 3.98 | **0.5** | 2.02 | 4.02 |

相机帧"隔 1 像素像、相邻像素不像"（Bayer），pattern 图恰好相反（连续斜坡）——两者在结构上是镜像关系，不可能是同一个源。

### 判据 4：图像是活的、有真实场景结构（**实测**）
- 三次抓帧（19:23 / 19:25 / 19:29，相隔 2~4 分钟）的行均值剖面相关 **r=0.909 / 0.967 / 0.860**，而 cam 与 pattern 的同类相关 ≈ **0.01~0.2**（无关）。行/列均值剖面（`cam_a` 行均值 12.0~26.5、列均值 14.4~30.0）三次都很接近 ⇒ 稳定的光学结构（顶部暗行 + 左侧亮区 + x≈360 一条竖亮线）。
- 但**逐像素**不同：cam_a vs cam_b 只有 18.8% 像素相同、mean|Δ|=5.07、max 170；最亮 20×20 块从 98.9 → 66.8 → 64.0。⇒ 内容在变（光照/自动增益变化或场景变化），**不是冻结的陈旧缓存**。

### 已知的测量局限（如实说明）
- 这一帧**不是时间上单一的一张**：PIO 逐 dw 搬运 307200 B 需要 ~0.4 s，而相机帧周期 64 ms（见 §4），所以各行大概率来自相邻几帧（撕裂）。**在 pattern 抓帧里我直接证实了撕裂**：480 行里有 474 行能各自解出一个恒定帧号，共出现 6 个不同帧号。相机帧因为帧缓存无双缓冲，无法用现有工具消除该效应（工具是旧版，pattern 模式写 CTRL=0x05 即 enable=1 连续出帧，属"边写边读"）。这不影响"像素真伪"判定。
- 帧偏暗的成因（曝光/增益/是否包含光学黑行）**未确认**，本轮没查寄存器表的曝光段。

## 4. 时序约束核对：`constraints/ph1p_pcie_case_ep.sdc`（**已过期**）

### 4.1 约束里写的是什么（实测，读文件）
```
create_clock -name {cam_a_clk_lane} -period 1.333 -waveform {0.000 0.667} [get_ports {mipi_a_clk_hs_p}]   # 750 MHz
create_generated_clock -name {cam_a_byte_clk} -source [get_ports {mipi_a_clk_hs_p}] -divide_by 4 ... u_csi_a/u_rx_phy/u_hs_clk_div.clkdivout
```
注释里写得很明确：`1.5 Gbps/lane → clock lane = 750MHz(1.333ns) → 字节时钟 = ÷4 = 187.5MHz(5.332ns)`，依据是"与板测遥测 CKA=CKB=0xB2D 一致"。

⚠️ **关键点：这个 1.5Gbps/lane 是"按 MCLK=25MHz 推的"，不是从 MCLK 分频器直接推的。** 时序上它是这么来的：
- `PH1P_PHY_LCLK(DIV="4")` 只对 **MIPI clock lane 引脚**分频（`rtl/ep_side/cam/rx_phy_ph1p.v:59-75`），MCLK 不参与。所以 MCLK 改动**不会**自动改变字节时钟的约束值——两者的一致性完全靠人工按"INCK→链路速率"换算。
- 该约束是 **commit 21dd0e6（17:44）** 与"把 MCLK 改成 25MHz"**同一笔提交**加进去的；随后 **commit c2daa30（19:16）把 MCLK 改回 12.5MHz，但没有动 .sdc**。
- 引用链核对：参考工程 `f9p_ph1p100_imx415x2_top.v:31` `MCLK_DIV=2 → 50MHz/2 = 25MHz`，其 `README.md:17` "4K@30，1.5Gbps×4 lane"、`:30` 遥测 `CKA=0xB2D`；`0xB2D=2861 = 187.5e6 × 0.5s / 2^15`，与该工程 `clk_activity(DIV_BITS=15)` 的计数口径**吻合** ⇒ "187.5MHz@INCK=25MHz" 这条自洽。

### 4.2 现在顶层实际在跑什么（实测，读 RTL + 板上寄存器）
- `CTRL[2]=1`（0x98 bit4=1、CTRL=0x15）⇒ `sys_clk(50MHz, .al/SDC:20ns) ÷ 4 = 12.5MHz`，周期 80ns、占空 50%（`ph1p_pcie_ep_top.v:847-853`）。
- `CTRL[2]=0` 的另一源 = `tl_clk_user(62.5MHz, al_ip 参数 PCIE_USR_CLK=62.5) `经 3 位累加器 +2/−3 → 12.5MHz，周期恒 80ns、占空 32/48ns（`:834-845`）。
- **两源都是 12.5MHz**，所以 MCLK 频率无歧义。

### 4.3 不一致判定

| | clock lane | 字节时钟（÷4） |
|---|---|---|
| .sdc 里写的（= INCK 25MHz 时代） | 1.333 ns（750 MHz） | 5.332 ns（187.5 MHz） |
| 现在 MCLK=12.5MHz 的理论值（**推论**） | 2.667 ns（375 MHz） | 10.667 ns（93.75 MHz） |
| 是否一致 | **否，差 2×** | **否，差 2×** |

**"理论值"是推论，依据（实测锚点）：**
1. 同一张 201 条寄存器表（`ui_imx415_reg.v`，MODE 固定 `2'd1`=4K，`ph1p_pcie_ep_top.v:984 / :999`）、同一块子卡，参考工程 INCK=25MHz 时遥测 **30 fps**；
2. 本板此刻实测 **15.62 fps**（regdump 两次采样：A-vsync 10449→10918，Δ469；FRAME_CNT 3245→3714，Δ469；Δt=30.026 s ⇒ 15.62 fps；另一对采样 8461→10449 / 127.24 s 同样 15.62 fps）。比值 **0.52 ≈ 25/12.5**；
3. 帧时基 HMAX/VMAX 在同一张表里是常数，帧率只随 INCK ×（表内固定 PLL 倍数）缩放；MIPI 链路速率来自同一 INCK 参考的固定倍数 ⇒ **链路速率同比减半**（750 Mbps/lane → clock lane 375MHz → 字节时钟 93.75MHz）。

**影响方向（对你决策有用）：** 约束比实际**严 2×**（按 187.5MHz 去算实际跑 93.75MHz 的域）⇒ 对 setup 是**保守**的，不会产生假违规；hold 检查与周期基本无关，也安全。也就是说重建后 `SWNS +0.349ns / STA coverage 97.48%` 那组数字**不描述当前（12.5MHz MCLK）的真机配置**，只是偏保守。反过来风险是：将来若把 MCLK 再调高（真实链路 >187.5MHz 等效），这条手工写死的约束就变成**欠约束**。

**按要求：我没有改任何文件。**

### 4.4 未确认 / 待查（不写成功）
- **本 bit 没有任何"字节时钟测频"寄存器**：`clk_activity(DIV_BITS=15)` 只把结果并成 `r_a_bclk_seen`（"跳没跳过"的锁存位），没有对 tl 域的翻转计数，`w_cam_stat` 里也没有该计数字段 ⇒ **无法上板直接测出字节时钟频率**，也没有示波器。所以"实际 = 93.75MHz"是**推论**，不是实测。
- 顺带发现一个**我没查清的吞吐疑点**（不影响上面结论，故不作为证据）：0x90 像素组计数 = 8.426 M 组/s ÷ 15.62 fps = **539,400 组/帧**，只有 4K 一帧应有的 2,073,600 组的 26%；而按"每组消耗 5 个字 ×4 lane-byte"折算出的每帧链路运输量 10.79 MB 又恰好≈4K RAW10 的 10.36 MB。两者不能同时成立，说明接收链每行只处理了约 250/960 组就落后丢弃（丢尾不影响前 640 像素的裁剪图，故图像仍然正确）。这属于吞吐设计问题，**未确认，本轮不展开**。
