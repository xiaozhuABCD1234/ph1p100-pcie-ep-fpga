## 0. 一句话结论

真实平台与 v1 假设的板卡**完全不同**：PH1P100SBG484 **没有 MIPI D-PHY 硬核**（与 v1 的 PH1A90SEG324 一样要走软 PHY，但原因与证据不同），但**本项目已经把软 MIPI PHY + CSI-2 接收在真板上打到 2 路 4K30、1.5 Gbps/lane**（参考工程 `f9p_ph1p100_imx415x2` 实测），**FPGA↔RK 的 PCIe Gen2 x2 也已经在 RK3588 上跑通寄存器与整帧数据**；真正卡住下一步的不是接口，而是**片内 ERAM 帧缓存方案在物理上不成立**（当前工程因此**布局失败、不 fit**）与**预处理/压缩模块还没写**。

**关键器件事实（决定整个技术路线）**：PH1P100 **没有 MIPI D-PHY 硬核**。

> `DS1300_PH1P_Datasheet_1.2.1.pdf 表 1-1 PH1P FPGA 系列选型表`：`MIPI DPHY` 一行为 `- | 2 | - | 2`（列依次为 PH1P100 / PH1P35 / PH1P50 / PH1P50GEG324），即 **PH1P100 = 无**，PH1P35/PH1P50 = 2 组。
> 交叉印证（TD 里 IIP 的真实可选值）：`/opt/anlogic/TD_Release_2026.2_NL/ip/depot/MIPI_DPHY_1.0/Dependency.tcl` 的 `MIPI_PHY_TYPE_PROC` 对 `$IP_DEVICE == "PH1P100SBG484"` 无论 TX/RX 都只 `return [list "LVDS"]`（对比 `PH1P35M*`、`PH1P50MBG484/MEG324*` 返回 `[list "LVDS" "Hard MIPI"]`）。
> 因此：**本板只能走软 PHY**（LVDS 差分收 + ISERDES + 动态 IDELAY 重建），v1 的「软 D-PHY」判断在这一点上沿用成立，但**依据要换成 PH1P 手册与 TD 的 IP 设备表，不能再引用 DS900 的 PH1A 结论**。

参考工程 `~/Projects/f9p_ph1p100_imx415x2`（同一块 F9P + FEP-VID006-MIPI + 2× IMX415）README 记录的**上板实测**：

**软 PHY 的实现路径**（原创代码，非厂商 IP）：

> `f9p_ph1p100_imx415x2/uisrc/03_ip/mipi_phy_ph1p/rx_phy_ph1p.v` 头注释：「时钟 lane : IBUF_DIFF → PH1P_PHY_LCLK(DIV=4) → 串行时钟 + 字节时钟(BUFG)…数据 lane : IBUF_DIFF → PH1P_LOGIC_DYNAMIC_HR_IDELAY(tap) → PH1P_LOGIC_HR_ISERDES(DDRX4) → csi_rx_byte_align（找 0xB8 同步头，输出对齐后的字节 + 有效）」

CSI-2 协议层与相机寄存器表来自米联客 AFC03 例程（PH1A90 平台）：
> `…/uisrc/03_ip/README.md`：「`mipi_csi_2/` CSI-2 包层、字节对齐、IDELAY 眼图扫描 ← 米联客 AFC03_IMX415_PCIE_X1 例程」「`ui_imx415_cfg/` IMX415 寄存器表 + I2C 主机 ← 同上；201 条寄存器表，支持 1080p/4K/720p 三档」

**上板踩坑（都是设计必须吸收的事实）**：

1. 差分输入必须开端接：`PH1P_LOGIC_IBUF_DIFF` 的 `DIFF_TERM` 默认 `"FALSE"`，开启后同一 tap 收包数 743 → 4151（5.6 倍）。
2. IDELAY 采样点必须实测：自动扫描在本板找不到窗口，回落到 tap=32，而**实测眼图中点在 tap=45~47**（32 的收包率只有 1/9）；现固定 `tap=46`。
3. 子卡 A 排那侧差分串了 100R、C 排 0R 直连 → 必须用 C 排球号（用 A 排时"每条 lane 都能找到同步头但组装成包就废"，只收到 ~12% 的包）。
4. 传感器 XCLR 释放/I2C 启动要等久一点（MCLK 先跑、168ms 后放开 XCLR），否则 B 口那颗 NACK 且一直不出流。
5. 帧缓存必须写成"简单写口"才会被判成 ERAM20K，否则落成分布式 RAM；**单块大显存的选择器会把时序拖垮**，需拆 4 bank（整帧 518KB 版本实测 SWNS −0.312 ns）。

## 3. 五项硬性交付的落地设计（真实硬件）

### 3.1 交付 1：MIPI CSI 图像传感器 FPGA 驱动 IP 核

**采用：自研软 PHY + 复用/重写 CSI-2 包层**（已有可运行资产，只需整理成"IP 核"形态）。

模块划分（`fpga/rtl/ep_side/cam/` 已存在同名文件，属"整理 + 参数化"而非从零写）：

| 模块 | 职责 | 现状 |
| --- | --- | --- |
| `rx_phy_ph1p.v` | 时钟 lane：`PH1P_LOGIC_IBUF_DIFF(DIFF_TERM=TRUE)` → `PH1P_PHY_LCLK(DIV=4)` → BUFG 出字节时钟；数据 lane：`PH1P_LOGIC_DYNAMIC_HR_IDELAY` → `PH1P_LOGIC_HR_ISERDES(DDRX4)` | 已有（参考工程原创） |
| `csi_rx_byte_align / word_align / gear_box / 10bit_unpack` | 字节对齐（找 CSI-2 HS 同步头 0xB8）、字对齐、Lane 打包还原 | 已有（米联客 AFC03 复用） |
| `csi_rx_hdr_ecc / csi_rx_packet_handler` | 短包（FS/FE/LS/LE）与长包（PH+payload+PF）、VC/DT、ECC/CRC | 已有 |
| `ui_i2c.v / ui_imx415_reg.v / ui_cfg_imx415.v` | I2C 主机（100 kHz，按 62.5 MHz 重算 `CLK_DIV=624`）+ 201 条寄存器表（4K/1080p/720p 三档） | 已有；**MCLK 分频算错、I2C 忙位拼错名、配置失败不重试**（见 §6 风险） |
| `mipi_csi2_rx_ph1p.v` | 上述的集成顶层，输出 `O_pixel_data[39:0] + O_pixel_valid + O_vsync/O_in_frame/O_in_line` | 已有 |

**必须修的三处**（有明确证据，不是优化项）：

1. **MCLK**：`ph1p_pcie_ep_top.v:763-771` 的累加器分频实测输出 **12.5 MHz / 占空 40%**（注释写 25 MHz）。IMX415 明确只支持 `INCK 24MHz, 27MHz, 37.125MHz, 72MHz, 74.25MHz`（`IMX415 数据手册` INCK 波形段），**12.5 MHz 不在允许清单内** → 必须改成 24/27 MHz（用 PLL 出）。
2. **BANK13 跳线必须先切 1.8V**：子卡控制信号是 1V8（FEP-VID006 手册 §1「2 路 MIPI 接口的控制信号为 1V8 电平信号」），而当前工程 `.adc` 只抄了引脚、**没抄这条前提**（参考工程 `fep_vid006_imx415.adc` 头部原文有）。
3. **字节域时序约束**：`constraints/ph1p_pcie_case_ep.sdc` 只有 4 行（sys_clk / derive_clocks / rename），**两个 MIPI 字节时钟没有任何 create_clock**，导致 STA 覆盖率 71.84%、`u_word_align/u_packet` 在时序报告里出现 0 次。

> 已证能力上限（真板实测）：**1.5 Gbps/lane × 4 lane × 2 路 = 12 Gbps 同时收**（参考工程）。这比 v1 计划里最激进的「1080p60 4-lane 311 Mbps/lane」高一个数量级，说明**软 PHY 不再是本项目最大风险**。
> IMX415 自身上限更高：数据手册「MIPI CSI-2 / 4 Lane, **2079 Mbps**」「10 bit: 90.9 frame/s（All-pixel scan）」。

### 3.2 交付 2：≥3 种硬件预处理

**采用「流式（行缓存）+ 单路独立实例」结构**，不做整帧进 ERAM/DDR 的处理（理由见 §4）。建议的 3 种基础 + 2 种加分：

| 级别 | 算法 | 实现要点（面向 4K@30 的吞吐） |
| --- | --- | --- |
| 基础 1 | 灰度化 | RAW10 需先做 2×2 同色平均（Bayer 同色）或 RGB 去马赛克；参考工程已实现「2 抽头水平 + 2 行垂直平均」的 2×2 平均灰度（`cam_preview.v`） |
| 基础 2 | 3×3 高斯（可分离） | 行缓存 2 行 × 4K × 10 bit（每 stage 76.8 Kbit）→ 行卷积 → 行缓存 → 列卷积；系数用移位加法或 DSP |
| 基础 3 | 直方图 + 均衡 | 帧内 256 bin 累加（ERAM 小块），CDF 由 CPU 或片上求；需与帧同步双缓冲 |
| 中级加分 | Sobel / 阈值分割 / 3×3 形态学 | 直接复用高斯的两级行缓存结构 |
| 高级加分 | 亚像素边缘/尺寸测量 | 梯度重心法 + 标定换算；误差判据需先算像素当量（见 §7 风险） |

**吞吐约束（关键，必须体现在设计里）**：4K30 单路 = 3840×2160×30 = **249 Mpixel/s**。字节时钟实测只有 **187.5 MHz**（= 1.5 Gbps/lane ÷ 8），所以
- 1 pixel/clock 的流水线只能吃 187.5 Mpixel/s → **不够**（仅 75%）；
- 二选一：**(a) 同域并行 2 pixel/clock**（面积×2）；**(b) 把处理时钟抬到 ≥250 MHz**（需要新的时序收敛验证）；**(c) 处理前先抽降**（如 1080p 或 ROI）。
> v1 的「4×1080p60 = 500 Mpixel/s，每路独立实例或成对共用」在真板上要改成：**2 路 4K30 = 498 Mpixel/s，与 v1 的 4 路 1080p60 同量级**，资源估算要按这个来，而不是按 v1 的假设。

### 3.3 交付 3：JPEG/LZ77 硬件压缩

必须**有损 + 无损双模且无损里真的含 LZ77 或 Rice**（v1 审查报告 §7.1 的提醒：「若'无损'通路只做 DPCM，会被质疑没有 LZ77」）。

| 模式 | 通路 | 目标压缩率 | 备注 |
| --- | --- | --- | --- |
| 有损 | 8×8 DCT → 量化（表可切换）→ ZigZag → Huffman（Baseline） | 8~20:1 | 灰度输入时只有亮度分量，DCT 规模可减半 |
| 无损 | MED/左邻预测（DPCM）+ **LZ77 匹配** 或 Rice 熵编码 | 2~3:1 | 需给出逐字节可逆性验证方法（本机无仿真器 → 只能用板测比对） |
| 码率环 | 按输出缓冲水位/QP 步进反压量化表索引 | — | 对应拓展项 3 中级/高级 |

**资源与复用策略**：先做「**单路单实例实测**」再决定复用（v1 审查 §5-③ 已指出「4 路并行 + 压缩复用 2 份」在 250 Mpixel/s/份 下对流水线深度与 Huffman 表带宽都是硬要求）。本机不能编译验证 → 该模块的所有资源数在本文中一律标 **待实测回填**。

## 4. 资源与带宽核算

### 4.1 片内存储：这个器件的 ERAM 只能做行缓存，不能做整帧

| 量 | 计算 | 结果 |
| --- | --- | --- |
| ERAM 总量 | 300 × ERAM20K(20 Kbit) = 6,000 Kbit | **750 KB** |
| 4K 灰度整帧 | 3840×2160×1 B | **8.29 MB ＝ 全器件 ERAM 的 11 倍** |
| 1080p 灰度整帧 | 1920×1080 | 2.07 MB（2.8 倍） |
| 640×480 灰度整帧 | 307,200 B | ~120 块（41%）——**当前工程实际落成 65536 LUT（分布式 RAM），直接布局失败** |
| 参考工程 2 个 960×540 帧缓存 | 2×518 KB | 192/300 块 = **64%**（已到危险区，且需拆 4 bank 才能收敛时序） |
| 单路 3×3 高斯两级行缓存 | 2×3840×10 bit × 2 级 | 153.6 Kbit ≈ 8 块 ERAM ≈ **2.6%** |

**结论：任何「整帧进片内」的设计在 4K/1080p 下都不成立；预处理必须按行缓存流式做。**（这正是 v1 审查 P0-2 建议的"流式预处理优先"，在 PH1P100 上从"降风险"升级为"唯一可行"。）

### 4.2 DDR3：可以放整帧，但速率口径必须先定

见 §5.2 的核查；按最保守口径（800 Mbps × 32 bit = **3.2 GB/s 峰值**）算：

| 用途 | 带宽 |
| --- | --- |
| 2 路 4K30 RAW10 写入 | 2 × 2.49 Gbps = **0.62 GB/s** |
| 同量读出（送预处理/压缩） | 0.62 GB/s |
| 合计 | **1.24 GB/s = 800 Mbps 口径下的 39%**；若按 1066 Mbps（4.26 GB/s）→ 29%；按 1600 Mbps（6.4 GB/s）→ 19% |
| 容量 | 4K RAW10 一帧 8.29 MB；2 路 × 双缓冲 = 33 MB；即便 4 路 × 三帧 = 100 MB，512 MB 也够 |

> 结论：**DDR3 做整帧缓存容量够、带宽在 800 Mbps 口径下也够（39%）**，与 v1 在 PH1A90（16 bit @1066 → 2.13 GB/s，占用 56%~85%）的窘境不同。但注意：PH1P100 的 DDR 控制器/LCLK/PHY 是**独立 IP**（`ip/depot/MIS_DDRF6F1D0P0_1.2`），它的 PLL/BUFG 占用与引脚约束要单独规划，且当前工程**尚未集成**。

### 4.3 链路带宽总账

| 环节 | 2 路 4K30 | 4 路 4K30 | 备注 |
| --- | --- | --- | --- |
| MIPI 输入（RAW10） | 4.98 Gbps | 9.95 Gbps | 软 PHY 已证 12 Gbps（1.5 Gbps/lane × 8） |
| 灰度后（8 bit） | 3.98 Gbps | 7.96 Gbps | 抽降至 1080p60 则为 2.49 Gbps |
| PCIe Gen2 x2 可用 | **8 Gbps**（理论 8b/10b 后） | 同 | 灰度原图 2 路已占 50%；4 路必须压缩 |
| 压缩后（JPEG 10:1） | 0.4 Gbps | 0.8 Gbps | 余量充裕 |
| 无损（2:1） | 2.0 Gbps | 4.0 Gbps | 在 8 Gbps 内但余量变小 |

> **结论：压缩模块不是"为压缩而压缩"，而是 4 路场景的必要条件；2 路场景下压缩主要服务于"无损+有损双模"的得分点。**

### 5.4 相机侧引脚可行性：2 路已实测，4 路需新转接卡（任务书问题 a 的延伸）

当前 2 路 4-lane 相机占用 BANK13 的 28 根脚（MIPI 20 + 控制 8）。BANK13 共 48 根（24 对差分），**剩余 20 根**：

- 剩余球号：`G15 G16 H14 H15 H17 H18 J14 J15 J17 K13 K14 K16 K17 L13 L14 L15 L16 M13 M15 M16`
- **剩余里 0 根 GCLK 专用脚**：BANK13 的 4 对 GCLK（`K18/K19`、`J19/H19`、`J20/J21`、`L19/L20`）中，2 对（K18/K19、J19/H19）被用作两路相机的**时钟 lane**，另 2 对（J20/J21、L19/L20）被**当作数据 lane** 用掉了。

因此：

| 4 路方案 | 引脚可行性 | 说明 |
| --- | --- | --- |
| 4 路 × 4-lane（像 K 现在的子卡） | **不可行** | 需要 20 对差分（4×(1 clk+4 data)）+ 控制线，BANK13 只有 24 对，且 4 对 GCLK 里 2 对要当数据用 → 时钟脚不够 |
| 4 路 × 2-lane + 共享/复用控制 | **理论可行** | 4×(1 clk+2 data) = **12 对**，4 对 GCLK 全部作时钟；控制线（MCLK 共享、I2C 共享总线 + IMX415 `SLAMODE0/1` 改从地址、XCLR 每路 1 根）用剩余 12 对拆单端。**但这需要自制 FEP 转接卡**，现有 FEP-VID006-MIPI（2 路）用不了 |
| 4 路中 2 路走 CEP 兜底 | **不建议** | CEP 是 2.54 排针（无阻抗控制，手册写 LVDS 500 Mbps），且引脚与 RS485/音频复用（`MLK-F9P底板.pdf` 第 518–572 行 `B14_L9_N复用CEP_L16_N` 等） |

**附带的好消息**：IMX415 支持多传感器同步——数据手册特性表列出「**Synchronizing sensors function**」，且 `XVS/XHS` 有从模式输入特性（Register `XMASTER = 1`）与「Slave Mode and Master Mode」章节；CAM005 模块也已经把 `VI_HS`/`VI_VS` 引到 FPC 座上（子卡接口定义 PDF）。→ **"4 路同步 + 时序校准"在传感器侧是有硬件根据的**，瓶颈在 FPGA 侧引脚与转接卡。

## 8. 建议的下一步顺序

> 原则：**先把"已经跑通的两段"接起来变成"基础项闭环"，再谈拓展项**；每步都以"能在板上看到数字"为验收。

**第 0 步（不写代码，先定案）**
1. 向米联客/安路确认 **U1（DDR3 速率）**、**U2（DDR refclk 占用 H4）**、**U4（FPC 座兼容）**、**U3（相机数量）**。
2. 把当前工程的 `.adc` 补上 **BANK13 = 1.8V 跳线前提**（断电改跳线），并修 **MCLK** 与 **`ic_busy/iic_busy`** 两处已知错误。

**第 1 步：让现有工程重新 fit 并产出位流**
- 把 `img_frame_src` 的 640×480 整帧缓存从"大 reg 数组"改成 `PH1P_LOGIC_ERAM` 显式例化（或直接删掉测试图样，改由 PCIe 搬 DDR/主存）。
- 验收：`phy_1` 成功、`gate.area` 的 `#eram` 有块数且 `#dram lut` 大幅下降、`route.qor` 无违例。

**第 2 步：补时序约束，拿到"字节域真的能收敛"的证据**
- 补两个 MIPI 字节时钟的 `create_clock/create_generated_clock` + `set_clock_groups -asynchronous`（照抄参考工程 `timing.sdc` 的做法）。
- 验收：STA 覆盖率上升、`final_timing.rpt` 里出现 `u_word_align/u_packet/u_gear_box`。

**第 3 步：把像素接进 PCIe（基础项 1+4 闭环）**
- 用 CSI-2 的 `O_pixel_data/O_pixel_valid/O_vsync` 做一个"**行缓存 + 行抽降**"的最小通路，把一行/一块像素推给 `ep_bar_win`，主机侧比对。
- 验收：RK3588 上能读到"来自真实相机"的像素（而不是测试图样），并记录行/帧计数。

**第 4 步：PCIe 升级到 DMA + 中断（基础项 4 的"高速"）**
- 启用引擎的 H2C/C2H（MM 模式）做数据搬运；在 EP 侧补 MSI/MSI-X capability。
- 验收：≥ 数十 MB/s 级带宽数据 + 中断驱动（不再是轮询帧计数）。

**第 5 步：单路 1080p 的预处理三件套（基础项 2）**
- 灰度（已有 2×2 平均基础）→ 3×3 高斯（行缓存两级）→ 直方图均衡；每级 `valid/ready` + 行缓存，**不落整帧**。
- 验收：TD 报告里 LUT/DSP/ERAM 实测回填；板上分屏对比。

**第 6 步：单路 JPEG（基础项 3 的有损半边）**
- 先做灰度 JPEG Baseline 单实例，测压缩率与吞吐；再决定"复用几份"。
- 验收：压缩率 + 码流字节数 + 恢复图 PSNR（对照用 PC 解码）。

**第 7 步：NPU 推理闭环（基础项 5）**
- 用 `rknn_model_zoo` 的 YOLOv8n int8（NPU 通路已实测可用），先做"PC 图 → NPU"再换"FPGA 图 → NPU"。
- 验收：帧率/预处理/推理/后处理分段的耗时表。

**第 8 步（拓展项，按性价比排序）**
1. **无损压缩通路 + 双模切换**（拓展项 3 高级；只需在已有链路上加一条通路）；
2. **4K@30 单路稳定 + 时序校准/亚像素尺寸测量**（场景 1 高级 + 拓展项 2 高级；测量精度必须先算像素当量）；
3. **双路并行 + 同步偏差统计**（拓展项 1 中级→高级的 2 路半步）；
4. **千兆网/SFP 上传 + TF 卡事件存图**（拓展项 6；用 SFP 替代 v1 的 4G）；
5. **4 路**：只有在"新转接卡 + 2-lane/相机 + 资源重算"三件事都成立后才启动。

**并行不做的（避免浪费）**：自研 FMC 转接板（已不存在 FMC，且子卡现成）、4G 模块方案（本板无接口）、MC20901/桥接芯片保险丝（软 PHY 已实测 1.5 Gbps/lane，不需要）。
