## 4. Frame commit / abort / backpressure semantics

Passing parts:

- `frame_commit` is asserted only on `svalid && out_ready && slast && !killed` (`a1_frame_top.v:149`). Clean cases have `p1_commit=1, p1_last=1`; abort/reset/proto/stall phase 1 all have `p1_commit=0, p1_last=0`.
- Recovery: all four abort/reset/proto/stall phase-2 frames commit and decode with 0 mismatch, so the next frame starts clean after the tested abort/reset paths.
- Busy-output stability: `p1_stab_err=0` and `p2_stab_err=0` in all cases; `stall_abort` reports `p1_pending_after_abort=1`, `p1_commit_after_release=0`, `p1_last_after_release=0` for a mid-frame pending word. The RTL holds `sdata/skeep` while `svalid && !out_ready`.
- Backpressure: random `out_ready` changes timing but not the byte stream (`bp20x5` = `odd20x5_p1d1`).
- `reset_recover` has `p1_abort=0` because synchronous reset clears `frame_abort_r`; it still has `p1_commit=0, p1_last=0`. This is consistent with reset semantics, though downstream sees reset rather than a `frame_abort` pulse.

### F1 (blocking, functional): abort with the final word pending leaves `out_last` asserted

The targeted TB `tb_abort_last.v` drives a 20×5 frame, stops `out_ready` exactly when the core presents its final byte, waits for `out_valid && out_last && !out_ready`, then asserts `abort` for four cycles and releases:

```
PENDING_LAST valid=1 last=1 keep=1 slen=117 stream_len=117
AFTER_ABORT valid=1 last=1 frame_abort=1 commit=0
RESULT saw_pending_last=1 last_while_pending=1 last_after_release=1 commit_after_release=0 frame_abort=1
ABORT_LAST_EOP_BUG reproduced
```

Why it is real, not a TB artifact:

- `assign out_last = svalid && slast;` (`a1_frame_top.v:148`) is **not** qualified by `killed`.
- The abort branch (`a1_frame_top.v:246–259`) sets `killed=1`, `frame_active=0`, `istate=I_ABORT`, but deliberately leaves the already-presented `svalid` word intact and does **not** clear `slast`. Therefore, if the pending word is the final word, `out_valid=1 && out_last=1` survives the abort; when downstream consumes it, it sees eop while `frame_commit=0`.
- The frozen `stall_abort` case aborts at group 3000 of 7680, so its pending word is an early word, not the final word. Its `p1_last_after_release=0` is therefore not evidence that the final-word corner is safe.
- This directly contradicts `dev-result.md` §1 "abort … 不置 eop" and guide §4 "`abort` … `eop` 不得置位". It is a half-frame eop (not a commit), which is still a P3 stop-condition violation.

No half-frame **commit** was observed: `frame_commit=0` in the targeted case and in all frozen abort/reset/proto/stall cases. The defect is specifically the eop/`out_last` signal, which downstream may use to publish the aborted frame.

Other untested/limited semantics:

- Invalid geometry (`W%4!=0`, `H<2`, `2*stride>4800`) and `pred_en=1 && prep_en=0`: the RTL has `GEOOK`/`I_DEAD` checks (`a1_frame_top.v:70–71, 271–274`), but the frozen regression has no such case. The RTL enters `I_DEAD` and requires reset; this is not a demonstrated "next sof recovers" path. The dev-result's claim that these are handled is code-inspection only, not simulation evidence.
- `prep_en`/`pred_en` are **not latched at `in_sof`**: the guide §5 says configuration is sampled at sof, but the RTL uses the live ports in the input path (`:317`), drain path (`:374`), and legality check (`:271`). A mid-frame change would corrupt the transform; no test covers this. Treat as an interface risk, not a proven failure in the frozen cases.
- "Committed frame not modified by a later abort" is not explicitly exercised. The DUT has no frame writeback buffer; committed bytes are external, and the abort branch requires `frame_active`, which is cleared at commit, so an abort after commit is ignored by design. The stats are only reset at the next sof. Mark as not directly tested.
- "Complete frame only" is true at the **commit** level (`frame_commit` only on the final word handshake), but the zlib bytes are streamed on `out_valid` before commit. A downstream that writes bytes immediately must buffer/rollback until `frame_commit`; the current contract is commit-gated, not store-and-forward.

## 5. Throughput basis (actual simulation, content-dependent, not a guarantee)

The numbers are from actual simulation counters, not theory:

- TB `p1_cycles = commit_cyc - first_cyc`: first accepted input group → `frame_commit`. For 1080p, `stats.txt` has `p1_cycles=4677301`, `p1_stall=3623574`, `p1_blocks=540`, `p1_stream_len=81707`.
- 4,677,301 cycles / 2,592,000 B = **1.8045 cycles/B**; at the assumed 187.5 MHz: 2,592,000 × 187.5e6 / 4,677,301 / 1e6 = **103.91 MB/s**. Gate 77.76 MB/s (0.4147 B/cycle) is met; 97.2 MB/s margin is met **on this frame**.
- `rand1920x16`: 80,991 cycles for 38,400 B = 2.1091 cycles/B → **88.90 MB/s**. It meets 77.76 but **not** 97.2. It is a stored-path frame; the 8 stored blocks are 38,400 B + 8×5 B + 6 B = 38,446 B.
- Small frames (`20×5`, `12×6`) are 44–46 MB/s because fixed per-frame/block overhead dominates; they are not the 1080p target geometry and are not used to claim the 77.76 gate.
- The 1080p input is a synthetic gradient (`a1_p3_gen.py` "grad") with 31.7:1 compression; the input is stalled for 3,623,574 of 4,677,301 cycles (77.5%). The measured value is a **single-frame average latency/throughput**, not a back-to-back multi-frame steady-state service rate. The 97.2 MB/s result is content-dependent and must not be presented as a guaranteed rate. The dev-result §4 already says "服务率随内容变化，不作跨图集宣称"; that caveat is correct and should be preserved in the final summary.
- The 77.76 MB/s gate itself passes for the 1080p target and for the 1920×16 incompressible case. No claim is made for real RAW, real image statistics, or dual-channel 155.52 MB/s.
