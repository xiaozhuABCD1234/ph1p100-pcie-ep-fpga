# T10.b15-ddr-pace — 用户小结（2026-10-26，规划）

**一句话**：画面链路已经全通了——A 相机会出图、几何没错、每帧都进了 DDR 槽；现在唯一的毛病是**读回来的时候每次少 1 个数据包**，所以一帧都编不出来。这一包只改 DDR 读的“排队规则”，不碰相机、不碰格式、不碰时序约束。

## 这次板级到底发生了什么

- A 相机恢复：`cap_frames=4470`，`pix_beats`/`line_rises` 正常涨，`crop_short=0`、`crop_geom_err=0`，`raw_pub=4470`（每帧都发布）。
- 但 A+ 读每帧都失败：`timeout=13,410`（≈3/帧）、`retry=8,940`（2/帧）、`giveup=4,470`（1/帧），`enc=0`、`exported=0`。
- 计数对不上：`ar=17,213,681` vs `r=17,200,031`，**差 13,650** —— 每次读尝试都少回 1 个 R，稳定复现（就是之前叫 H4 的那个现象）。

## 我的判断（有源码依据）

读桥里那个“同一时刻只允许一笔读”的标志，**在第一个数据拍回来时就被清零了**，而不是等这一笔读完（`rlast`）。于是：

1. 前一笔还没回完，下一笔就可能被发出去；
2. 这中间晚到的那一拍，桥上 `rready` 是 1（看起来收下了），但**没有真的入队**——被静默吞掉。

每帧读几千笔，最后总差 1 拍 → 帧永远读不完 → 超时 → 重试 → 再差 1 拍 → 放弃。所以 `enc/exported` 一直是 0。

## 这一包怎么改（只改 1 个文件）

`p2_ddr_bridge.v`：

- 一笔读从发出到 `rlast` 之间，**绝不发下一笔**（真正的一笔在途）；
- `paxi_rready` **一直保持 1**，收到的每一拍都必须入队，不许再“假接收”；
- 靠“发之前先确认读缓冲是空的”来保证不溢出，而不是靠反压（反压正是丢数据的来源）；
- b13 的 8192 超时 + 最多 2 次重试**原样保留**当兜底（理想情况板上应该一次都不触发）；
- 状态包 v5 **一个字节都不动**（241 B / 59 字段），未完成笔数直接用现成的 `ar − rlast` 读出来。

其余 10 个 RTL 文件逐字节不变，SDC 一行不改，相机/几何/帧格式/四槽/UART/时钟全部冻结。

## 关于 A/B 两路

- 本轮**只用 A**（板上就是 `sel=0`、`bit20=0`）。
- B 的代码还在核里、照常初始化，只是不选它。
- b14 那套 `CAM_SEL` 选择逻辑**本轮不合并**——它会把“相机选择”和“DDR 读”两个变量混在一起；等读通了再单独做。

## 怎么算过关

- **仿真**：正常整帧能出；故意丢 1 个 R 时能超时→重试→整帧成功；连续 3 帧；满尺寸两帧；P1 三黄金逐字节不变；b12/b13 回归；再补 4 个刁钻用例（丢最后一拍、晚到重复包、ready 被压 100 拍、数据中途断 64 拍）。
- **构建**：布线 0 违例；WNS 目标 ≥+0.05（落在 +0.003~+0.05 也接受，但会标注“薄余量、非量产签核”）；1 次 bitgen + 1 次 CWC。
- **板级**：先下载、再开 COM8 跑 150 s。目标很硬：**timeout / retry / giveup 全部归零**，`enc_frames`/`exported` 有增量，至少 1 帧四个 CRC 全过 + zlib 解压成功。
- **如果还是每帧丢 1 个 R**：立刻停，把 `ar/r/rlast/stale` 和地址证据留全，交回来重新判，**不做第二次下载**。
