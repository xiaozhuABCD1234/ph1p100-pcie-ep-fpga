# b6 用户摘要（收尾，2026-10-24）

**结论：T10 的压缩吞吐回归已修好并通过独立验收（PASS），但 T10 整体仍未完成。**

- 修好的是什么：b5 版本为了修时序，每个 match 多等 1 拍，压缩一帧 1080p 要 374,461 拍（76.91 MB/s，低于 77.76 门槛）。b6 去掉这个等待，回到 **355,261 拍 = 81.067 MB/s**，输出字节与原来完全一致。
- 独立测试者没有只读开发自述：它自己重跑仿真、自己解析 TD 报告，还用“旧版本 core”做负对照，确认 374,461 与 355,261 的差值正好等于 match 数 19,200。
- 工程：布线 0 违例、setup +0.119 ns、hold +0.020 ns；生成 1 次 bit 和 1 次 CWC，**没有下载、没有写 Flash**。
- 需要你知道的两个风险：① 时序余量很薄（+0.119 ns，hold 只有 0.020 ns），上板/温度变化时风险高于常规；② 综合 +0.280 略低于我们希望的 +0.3（这是事先允许的）。
- 计划上开发没有照“首选方案”写，而是用了等价做法；测试者独立验证了目标结构确实达成、门槛没被放宽，我作为规划**接受**这个等价实现。
- T10 仍未 done：需求二（真实 RAW/参数）和需求三（板级端到端）没完成；而且板级诊断发现**相机前端一帧都没进来（cap_frames=0）**，所以下一包是相机前端诊断，不是继续压时序。

# 用户短总结：T10.b6-a1-htab-nw（r0 计划冻结）

**结论：已按你的要求冻结修复包，当前状态 `ready`，等待派开发；还不是 PASS，也没有新 bit/CWC。** 本轮不下载。

## 做了什么

- 确认 r5 的吞吐回归：P2 comp **374,461 cycles / 76.91 MB/s**，比 r4 的 **355,261 / 81.07 MB/s** 多 **19,200 拍**，正好每个 match 多 1 拍；低于 77.76 门槛。
- 根因是 r5 为时序把 bm_b 候选地址寄存了一拍，导致命中后 S_EXT 多等 1 拍。
- 新开 **T10.b6-a1-htab-nw**（不把 b5 r0 追认为 PASS）：用“提前一拍的 htab p3v 影子读 + 必要时一级 bm_a 预取”保留 flop-only 地址，恢复 r4 命中拍首字节比较，去掉等待拍。
- 只改 `a1_deflate_core.v` 的 htab/bm_b 读地址结构；协议/帧/CRC/DDR/SDC/UART 状态包都不动。

## 验收线

- P2 comp **精确 355,261 cycles**（81.067 MB/s），压缩流逐字节 SHA `2601d57c…a7c05` 不变。
- P1 三例逐字节：63 B / 150 B / 40,076 B 对齐 r4 金标；随机 stored 与 8×3 边界复测。
- 综合/布线 **Routed 0 违例，WNS ≥ +0.05 ns**（记录 caveat），hold/period/资源通过。
- **1 次 bitgen + 1 次 CWC**；本轮 **0 下载**。

## 预算

- 开发 90 分钟 / 50 calls；TD 3 会话 / 150 分钟；综合 ≤3、布线 ≤2、bitgen 1、CWC 1、下载 0。
- 综合测试 45 分钟 / 30 calls，不重跑 TD、不下载。

## 边界

- 相机前端 `cap_frames=0`、真实曝光同步、板级吞吐：独立问题，本轮不混入。
- 板级下载/Flash/COM8 采集：本轮明确不做。
- 若 b6 仍达不到 355,261 或 WNS < +0.05，按 FAIL 保留证据，不放宽门槛；后续是否做更深结构/器件授权需要你另行决定。
