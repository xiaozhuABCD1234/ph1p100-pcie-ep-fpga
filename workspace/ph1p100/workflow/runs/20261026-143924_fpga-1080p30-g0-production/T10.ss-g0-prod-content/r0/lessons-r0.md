# lessons — T10.ss-g0-prod-content r0

只记可复用的根因 / 触发条件 / 修正入口 / 验证方式；不复述报告数字。

## L1 `tb_ss_4run.v` 的 12,000,000-cycle 看门狗会把"难内容"判成挂死（本包直接触发）

- 根因：`SS_STALL` 计的是 `cycles - last_exp_t > WD_LIMIT`，初始 `last_exp_t = 0`，`WD_LIMIT` 是 **`localparam 12,000,000`**（不是 `-g` 可覆盖参数），所以它实际约束的是**首帧冷启动上限**，而不是"帧间卡死"。
- 触发：内容越难，单帧压缩延迟越长。P4 合成基线首帧压缩 4.678M cycles（`L_cold` 6.45M）；本包自然内容 6.98M（L）/ 7.48M（N），加首帧导出 4.31M/3.36M → 12.90M/12.44M，**双双越过 12M**，于是 `$finish` 且 **stats 行来不及落盘**（`$fwrite(fs,...)` 只在结尾写一次）。
- 后果：不仅丢 4 帧证据，连 `cap/enc/exported/read/drop` 计数都拿不到，只剩 transcript + `+EVT`。评审时要能区分"内容不可信"和"TB 看门狗不够用"，别让它冒充 FAIL 或 PASS。
- 修正入口：任何要用自然/高熵内容做 4 帧稳态的包，先按 `首帧压缩延迟 + 首帧流长×2clk` 估 `t_exp(1)`；超过 WD_LIMIT 就必须用新 TB（P2/P3 允许，需 diff + 白名单）把 `WD_LIMIT` 提到 ≥20M，或把看门狗改成从 `t_sof(1)` 起算。
- 验证：先跑 1 帧 precheck，看 `enc(1)` 与 `+HDR` 里的 `stream_len`，再决定是否值得花 20 min 跑 4 帧。

## L2 导出头 `stream_len` 是"零成本"的每帧码流实测（别只看 stats）

- `+HDR`（`CAPTURE=0`）会抓导出流前 44 B，offset 24 是 `stream_len`、28 是 `raw_crc`、40 是 `header_crc`。即使 4 帧没跑完，也能拿到**首帧精确码流长度**与 **raw_crc**。
- 本包用它做了两件事：① 证明内容→DUT 字节映射正确（`raw_crc` = 本包 `zlib.crc32(raw bin)`）；② 反推首帧导出时长、判定看门狗是否必然触发。
- 复用建议：任何"内容类"包都应把 `header_check` 作为强制证据项；它不依赖 `CAPTURE=1`（后者会把 6M 字节 dump 到磁盘）。

## L3 `P4 r1` 的 `enc(1)-t_pub(1)` 是合法的 `S_ss` 估计器（误差 0.0002%）

- 观测：P4 r1 首帧压缩延迟 4,677,960 vs 实测 `S_ss` 4,677,970（差 10 cycles）；本 TB 的核是帧串行，导出与下一帧压缩重叠，所以稳态间隔 ≈ 单帧压缩延迟。
- 但**只能当估计器**（标 `estimate_not_steady`），不能当 4 帧证据；一旦内容让导出成为主约束（`tail_frac≥50%`），该估计器会低估 S_ss。
- 用法：做预算/可行性预判（省 20 min/次），或在 TB 看门狗限制下给"下界/量级"。

## L4 自然内容的压缩吞吐是 1.5–1.6× 于合成内容，sink 不是唯一约束

- 同样的 DDR 通路、同样 4.147 MB raw 槽：P4 合成内容读+压缩恒为 4.678M cycles（C1 与 C2 **完全相同** → 说明那时是 DDR 读速上限，不是核上限）；本包自然内容 6.98M–7.48M cycles → 核成了瓶颈（≈3.3–3.6 cycles/px）。
- 含义：只提高 sink（P3）不能救自然内容；压缩核的**内容相关吞吐**要单独列为 P2/P3 的风险项。
- 另一方面自然内容码流更小（1.68/2.16 MB vs rand 2.59 MB），**压缩流**的 sink 需求 50–86 MB/s 反而在 93.75 以内——不要把"raw band 2,594,706 B 需要 103.79 MB/s"直接套到压缩流上。

## L5 冻结 TB 副本 + 独立打包器交叉校验，能挡住"镜像自证"

- 本包的 hex→bin→mosaic 三联自检都是"我自己写的编码器解我自己写的数据"，属于镜像自证；真正有判别力的是**用本包的打包器重算 P4 冻结件 `raw40_p1d1.hex`（518,400 组）→ mismatch 0**，以及 **DUT 导出头 `raw_crc` = 本包 bin 的 crc32**。
- 复用：内容类包至少要有一条"跨实现"校验（冻结旧件重算 或 DUT 侧 CRC），否则 A4 的"逐值复算"会退化成自证。

## L6 进程回收：`taskkill /T /F` 不保证回收 ModelSim（本包留了残留 vsim/vish）

- 观测：precheck 在 300 s 超时后被 kill，但下一次 vsim 启动前仍检测到 `vsim/vish` 存活（约 45 min 后才自然退出）。
- 规则：超时后应显式按进程名复查（`Get-Process vsim,vish`）并 `Stop-Process`，再启动长跑；长跑墙钟记账要注明是否含竞争（周期数是确定的，墙钟不是）。

## L7 `+RAW40` 内容包不需要新的 RTL 或 TB 改动，但**必须本地重算 geometry**

- 518,400 行 × 10 hex 位 = 5,702,400 B；少一行或多一行 `$readmemh` 不报错（缺省为 0/X），`SS_RAW_MATCH` 只比 TB 内部一致、不比文件长度，所以"行数/字节数/CRC"要由本地脚本断言（本包 `verify` 已断言）。
