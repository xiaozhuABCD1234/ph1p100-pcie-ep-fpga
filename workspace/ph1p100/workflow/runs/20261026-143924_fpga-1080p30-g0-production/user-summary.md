# 用户摘要 — 1080p30 G0 本轮结论（run 已收尾）

**一句话：本轮 G0 判定为 `G0_not_closed`（未闭合）。** 在冻结的实验条件下，自然场景和低照夜景都达不到 30 fps 的 core 吞吐要求；瓶颈是压缩核，不是输出通道。P1–P4 全部 PASS，但 P4 PASS 只表示合并/判定/证据绑定正确，**不是 G0 通过**。

- **差多少**：自然场景每帧 7,475,240 cycles（比 G0 的 6,250,000 慢 **16.39%**，约 25.08 fps）；低照夜景 6,986,952（慢 **10.55%**，约 26.84 fps）。首帧冷启动 12.4M/12.9M 单独记录，不算失败也不算通过。
- **为什么不是 sink**：低照的“尾部占比”61.7% 看起来像输出卡住，但输出通道实际只有 **61.72%** 的时间在忙（自然场景 44.88%），低于 95% 的判定线；帧间隔由压缩核决定。因此两类都按“实测未闭合”处理，而不是“无法证明”。**这是一次口径澄清：P1/P3 报告原来的 `G0_not_proven` 在 run 级被修正为 `G0_not_closed`；所有数字和证据不变，原报告没有改写。**
- **有没有希望**：P2 找到 187.5 MHz 下算术上够快的组合 **A+H**（6,008,078 cycles，约 +4.03% 余量），但它只是**估算、未实现**，不确定范围 **45%**，只能算“有条件（conditional）”；单独改 H 仍差 0.17%。A+B+H（5,916,475）也算术闭合，但 B/C 的匹配器增益未验证、2% 信用是假设，所以 A+H 只是**最小/首选**组合，不是唯一，也**不是 G0 闭合**。
- **提时钟/双核行不行**：不行。现有 b11 布线只支持约 188 MHz（187.5 MHz 只剩 +0.015 ns），209.6/224.3 MHz 需要重做流水线并重新做时序；双核不会提高单路吞吐（单路仍是 7,476,245 cycles）。
- **输出通道**：93.75 MB/s 对实测压缩流够用（最紧的低照 25 ms 需求 86.25，占 92.0%）；但“原始字节直通”的 25 ms 需求是 103.79 MB/s，**没有实现也没有证明**，而且只对不可压的 RAW 回退路径有意义。现有生产的 115200 UART 只有约 11.52 kB/s，生产输出仍未做。
- **需要你决定**（三选一，降档不主推）：
  1. 投入 core 结构改版（A+H：双位置扫描 + 2 B/cycle 回放），先做原型，再 TD/时序，再板级和 4 帧复测；
  2. 换压缩核/换算法（另立任务、另算预算）；
  3. 接受当前 `G0_not_closed` 边界（仅限已声明的内容与 scope）。
  降档（G25 等）需要你明确授权，本轮不会拿 G25 当理由推降档。
- **不能说**：这些结论只覆盖“图像派生的自然/低照内容 + 仿真 slot-free + 93.75 代理 sink + 行为级 DDR + 单核 187.5 MHz + 单路”；不等于真实传感器 RAW、最坏/全内容、生产 sink/DDR、板级或双路已经通过。
- **下一步**：若要继续 1080p30，先做 A+H 的独立 RTL 原型（需 TD/时序/资源，本轮未授权），或用真实传感器 RAW 复核 N/L 内容；**不得直接说 G0 已闭**。准确启动文本见 `handoff.md` §5 / `final-summary.md` §8。
