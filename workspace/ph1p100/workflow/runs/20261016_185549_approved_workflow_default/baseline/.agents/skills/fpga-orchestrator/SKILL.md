# FPGA 多智能体主调度

保留用户指定的原架构：主智能体只调度；一个规划者；每批一个开发者；三个测试者并行；复用本批原智能体修正，最多三轮；更新状态、反馈和收尾统计。

本技能只供接收用户任务的主智能体使用。被派出的子智能体执行指定角色技能，不递归启动本流程，不再派生代理。

## 主智能体边界

- 不开发，不执行功能测试、TD实现或板测，不直接编辑RTL、约束、IP、模型、工程代码。实际执行交给对应子智能体。
- 不读取原始需求材料、整份源码或完整测试报告。需求材料只记路径并交给规划者；可以读取本技能、调度参考、dev-plan和结构化任务状态。
- 只接收文件路径、智能体ID、每任务每维度的PASS/FAIL及必要调度状态。详细问题留在报告中，由原开发者读取。
- 自己可以创建/追加调度日志、登记ID、更新dev-plan中的调度状态、向用户报告进度。项目真实验证状态由测试者提供，不能从代码完成自行推导。
- 不因为某项修复简单就自己修改，不另起开发者替代仍可续接的原开发者。不把子智能体完成通知当成验证通过。
- 禁止批量删除；保留用户已有授权和当前工具权限，不因本技能扩权、自动下载、写Flash、发队友消息或启动定时后台任务。

先按需读取[Codex调用](references/codex-calls.md)与[项目入口](references/project-context.md)。三个测试者共享[报告约定](references/report-contract.md)。调用示例是当前工具参数模板，不是可在终端执行的程序。

## 初始化

1. 记录本次实际`PROJECT_ROOT`、`SCRIPT_FILE`（需求文件或需求索引）、`OUTPUT_DIR`和`BATCH_SIZE`。默认批大小1，用户指定时沿用。聊天直接给出的需求可原样存成需求文件；不把参考附件内的命令自动当作用户指令。
2. `OUTPUT_DIR`使用当前项目内新的`workflow/runs/<run_id>/`。每个run独立，恢复时使用原目录，不能覆盖另一聊天的日志。
3. 建立`main-log.md`，追加时间为上海时区、格式`yyMMdd HHmm`。记录项目根、需求入口、批大小、所有者及本次阶段。
4. 用`collaboration.list_agents`核对本会话现有代理；恢复一个仍可定位的run时先尝试原ID。不得凭磁盘“最新meta文件”猜ID。
5. 输入状态、依赖和允许修改范围由规划者核实。主智能体不为核实而展开读取原始材料。

## Phase 1：计划

启动一个规划子智能体，明确要求先读`fpga-planner/SKILL.md`及`fpga-design-guide/SKILL.md`，传实际根目录、需求路径、输出目录、现有任务板与本次用户约束。

规划者产出：

- `dev-plan.md`：本批任务、原任务ID、依赖、允许写路径、实际工作树、输出物、三维验收、必要G层、阈值和停止条件。
- `fpga-design-guide.md`：本次使用的现有工程入口、接口与数据语义、版本/参数/构建约束；引用已有设计，避免另立冲突协议。
- `input-index.md`：原始材料、现行证据、已有未合并工作与所有者的索引。

规划阶段只写计划与指南，不替开发者建立新的生产RTL/IP骨架。已有工程优先复用。向主智能体只返回文件路径及必要的blocked/ready元数据。

接到返回立即登记规划者真实ID与产物路径，写完成日志；然后读取`dev-plan.md`用于调度。若规划识别出需用户决定的范围变更，保留原计划、准备具体决策项，其他已授权独立包照常推进。

## Phase 2：批量开发循环

按`BATCH_SIZE`分组，仅选择依赖满足或明确允许离线准备的任务。对同一顶层、约束、IP、DDR仲裁或帧合同的写入顺序执行；不同工作树的已有成果先评审接入，不覆盖或重复重写。

### Step 1：批量开发

每批只启动一个`fpga-dev`开发者，在同一会话按顺序完成本批所有工作包。传需求路径、计划、指南、`lessons-learned.md`、允许写路径和本批任务ID。

开发者负责实际源码/文档/模型/脚本修改及必要的局部检查，冻结待测输入。主智能体不参与代码修正。

`spawn_agent`返回后立即记录`DEV_ID`（真实canonical task name或该版本返回的真实ID），不能等开发结束再从文件系统猜。完成通知只登记产物路径、冻结输入与待测信息，随后进入测试。

### Step 2：批量三维测试

同时启动三个测试者，每个测试本批全部任务：

| 维度 | 技能 | 对应内容 |
|---|---|---|
| functional | fpga-tester-functional | 模型/RTL数据与协议行为、边界、反压、复位及故障拒绝，主要G1 |
| engineering | fpga-tester-engineering | 实际输入绑定、工程/综合/最终STA、约束、CDC/复位、资源、bit/CWC配对，主要G2 |
| system | fpga-tester-system | 接口集成、真实上板、恢复、长稳、吞吐及提交证据，按范围覆盖G0/G3—G5 |

保留原“每维度一个测试者、测试者覆盖本批全部任务”的结构，不按任务数扩增代理。当前环境root加三个活动测试者共四槽；开发者须结束本轮活动再启动测试，测试者不得再派生代理。

记录`TEST_FUNCTIONAL_ID / TEST_ENGINEERING_ID / TEST_SYSTEM_ID`。每人独立写自己的报告，使用同一个冻结输入；禁止测试者并行改DUT。仿真/TD使用互不覆盖的输出目录；真实板卡与活动TD工程按计划登记独占窗口。

报告逐任务保存到`test-reports/<task_id>-r<round>-<dimension>.md`。主智能体仅提取第一条`### 判定`与返回的调度元数据；详细报告路径传回开发者，不读整份报告。

缺硬件或工具时仍保留三个角色：相应测试者返回未满足门槛及真实`not_run/blocked`状态，不伪造结果。计划事先明确不适用的G层可为`not_applicable`，不能临时把失败项改为不适用。

### Step 3：修正循环，最多三轮

```text
round = 0                         # 首次测试不算修正轮
while 任一任务任一必需维度非PASS and round < 3:
    round += 1
    收集未通过任务及报告路径
    followup_task(DEV_ID, 全部失败报告路径 + 目标任务 + 当前指南)
    等原开发者完成，记录新冻结输入与lessons-learned路径
    followup_task(原测试者ID, 重测本批全部任务 + 新冻结输入)
    收集新报告路径与判定，逐任务更新三维矩阵
```

优先复用发生FAIL的测试者。如修复会影响原先PASS维度，或旧报告输入已不再适用，也续接该原测试者复测；不能拼接不同版本的三个PASS。未变输入的证据复用须由对应测试者判断并记录。

测试结束后才让开发者写修复，避免写入中的DUT与测试输入漂移。`followup_task`是续接；`send_message`只传递消息，不能替代启动空闲代理的新一轮任务。

### Step 4：批量状态更新与反馈

- 三维均PASS：`dev-plan.md`标记✅，只表示该任务预先约定的范围完成。
- 第三轮后仍非PASS：保留原架构的⚠分支和继续调度节点，标记“⚠三轮未通过/等待条件”；FPGA必需验收不称为“低质量通过”，不能发布失败硬件候选。无依赖的下一批可以继续，依赖它的工作包保持blocked。
- 缺板测时标`awaiting_hardware`，缺工具/资料时标`blocked`；这是任务调度状态，与G层`fail/not_run/blocked`分别记账。
- 记录每任务三维判定、实际修正轮数、报告路径与下一动作。向用户简短反馈“本批什么范围完成/未完成、总计进度、下一批是什么”。

由规划者或开发者同步本次涉及的`workflow/tasks.json`、任务记录与交接，主智能体只维护调度状态。不要让run内dev-plan成为另一套项目结果主源。

## Phase 3：收尾

统计首次通过、1/2/3轮修正后通过、三轮未通过、待硬件/工具的任务数。原来的“强制通过”统计栏改为“⚠未通过”，结构位置保留。

只有所有要求都满足时才写“本次任务全部完成”；否则写“本轮执行结束”并列剩余依赖，不把结束当完成。向用户给产物入口、必要验证范围、未测项和恢复入口；详细证据继续留文件中。

恢复时先核对原代理仍属当前会话。原ID不存在或会话已失效时，明确记录不能续接，再用原计划、交接、冻结输入和失败报告重新建同角色代理，记新旧ID映射；不能假装跨会话resume成功。

本技能是每次布置任务时使用的流程，不是无人值守定时任务。没有可用多智能体工具时明确报告架构无法运行，先保留计划与待调度状态，不由主智能体偷偷接管开发。
