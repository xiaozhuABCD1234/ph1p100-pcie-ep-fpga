# user-summary-04.md — 压缩方案：先澄清，再给搭配建议（大白话）

**一句话：我上次除了 LZ77，提到的“另一个”是 **DEFLATE/GZIP**；严格说它不是另一种匹配算法，而是“LZ77 + Huffman 编码 + 标准容器”。更优的搭配不是二选一，而是：Bayer 预处理 + LZ77/Huffman 标准流 + 块级 RAW 回退（stored 块，仍然合法），容器预留 Rice 第二模式。**

## 先澄清

- 我在 `next-task-and-progress.md`、`user-summary-03.md`、`question-03.md` 里写的是 **LZ77** 和 **DEFLATE/GZIP 兼容**。
- DEFLATE = LZ77 + Huffman + 标准容器；GZIP 是外层封装。所以“LZ77 vs DEFLATE”不是两种匹配算法之争，而是“私有格式 vs 标准流”之争。
- 另外，项目任务板里还有 **BPR1（Bayer 同色预测 + 有界 Rice）**，那是更早的历史路线（后来改成 LZ77 合规基线 + BPR1 转可选第二模式）。它不是我在上一条里说的“另一个”，但这次我把它作为组合项一起评估了。

## 三个组合（详细表见 `compression-options.md`）

- **组合 A（推荐起步）：Bayer 预处理 → LZ77 → DEFLATE/GZIP 标准流 → 块级 RAW 回退（stored 块）。**
  - 压缩比估算 1.1–1.5×；资源增量 LUT +10–18k、ERAM +8–16；单A 77.76 MB/s 可行；规则最稳（zlib 可独立解）；验证成本高但可用 zlib 对照。
- **组合 B（比率优先）：Bayer 同色预测 → 有界 Rice（BPR1）→ RAW 回退；LZ77 只做可选第二模式。**
  - 压缩比 1.5–2.2×；资源更省（LUT +5–10k）；吞吐最容易；但私有格式，规则接受不确定，且和你之前定的“LZ77 合规基线”冲突。
- **组合 C（上限最高）：统一块容器，逐块在 {LZ77/Huffman 标准子流、Rice、RAW} 里选。**
  - 压缩比 1.3–2.2×；资源最紧（LUT +15–25k、ERAM +12–24）；验证成本最高；私有 Rice 块会破坏纯标准流，需要“合规子集”口径。

## 我的建议

**先做 A，容器预留 Rice 第二模式位（“A+”）。** 理由：先用标准流把合规基线跑通（zlib 可解、规则风险最低），Bayer 预处理把比率拉起来；如果实测比率不满意，再在同一容器里加 Rice，而不是推翻重来。**不建议**现在一步到位做双引擎（C），也不建议把 B 单独当主方案（规则风险大）。
