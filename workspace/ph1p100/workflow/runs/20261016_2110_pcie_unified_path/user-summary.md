# 统一最终路径（PCIe）对接评估——结论与分工建议

> 本次只做评估：没有改您的代码/工程，没有运行队友仓库里的任何脚本，没有动 TD/任务板和其他 run。详细技术依据（含 commit/SHA、逐条核对）在 `workflow/runs/20261016_2110_pcie_unified_path/pcie-unified-path-assessment.md`。

## 一、核心结论

**统一到队友的"EP 主动 MWr 推帧"通路作为传输层，内容仍用我们自己的帧格式（R10F 帧头＋载荷，后续 BPR1）。**

理由：队友那条路（FPGA 每笔 128 字节 Memory Write 推整帧→门铃通知→RK 驱动轮询收帧）是两边**唯一已经上板跑起来**的形态；我们计划里的"C2H 固定块"本质上和它是同一类机制（FPGA 主动写主机内存），只是更严格的测试与成帧要求——这些要求可以直接在那条通路上核对，不需要再建第二条通路。我们的压缩/元数据/双路内容对它是"不透明字节"，队友不用懂 BPR1。

## 二、分工建议（谁改什么）

### 您来改（适配队友）- 主体在 FPGA 侧
1. **TD 升到 6.2.3**（您已决定），并核对队友的 PCIe EP 核/PLL 在您机器上重建或直接复用。
2. **把队友的 PCIe 后端接入我们的 csi2 工程**：EP 核/引脚约束、BAR0 寄存器窗、推帧引擎（`ddr_frame_pusher`）、引擎里的"用户发送口"改动；我们的相机/CSI/压缩前端保持不动。
3. **帧内容按我们自己的合同成帧**：R10F 128B 头＋RAW10 packed（1920×1080 一行 2400 字节、整帧 2,592,128 字节），CRC 沿用现有实现；之后再接 BPR1。
4. **推帧数据源适配**：我们的 DDR 是原生 PAXI（队友是 AXI），要么把推帧读源移植到 PAXI，要么按"双方约定"第 4 条换用队友的 DDR 配置——这一条要先定。
5. **主机侧**：用队友的 RK 驱动，我们负责 R10F 解析、后续 BPR1 解码、立体/深度链路和联调脚本。
6. **板测按分级判据**（固定块→640×480→1080p 单路→双路……见评估文档 §6）。

### 队友来改（适应我们）
1. **说清"跑通"到底到哪一步**：链路？寄存器读写？推帧发了 2400 笔？**主机有没有真的收到并验过整帧**？他 README 里还写着"收帧等 FPGA 接通后再验"，与最新提交有出入，需要他给一份实测说明。
2. **推帧参数化**：1080p 帧比现在的 640×480 大 8 倍多——帧长、尾块、以及一个我们已核实的问题：**他的推帧 TLP 计数器只有 12 位，1080p 一帧要 20,251 笔，装不下**，需要加宽；DDR 缓冲也要相应放大。
3. **驱动适配**：1080p/2.59MB 帧的几何参数、槽头长度字段语义（压缩帧变长时）、双路时按"只增不改"扩 ioctl。
4. **给 RK 联调信息**：内核版本、IOMMU、CMA、MPS、实际 BDF，以及他能否配合板端联调。
5. 共享的逻辑改动（推帧/驱动参数化）明确由谁在哪个仓库改、怎么回流，避免双方各改一份。

### 双方一起约定（不冻不定不动手）
1. **传输合同**：地址/门铃寄存器、门铃=完成、数据与门铃的先后顺序、错误码。
2. **帧内容合同**：一帧传给传输层的字节数、R10F 头为准还是含填充、槽头长度字段。
3. **填充规则（建议）**：1080p 帧补齐到 4KB 整数倍（2,592,768 字节，尾部零填充，头里的长度字段为准），这样双方的突发/分包逻辑都最省事。
4. **DDR 配置定案**：队友用 800Mbps＋AXI，我们用 1600（1333 候选）＋PAXI。带宽两边都够，主要差别在既有验证资产和 IP 生成入口——需要一次决定。
5. **双路语义**：两台相机是给两个目标/两个邮箱，还是单门铃串行推、靠帧头里的 camera_id 区分。
6. **对齐修正**：评估发现他现在的推帧目标地址是"槽基址+16 字节"，这会让每 4KB 边界都有一笔 128 字节的写跨界（PCIe 规范不允许）；建议把目标改成 128 字节对齐（驱动小改，FPGA 不用改）。
7. 联调判据（固定块逐字节一致→单路→双路→压缩）与证据记账方式。
