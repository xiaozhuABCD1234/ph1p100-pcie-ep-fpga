# 从人工流程到自动化的接入路线

这是一条可分阶段落地的接入设计。本轮已经提供流程、任务数据、模板和示例；以下 runner/CI/插件开发尚未实施，不把“有配置文件”当作“已经自动执行”。

## 三种方式及选择

| 方式 | 适用 | 代价 |
|---|---|---|
| 仓库内记录 + 可替换适配层（推荐） | 现在即可使用，后续接自有工具和 AI | 初期人工记录；逐步补自动采集 |
| 直接依赖 GitHub Projects/Actions | 团队已经全在 GitHub | 需远端配置、构建节点与权限；硬件观察仍需独立回传 |
| 自建多代理/调度平台 | 已有稳定接口、较多项目和机器 | 维护/故障/权限成本高，目前易挤占竞赛研发时间 |

选择第一种：任务和证据先稳定，适配层仅负责输入冻结、执行、采集与结果归一。GitHub/自有平台均可作为视图或执行端，不让某一工具成为唯一可恢复入口。

## A. 现在：手工用起来

- 从 T01/T02 选当前主任务，T03 准备双方接口确认。
- 复制对应模板到 `workflow/records/<task-id>/`，把既有证据用链接引用。
- 结束时更新 tasks.json 与 handoff；真实结果变化后更新根 README/基线摘要。
- 用 `.github/ISSUE_TEMPLATE/` 和 PR 模板整理任务/缺陷；仅在将文件推送到 GitHub 后才影响远端模板。
- IC Coder 按 [有限额度使用方案](ICCoder有限额度使用方案.md)作为可选专项审阅者；先人工交接一个只读任务，不因其存在另建常驻付费 Agent。

验收：换一个人或新会话，只看任务、证据和 handoff 能知道输入版本、当前边界与下一步，无需重读全部聊天。

## B. 首个自动化：只采集与校验，不控制硬件

拟新增 `tools/workflow/` 下轻量本地入口，消费 tasks.json 和固定命令清单，输出 [run-record 示例](examples/run-record.json)对应的记录。

第一版能力限于：检查任务 ID/依赖、记录源码/工具版本、验证输入哈希、执行已审查的相关仿真、保留原始日志、区分正常通过与预期拒绝、生成新索引。默认只展示执行计划，显式选择后才运行；没有连接的动作返回 blocked，不伪造 pass。

实现前需落实：本机 Python/ModelSim/TD 真实路径、允许写入的构建区、每条命令的真实结果标记，以及现有脚本是否会产生外部目录。首次适配只覆盖一个已知测试入口，不包装全部历史脚本。

验收重点：旧输入哈希不一致、缺工具、D 盘无当前授权、退出 0 但无 PASS、负对照未拒绝、截断日志都不能误报成功；任务/输入路径不能逃出允许范围；绝不加入批量清理。

## C. 本地/CI 构建节点

先接软件/仿真轻检查，再接有许可证的 TD 本地节点。TD 阶段按现有隔离候选方式运行，最终数据库、报告、约束审查和位流明确绑定。节点输出是“候选”，不能自动提升为板测通过。

原始产物保留在实际允许位置，Git 中记录清单、哈希与小型证据索引。大型日志/数据库/位流可用团队产物存储；备份恢复另做演练。不要通过 git clean 或清目录维持 runner。

验收：同一 manifest 能定位精确输入和产物，报告变化可解释，失败保留；不承诺位流逐比特重现，需区分输入可追溯与确定性构建。

## D. RK 与团队接口

先落实 T03/T05 责任、环境和样例。自有 RK 工具通过输入文件/帧协议消费数据，输出解码一致性、运行版本及带单位/时间窗的指标。Linux DMA API、缓冲所有权、缓存可见性、超时/reset 行为先设计再实测。

验收：同一测试帧 FPGA/RK 长度与 CRC 一致，模式/裁剪/Bayer/端序有定义，错误流拒绝，失联恢复有记录。标定/推理离线基线成立后再连接实时流。

## E. 硬件在环与发布

下载器/观测工具先确认设备标识、候选哈希、允许操作与板卡独占锁；观测回传保留真实来源。人工断电、跳线、相机连接等写进板测记录。只有必需验证层有实际证据，才可形成发布 manifest。

验收：无法观测的内容保持 not_run；超时/掉线/错误计数不得自动忽略；发布材料可从稳定版本恢复。外部发布、消息、持久自动化依据用户实际授权执行。

## 工具接入时交给助手的信息

提供工具用途、CLI/API/MCP 入口、脱敏输入输出样例、版本、运行机器、允许路径、是否修改硬件/外部状态及测试数据。密钥不写入任务或仓库；使用本机受控配置。主助手先准备具体适配设计和验证范围，再执行已授权的接入工作。

## 参考来源

- [OpenTitan 阶段跟踪](https://opentitan.org/book/doc/project_governance/development_stages.html)：借鉴设计、验证分开描述。
- [Hog](https://github.com/Hog-CERN/Hog)：借鉴构建与位流追溯；没有直接迁移其工具链。
- [cocotb runner](https://docs.cocotb.org/en/stable/runner.html)：作为新独立模型测试的可选接入。
- [FuseSoC](https://github.com/olofk/fusesoc)：可借鉴文件集、target、工具后端解耦；现有 TD 工程不为此强制迁移，未验证 TD 后端适配。
- [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)：短分支、审阅和小范围合入。

这些是思想来源，本工作流按当前小团队和赛期裁剪，不声称达到上游项目的全部质量标准。
