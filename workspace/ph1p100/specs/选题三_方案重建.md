## 4. Evidence rules

每个技术结论必须标注：

1. 当前器件/当前板卡的原文事实：路径、版本、章节/PDF 页码或行号。
2. 跨平台参考：说明源器件、差异、可复用范围。
3. 候选方案/推测：列出成立条件与验证方法。
4. 当前器件编译/PnR 结果：关联源码、约束与报告版本。
5. 当前硬件实测：关联 bit、接线、配置和原始输出。

旧 Markdown、对话摘要和 Codex 结论是线索，不是独立的一手证据。
IP 文件夹存在、参数存在、许可证 included 均不能单独证明 PH1P100SBG484 兼容。
综合或 PnR 通过不能单独证明 D-PHY 电气合规、稳定接收或同步达标。

## 5. Edge cases / 风险

- 器件家族相同但型号/封装资源不同；PH1A、DR1 资料不得代替 PH1P100 的支持结论。
- zip 内原始文件、解压文件和本地修改稿不一致；现成 bit 和当前 RTL/约束不一定对应。
- 加密文件只证明存在接口/交付物，不证明支持当前器件或可直接移植。
- 同一相机信号的 HS/LP 分支、电阻网络和 FPGA 引脚不能只按名称解释。
- 1:10 解串不等于直接得到 RAW10 像素；仍需字节/通道对齐、CSI-2 解包与 RAW10 解包。
- RAW10、RGB、YUV、灰度数据的吞吐和处理要求不同；按真实格式预算。
- 不能靠加宽/调时钟掩盖丢帧、FIFO 溢出、反压、CDC 或 CRC 问题。
- RK 环境等待时，继续独立资料核验、仿真、参考模型和 FPGA 工程准备。
- 高分辨率升级必须保留可复现的已验证版本。

## 6. Definition of done

### 本轮方案重建完成

- 用户七轮回答均进入需求基线，旧计划明确标为历史参考。
- 赛题条款逐项引用原文；未核实项不写成硬要求。
- MIPI/IP、引脚、电气、时钟与同步形成结论/证据/待验证项对应表。
- 资料索引记录器件、板卡、路径、完整性、加密状态和参考价值。
- 队友交付项、时间节点与实验门槛明确。
- 用户批准下一版方案后再展开功能实现。

### 作品验收框架（数值门槛待原文核实）

- 两路独立采集正确帧，统计实际帧率、行长、错误与丢帧。
- 同步有明确控制方法、测量对象、共同测量时基和连续帧统计。
- 三类预处理要求若由原文确认，须逐项功能验证并有像素对照。
- 压缩输出能由参考解码器还原；按规定定义测压缩率与吞吐。
- RK 经 PCIe 收到带帧号、长度、相机 ID 与校验信息的数据并重建。
- 队友提供实际 RK/NPU 推理证据，全链路延迟按统一方法测量。
- bit、源代码、约束、参数、日志、报告与视频可相互对应。

## 8. Verification commands / 手工检查

资料复核使用专用 Read/Glob/Grep 工具、PDF/XLSX 解析，并保留准确定位。
需要实验时沿用 TD 的真实工程运行报告，不编造未知 TCL 命令。

队友 PCIe 初验（OrangePi Linux）：
```bash
lspci -nn
sudo lspci -vv -s <实际设备BDF>
```
保留完整输出；不要把模板 BDF 当真实设备地址。
当前 Gen2 x2 是规划目标，必须从 LnkSta 读取实际协商结果。
