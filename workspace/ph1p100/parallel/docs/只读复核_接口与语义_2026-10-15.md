## C3（最重要）：F2 的 BPR1 码流封装 ↔ 我的 128B 传输帧头

来源：`codex/bayer-codec-reference` 分支的 `docs/superpowers/specs/2026-10-15-bayer-codec-reference-design.md`（只读，未改动）。

### 事实

| 项 | F2（BPR1） | 我的帧合同（并行轨道） |
|---|---|---|
| 定位 | 明说："Frame envelope is a **test/interchange format, not a frozen PCIe session/DMA header**" | 传输/会话层（PCIe C2H） |
| 帧头 | `<4sBBBB7I` = **36B**，magic `BPR1` | **128B**，magic `R10F` |
| 行/块头 | `<BBHIII` = 16B/行 | 无（不由我定义） |
| CRC32 | IEEE 反射、init/final xor `ffffffff`、`check("123456789")=cbf43926` | **完全相同** |
| 相位 | phase u8（默认 0） | `bayer_phase` 0..3（RGGB/BGGR/GRBG/GBRG） |
| 载荷 | 逐行 RAW/Rice 二选一，无静默截断 | RAW10 packed / u16le |

### 结论：**互补，不冲突**

F2 自己声明了它不是传输头。因此合理组合是：

```text
[我的 128B 传输头 (R10F)] + [F2 的 BPR1 封包(36B 头 + 行块)] + [32B 对齐填充]
                                                     ↑ codec_id 标记
```

- 我的 `codec_id` 应取值表示"载荷是 BPR1 封包"（具体枚举值由 F2 定义，我这边已留字段，非压缩时=0）。
- 我的 `payload_bytes` = BPR1 封包总长（**含**我加的 32B 对齐填充）。

### 必须统一的字段语义冲突（否则联调必错）

两个层次**都有** `version / flags / raw_bytes / payload_bytes / raw_crc32`，但含义不同：

| 字段 | 外层（我的，128B） | 内层（BPR1，36B） | 风险 |
|---|---|---|---|
| `payload_bytes` | 含 32B 对齐填充 | **不含**填充（精确长度） | RK 按外层长度喂给内层解码器 → 多读尾部 0 → 可能被判"trailing bytes"而拒帧 |
| `raw_bytes` | `stride*height`（多行） | `width*height*5/4`（单帧原始） | 单相机基本一致，但语义不同层 |
| `flags` | u32（BAD/CROPPED/PARTIAL/OVERSIZE） | u8（BPR1 内部） | 不要互相套用 |
| `raw_crc32` | 覆盖 `payload[0:raw_bytes]` | 覆盖"所有原始 packed 行" | 若都启用，需明确用哪一个做最终判据 |

**建议**（任选其一，但必须写死）：
1. RK 侧解析顺序 = 外层 128B → 校验 `header_crc32` → 若 `codec_id==BPR1` → 把 `payload[0:payload_bytes]`（可含填充）交给 BPR1 解码器，并**按内层 `payload_bytes` 截断**后再解析；或
2. 外层去掉填充（`payload_bytes` 与内层一致），把我的 32B 对齐只用于 DMA 缓冲，不进入长度字段。

另外：F2 的 `raw_bytes=width*height*5/4` 依赖 `width%4==0`，与我的 `stride` 约束一致，**这一点两边是兼容的**。

## C2：`ddr_frame_store` 的所有权与丢帧语义

来源：`fpga/csi2/src/mem/ddr_frame_store.v`（只读）。

### 观察

1. 新帧 `VERIFY` 成功后，会释放其它 `READY` 槽（保留正在 `READING` 的槽）——这是"尽量显示最新完整帧"的**预览**策略。
2. 被替换掉的 `READY` 帧**不产生任何序号缺口记录**，只有聚合 `drop_count`。
3. `!ddr_ready` 时把 3 个槽全部置 `FREE`，且只在 `write_state!=IDLE` 时 `drop_count+1` —— 即"每次 ready 丢失记一次"，不是"每帧记一次"。

### 与帧合同的冲突点

我的帧合同要求"**有界丢帧 + 可追踪的 `capture_seq` 缺口**"（左右配对依赖它）。当前实现无法回答"丢了哪些帧号"。

**建议**：传输队列版不要复用该策略，单独实现五态所有权（写 / 已验证 / 编码中 / 发送中 / 完成可释放），并对每次释放记录 `reason` 与 `capture_seq` 缺口。DDR 接口、CRC、槽管理的**代码**可复用，但**契约**必须重写。这与导师复核 §4.1 的判断一致。

## C1：预览/白平衡链的舍入与采样

来源：`fpga/csi2/src/cam/bayer565_capture.v`（只读）。

1. **舍入约定一致**：WB 用 `rounded=product+512; step=rounded[22:10]`，即"幅值四舍五入（half-up）后再恢复符号"，与三算法金参考的 `(sum + n//2)//n` 属**同一约定**，两侧无冲突。
2. **采样率是真正的风险**：该模块每 4×4 只取首个 2×2（丢 3/4 像素）。若三算法分支复用它，深度输入的有效分辨率会被砍。**建议三算法走独立的全分辨率路径**，不复用预览采样器。
3. 未验证项：`line_phase` 在"帧上升沿与行上升沿同拍"时的取值（`line_phase<=line_rise?0:3`）属于边界情形，建议在 RTL 回归里补一个针对性用例，而不是靠现有 14 场景默认覆盖。
