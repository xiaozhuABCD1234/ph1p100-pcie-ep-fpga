# 相机 → DDR → HDMI：实现与验证记录

> 2026-10-12更新：用户反馈003550版本绿色亮点消失、灯态符合预期，记录为首次功能板测反馈，无独立下载日志/时长/持续计数。下文未下载状态属于生成时快照。两只相机均连接供电已确认，用户已确认断电并断开B路；主从核清前仅做A路。接收层审查返工与此已测版本分开，见仓库当前摘要。

本轮把已测的A路灰度采集/DDR写入接到显示端。原225520候选显示读ERAM；新工程显示数据必须经过DDR、显示异步FIFO和像素消费者。当前硬件反馈仍只属于225520，新版状态见[证据索引](evidence/camera_ddr_display_20261012.json)及[上板操作](相机DDR显示闭环_操作与预期_2026-10-12.md)。

## 1. 保持的配置

相机为IMX415 4K30、RAW10、4lane×891Mbps、27MHz MCLK；沿既有预览写口取960×540×8bit灰度。HDMI固定1920×1080p60，每个源像素复制成2×2。没有恢复彩色、增加采集帧率或存储全4K RAW；RAW12封存，30Hz测试停止。

## 2. 为什么需要这次改动

旧候选能证明至少一帧真实灰度数据写入DDR后CRC/元数据读回通过，但屏幕仍走ERAM。因此仅看旧画面不能验收DDR显示。

本轮在保持相机、PLL、配置读回及HDMI发送方式的基础上，新增DDR读消费者、显示FIFO和像素消费者。读端只在新显示请求时选完整帧；没有新READY槽时重复原READING槽。写端不能覆盖READING槽，活动画面期间到来的新帧留待下一请求，避免撕裂。

| 文件 | 可检索入口 | 责任 |

| [ddr_display_read.v](../fpga/csi2/src/mem/ddr_display_read.v) | `fresh_request`、`DRAIN`、`FOOT_WAIT`、`CRC` | 停止旧流、排空已接受读响应、选槽、检查footer、按行重复读、累计整帧CRC |

显示VS在像素域翻转请求位，经两级同步到DDR域；ACK返回像素域。只保留一个未确认请求。FIFO START携带epoch与帧ID，旧请求残流被消费丢弃。START到首个DE以后才返回时，本帧保持黑色，下个VS重来，不从屏幕中间开始显示。

显示FIFO为258bit×256项。960字节源行读两遍，使DDR输出流已经包含垂直复制；像素端对每字节做水平复制。估算显示载荷518400×2×60=62.208MB/s，加上采集写入与协议开销另计；未测得真实带宽。此选择减少首版行缓存控制，后续以欠载计数决定是否改为行缓存或突发。

RGB、HS、VS、DE在同一像素时钟边沿注册。缺数据后本帧剩余输出黑色，欠载每帧计一次，下个VS重新预取。无首帧时黑屏不记启动欠载。CRC只累计每源行第一次读取的全部字节；运行中显示可能早于CRC完成，因此本轮没有“CRC验证后才显示”的保证。

## 4. 本轮找到并修复的问题

后端收到错误RLAST时会消费响应、取消READING所有权，且不产生`rd_valid`。初版读消费者仍等待该响应，下一VS也可能卡在DRAIN。新增footer和DATA两种错误RLAST注入后，回归实际失败；随后用`frame_valid`取消确认清除`pending_read`并回IDLE，下一完整帧可恢复。故障日志与修复后日志分别归档，不把仿真进程返回0当测试通过。

最终复核确认原像素图案每256字节重复，会掩盖字地址bit4清零（偏移512字节）：实际故障负对照仍PASS。已将高位偏移量加入图案，新负对照在x=1024/y=0检出像素错误，正向生产/故障恢复重新通过。只增强TB和运行器，生产RTL及bit未改。

TD可将同步FF本地复位AND放到独立LUT。本轮核验器只接受已检查数值真值表和输入选择的两种单AND映射，不任意遍历逻辑锥。输入存在性检查仍需配合实际FF数据选择、时钟、复位源及物理skew复核。

## 5. 验证覆盖及边界

| 验证 | 实际覆盖 | 限制 |
|---|---|---|
| 零功能stub负对照 | 视频控制不对齐时确实产生FAIL | 不代表所有错误均能检出 |
| 64×16集成回归 | 65536个DE周期，包括正常帧与故障黑色；重复、活动期写新帧、切换、欠载及下一帧恢复 | 小尺寸用例；不能当长时间硬件运行 |
| 故障注入 | footer长度损坏、首字节翻转CRC、footer/DATA错误RLAST、未决读复位、ready丢失、START活动期迟到 | ready丢失模型依赖DDR控制器同时冲刷响应的契约 |
| 960×540生产尺寸 | 2073600输出像素逐个核对2×2关系、整帧CRC；32402读、16201写，无欠载 | 仿真使用紧凑消隐，未完整模拟2200×1125真实VTC或厂商DDR电气 |
| 既有模块回归 | pack 73检查、tap 217检查、store 77检查通过 | store的5个错误为预期注入，不是无故障运行 |
| TD原生实现 | 独立工程、最终STA/skew、网表、输入哈希和厂商依赖 | 不能替代板外HDMI/DDR电气及长期运行 |

小尺寸日志最终计数会在中途复位后清零；CRC损坏已在复位前断言，不能只看末行`rejected=0`推断未测损坏。PAXI模型包含周期性ready反压和4–10个模型延迟周期，不冒充厂商DDR仿真或实测延迟。

## 6. 工程及复现

从仓库根运行`tools/td/run_ddr_display.py`，加`--production`运行生产尺寸，加`--red`运行stub，加`--production --address-fault`运行地址别名负对照。每次结果在`D:/TD/work/csi2/_validation/ddr_display/`创建新目录，并冻结编译输入及SHA256，日志必须有指定PASS/FAIL标记。

运行`tools/td/prepare_camera_ddr_display.py`创建独立`camera_ddr_display_<时间戳>`；原相机/已测DDR候选不覆盖。生成器先核对固定相机和厂商依赖，再派生core/wrapper/top/约束。TD使用`TimingHigh`物理策略，不代表采用硬D-PHY。

从新目录执行`td_commands_prompt.exe ./build.tcl`，随后复制并执行inspect脚本、核验两只FIFO/输入清单，最后才运行bitgen脚本。完整命令见[工具说明](../tools/td/README.md)。最终候选、bit大小/哈希、STA/资源、仿真原路径及归档均由[证据索引](evidence/camera_ddr_display_20261012.json)唯一标识。
