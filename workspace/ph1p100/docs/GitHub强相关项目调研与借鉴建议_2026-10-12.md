# GitHub 强相关项目调研与借鉴建议

调研日期：2026-10-12。面向本项目 PH1P100 + 双 IMX415 + PCIe + RK3588 的实际链路。

2026-10-13归档说明：本文件沿用10-12调研结果，随用户工作流配套资料归档，本轮没有重新访问上游验证其最新状态。下文155843等项目状态为当时快照；当前状态以根README及RGB332专项记录为准，不据此恢复旧下载安排。

## 结论与调研范围

最值得立即学习的是 **Project F 的 TMDS 独立参考模型**和 **CSI 接收工程的分层验证方法**；下一阶段重点参考 **GZIP 压缩核、灰度/高斯/均衡化例程和 PCIe DMA**。RK 端可以直接从 OpenCV 官方双目样例及 Rockchip 官方 RKNN 样例开始。

本次检索并阅读了仓库说明、目录和部分关键源码。下面区分“上游公开实现/作者报告”与“针对我们工程的建议”。没有把这些工程移植到 PH1P100，也没有运行其全部测试或上板验证；上游性能数字不能作为本项目验收结果。链接使用当日访问的分支，正式采用时应固定 commit、保留来源及许可。

项目基线来自当前 README：A 路 IMX415 4K30 RAW10 接收，960×540 Gray8 经 DDR 输出 1080p60；持续上电后高亮边缘彩点尚未解决。155843 的 CSI CRC16/FE 后发布候选尚未上板，B 路保持断开。完整目标为双路 1080p30，压缩、图像 DMA、双目同步和 RK 整链路仍待验证。不能把显示 60 Hz 当成相机 60 fps。

## 1. Project F：最适合补充当前显示链验证

代码入口：[Python TMDS 模型](https://github.com/projf/display_controller/blob/main/model/tmds.py)、[TMDS 编码 RTL](https://github.com/projf/display_controller/blob/main/rtl/tmds_encoder_dvi.v)。README 提供 1080p60 等时序、测试图和仿真入口，许可为 MIT。

值得学的核心是：编码结果受历史 DC balance 状态影响，只检查几个像素不足以证明正确。其 Python 模型能为我们的 RTL 提供独立对照。

建议形成两个小闭环：

1. 用独立模型核对当前编码器，覆盖 0～255、重复值、高反差交替序列、消隐控制和消隐后的状态；另行检查串行输出位序和边界。
2. 保持现有 1080p60 输出，以固定色块、灰阶、黑白边缘图绕过相机与 DDR，持续上电复现。再逐层加入 DDR 测试图、真实相机，记录首次出错时间和计数。

README 对 Xilinx 7 系列 1080p60 SerDes 额定范围有专门说明。这提醒我们区分“短时出图”和“电气/时序/长期稳定通过”，但该说明不能推导出 PH1P100 的器件极限，也不能证明我们彩点的根因。上游 Xilinx serializer、PLL 和引脚约束不能直接复制。

## 2. circuitvalley：重点学对齐、解包和测试源

该工程采用 CrossLink-NX + FX3，公开 RAW10/12/14、多 lane、多像素输出实现。重点入口是 [Source/src](https://github.com/circuitvalley/USB_C_Industrial_Camera_FPGA_USB3/tree/master/FPGA_Firmware/Source/src)：

- `mipi_csi_rx_byte_aligner.v`、`mipi_csi_rx_lane_aligner.v`：字节同步与 lane 对齐。
- `mipi_csi_rx_packet_decoder_8b4lane.v`、`mipi_csi_rx_raw_depacker_8b4lane.v`：包头、长度与 RAW 解包。
- `output_reformatter.v`、`sample_generator.v`：输出重排、行缓存及测试数据源。

检查到的包解析模块根据 DT/WC 抽取有效负载，没有在该模块实现 CRC16/ECC 计算。因此适合作为结构和解包对照，不能替代我们的 CSI 完整性门禁；这一结论仅针对所读模块，不能外推为整个仓库都没有校验。

建议借其分层方式建立人工 CSI 输入：错字节对齐、lane 偏移、不同 WC、残缺负载、帧中断及 RAW10 尾部组合；每层比较输出内容、数量和错误状态。物理接收仍需保持适配本板 HRIO 的实现。

读到的输出重排使用双行 RAM 和独立输出时钟，依赖及时排空。借鉴时须重新证明 CDC、行覆盖和反压条件，不能当作完整帧缓存。README 标注 CC BY 4.0，而所读源码头标注 CC BY 3.0；实际复用前逐文件核对并保留署名。

## 3. gatecat/CSI2Rx：重点学端到端分层

先看 [vhdl_rx](https://github.com/gatecat/CSI2Rx/tree/master/vhdl_rx)。上游说明明确：已验证的是 VHDL 接收链，Verilog 版本仍是 work in progress。其测试平台为 Kintex-7 + OV13850，原始配置为四 lane、10 bpp，许可 MIT。

可以学习的模块关系是 PHY → 字节/字对齐 → 包处理 → RAW10 解包 → 行缓存 → DDR 帧缓存 → 显示。尤其适合对照我们每一层应输出什么计数、帧边界和错误信息。

建议让同一显示后端分别接固定测试源与真实采集，避免相机输入速率、接收器处理能力、DDR 读写能力、显示刷新率混在一起评价。其 AXI4 framebuffer 只能学习事务和缓存组织；我们当前 DDR 是原生 PH1P PAXI，256 位命令、地址步进 8、mask=0 全写，不能按标准 AXI master 直接接入。

## 4. FPGA-Gzip-compressor：值得认真评估的新候选

代码入口：[gzip_compressor_top.v](https://github.com/WangXuan95/FPGA-Gzip-compressor/blob/main/RTL/gzip_compressor_top.v)、[lz77_encoder.v](https://github.com/WangXuan95/FPGA-Gzip-compressor/blob/main/RTL/lz77_encoder.v)、[SIM](https://github.com/WangXuan95/FPGA-Gzip-compressor/tree/main/SIM)。上游采用 LZ77 + Huffman，输出标准 GZIP，附带 CRC32，许可 GPL-3.0。

顶层可学习“输入缓存 → 分块 → LZ77 → 符号化 → Huffman → 输出缓存”的组织，以及用通用软件解压检查硬件输出的验证方法。它比自定义压缩格式更方便接 RK 软件解码，但不是我们原先 LZSS-like 格式的直接兼容实现。

必须提前处理的边界：输入为每拍 1 字节，输出为带 `tkeep/tready` 的 32 位流；小于 32 字节的输入包会被内部丢弃。我们的封装应使短尾块走明确 RAW 旁路，携带原始长度、压缩长度、帧号、块号和编码类型。32 位输出接 256 位缓存时，要保留尾部字节有效信息，并测试下游反压。

作者报告 Artix-7 上 128 MHz、无输出反压时约 128 MB/s，约 8200 LUT、25 BRAM36K。这些不能当作安路综合结果；双路 RAW10 的需求已超过这一参考吞吐，详见后表。

建议先拿真实 RAW10、Gray8、低纹理、高纹理、噪声和随机数据做压缩率/最坏膨胀测试，再在 PH1P100 上测时序、RAM 与持续吞吐。采用 GZIP 会改变块格式和 RK 解码接口，应作为候选比较；其含 LZ77 并不自动证明满足赛题的具体表述。

## 5. image-processing：三种预处理的直接学习入口

入口：[Gaussian_filter/gaussian_filter.v](https://github.com/ykqiu/image-processing/blob/main/image_processing/Gaussian_filter/gaussian_filter.v)、[Histogram](https://github.com/ykqiu/image-processing/tree/main/image_processing/Histogram)、[整个算法目录](https://github.com/ykqiu/image-processing/tree/main/image_processing)。

高斯源码使用经典 3×3 权重 `[1,2,1; 2,4,2; 1,2,1]`，有窗口和视频同步流水线；README 的均衡化采用上一帧统计。很适合学习 RAM、窗口、查表与有效信号如何共同延迟。

与我们要求的差异需要显式适配：上游高斯为单像素流并用右移截断，我们计划四像素/拍且 `(sum+8)>>4` 四舍五入，结果可能相差 1 LSB。验收要按我们自己的参考定义，而非默认逐位一致。上游视频同步接口也不能直接等价于带反压的 ready/valid 流。

四像素直方图存在同拍多像素落在同一 bin 的冲突；上一帧 LUT 只能在有效整帧提交后切换，坏帧不能污染下一帧统计。本次未完成上游全部直方图冲突逻辑审计，应将这些作为我们自己的设计/验证要求。

建议分别比较灰度值、高斯边界/舍入、CDF-min 均衡化及首帧策略。双目匹配保留原始/旁路灰度，避免左右独立均衡化造成亮度关系变化。未确认该仓库明确许可证，优先学习方法，直接引入代码前确认授权。

## 6. verilog-pcie / LitePCIe：补齐图像搬运而非只点亮链路

重点代码：[dma_if_pcie_wr.v](https://github.com/alexforencich/verilog-pcie/blob/master/rtl/dma_if_pcie_wr.v)。所读源码包含描述符地址/长度/tag、写请求 TLP、MPS 与 4 KiB 边界分包及状态回报；仓库另有 cocotb 相关测试，所读文件为 MIT 许可。

它最值得学习的是将“帧在 DDR 中”和“主机确实收到完整帧”之间的工作拆开：描述符、PCIe 地址、包长度、数据有效字节、流控、错误状态、通知和缓冲所有权。上游分段 RAM/TLP 接口并非我们的 PAXI，未见可直接使用的 PH1P wrapper。

建议先做单缓冲 FPGA→RK 写入：固定模式、不同长度、跨 4 KiB 和尾部不足整字，RK 检查长度、序号、CRC；再接 DDR 帧与环形队列。FPGA DMA 状态完成后，仍应依协议确认主机可见性和缓冲释放条件，避免提前复用。

主机软件可配套阅读 [LitePCIe 软件目录](https://github.com/enjoy-digital/litepcie/tree/master/litepcie/software)，学习 SG DMA、MSI、mmap 和队列组织。LitePCIe 为 LiteX/Migen 体系，README 标注 BSD-2-Clause；其驱动要求对应硬件寄存器协议，不能当作通用 PH1P 驱动。当前已有 PCIe link 成功反馈，仍不能证明图像 DMA 可用或吞吐达标。

## 7. OpenCV：RK 双目的最短学习路径

直接读官方 [stereo_calib.cpp](https://github.com/opencv/opencv/blob/4.x/samples/cpp/stereo_calib.cpp) 和 [stereo_match.cpp](https://github.com/opencv/opencv/blob/4.x/samples/cpp/stereo_match.cpp)。它们覆盖标定图像对、角点、双目标定、校正参数及 BM/SGBM 匹配入口。

建议 RK 同学先用离线真实左右图像跑通 640×360 或 960×540 闭环，保存标定参数、校正图、极线误差、有效视差及已知距离误差，再接 PCIe 连续输入并测帧率/延迟。标定板尺寸单位决定后续距离单位；分辨率、裁剪、镜头或安装变化后必须重新核对参数。

静态场景能帮助分离标定与同步问题，移动物体仍需实际曝光同步证据。图像帧号配对不能代替曝光同步；他人的 R/T 参数和基线距离也不能用于我们的相机。保持匹配/深度在 RK 的既定分工，先取得数据证据再考虑 FPGA 化。

## 8. rknn_model_zoo：RK3588 NPU 的官方例程

入口：[YOLOv8 示例](https://github.com/airockchip/rknn_model_zoo/tree/main/examples/yolov8)、[rknpu2/yolov8.cc](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolov8/cpp/rknpu2/yolov8.cc)。仓库明确支持 RK3588；所读代码展示 tensor 属性查询、RGB/letterbox、输入设置、推理、输出取得和后处理。

建议照此建立单张图片检测，再换成 PCIe 送来的解码图像，分开记录解压、RAW 转 RGB/ISP、缩放、NPU 和后处理耗时。模型转换与部署应固定 Toolkit2、runtime 及驱动版本，并记录量化输入数据和预处理定义。

该 YOLO 例程不是 RAW10 直接推理接口，也不能证明 PCIe RAW 帧能自动进入 RK 硬件 ISP。需要团队明确交付 RAW 解包、Bayer 顺序、去马赛克/颜色处理、图像布局及缓存接口。

## 9. 安路近平台教学参考

[yexiao336/fpga_demo](https://github.com/yexiao336/fpga_demo) 有 MIPI/HDMI、视频流、ISP 和 DDR 的源码讲解，可帮助理解安路工程的接口连接与四像素视频路径。

但它使用 PH1P35、SC500CS、两 lane RAW10 和 DDR2，与我们的 PH1P100SBG484I、IMX415、四 lane及现有存储后端不同。其硬 D-PHY 用法不能证明我们这一具体器件具备同样可用的硬 D-PHY；传感器寄存器、PLL、引脚约束和复位写法均需回到本板资料核对。该仓库更适合教学对照，不能作为官方硬件能力证据；许可未确认。

## 吞吐与存储：借鉴前先算清楚

以下是我们按 `1920×1080×30×相机数量×位深/8` 独立复算的有效像素负载，MB 为十进制。RAW10/12 按紧凑打包计算，未计帧头、块头、PCIe 开销、填充和额外 DDR 读写；25% 为预算余量示例，不是已测吞吐。

| 输入格式 | 单路 1080p30 | 双路 1080p30 | 双路再留 25% 余量 |
|---|---:|---:|---:|
| Gray8 | 62.208 MB/s | 124.416 MB/s | 155.520 MB/s |
| RAW10 packed | 77.760 MB/s | 155.520 MB/s | 194.400 MB/s |
| RAW12 packed | 93.312 MB/s | 186.624 MB/s | 233.280 MB/s |

工程判断：单个 128 MB/s GZIP 核即便达到作者参考性能，也低于双路 RAW10 的裸输入量；对双路 Gray8 仅比裸输入量高约 2.9%，不满足上表余量。可以评估两路独立核心、更高实测频率或不同压缩实现，最终以本板资源/时序/反压测试决定。压缩率高不能补救压缩器输入端吃不下原始流的问题。

本地 `fpga/csi2/src/mem/ddr_frame_store.v` 当前 `FRAME_WORDS=16200`、`rd_offset/write_offset` 为 16 位，适合现有灰度预览配置。单路完整 1080p RAW10 为 2,592,000 字节，即 81,000 个 256 位字，字索引至少 17 位。扩展到完整 RAW 帧时，要一起检查计数器、地址拼接、槽位跨度、容量和尾部处理；这不是对当前预览配置的故障结论。
