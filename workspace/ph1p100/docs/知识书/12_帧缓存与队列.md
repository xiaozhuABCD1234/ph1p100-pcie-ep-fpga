## 10 分钟速读卡

- **本质一句话**：帧缓存不是"一块 FIFO 变大了"，而是一套**格子系统＋所有权规则**——一帧占一个"格"（帧槽），每个格在任意时刻只属于一个环节（正在写 / 待消费 / 正在被读 / 正在被编码 / 正在发送），别人无权覆盖它。
- **为什么重要**：显示闪烁、撕裂、丢帧、下游收到半帧，几乎都能回溯到"所有权规则没定好"；而对正式链路，"丢整帧 + 记录序号缺口"是唯一诚实的降级方式。
- **本项目怎么用**：三槽 `ddr_frame_store.v` 已在真实 DDR 上做了探针级验证（写入→围栏读回→READY→读取）；正式队列的合同（写入→验证→编码持有→发送持有→确认释放）已在策略与整合中冻结方向，实现与板测待后续任务。
- **一个记忆锚**：帧缓存像**快递分拣站的三格转盘**——每格有主人（所有权），格子交接只能在边界完成（帧边界换格），塞不下时**整票退回并记单号**（丢整帧＋序号缺口），绝不"把别人的货往下压"。

## 直觉：三格转盘与"格子有主"

【通用原理】视频/图像系统里"帧缓冲"（framebuffer）的基本矛盾是：**生产者一直写、消费者按自己的节奏读**。如果只有一块存储，写一半被读走，就会出现"上半帧旧、下半帧新"的**撕裂（tearing）**。解决办法的雏形是双缓冲/多缓冲（double/triple buffering）：写的那块和读的那块分开，在**帧边界**交换角色。

类比成"三格转盘"：

- 每一格（帧槽）在任意时刻**只属于一个环节**；
- 交接（换格）只允许发生在**帧边界**（不能读到一半换）；
- 三格的好处：一格拉去读（显示/发送）、一格正在写、还有一格"兜底"（上一帧完好的 READY 或缓冲区）。

帧槽的"主子"就是**所有权（ownership）**：谁在写、谁在读、谁在等，容器本身要知道，不然必然出现"把正在读的帧覆盖掉"这类事故。

## 原理：从 FIFO 到帧槽所有权

### 为什么 FIFO/ERAM 不够：先看容量量级

【本项目事实】把三个数字放在一起，量级差距一目了然：

| 存储 | 容量量级 | 说明 |
|---|---|---|
| PH1P100 片内 ERAM | 合计 6000Kbit≈**750KB**（还要分给各模块） | `../../当前必读/01_FPGA主线学习手册_由浅入深.md` §13（D1 路径） |
| 旧预览帧缓存 | 占用 **224/300 块** ERAM | `../RAW10灰度显示与DDR推进记录_2026-10-10.md` §1 |
| 一帧 960×540 8bit 灰度 | 518400B≈**506KB** | 同上 §4 |
| 一帧 1920×1080 RAW10 | 2,592,000B≈**2.5MB**（81,001 个 256bit 字） | `../完整RAW10后端_偏移扩展与保留进度_2026-10-14.md` |

结论：**帧级缓存必须离开片内**；片内只留行缓存、FIFO 与元数据。FIFO 解决"短时间缓冲、跨时钟域交接"，帧槽解决"整帧排队与所有权"——两者角色不同，不能互相替代。

### 帧槽生命周期：从 FREE 到再次 FREE

【本项目事实】现行显示/预览后端 `ddr_frame_store.v` 的状态机（`../../fpga/csi2/src/mem/ddr_frame_store.v`）：

```text
槽状态：FREE → WRITING → READY → READING →（读完释放）→ FREE
发布条件：帧长度正确 + 末字围栏读回比较通过（否则整帧不发布）
替换规则：新完整帧只替换 READY 槽，绝不覆盖正在读取（READING）的槽
异常路径：短帧/LAST 异常/取消/就绪丢失 → 不发布残帧，drop_count/error_count 计数
```

【通用原理＋本项目合同】正式传输队列的完整生命周期更长（策略 F6 与整合 M09 的方向）：

```text
入口写入 → 完整验证 → 编码持有 → 发送持有 → 确认释放
（正式队列至少区分：写入 / 已验证 / 编码中 / 发送中 / 完成可释放）
```

多出来的三段（编码持有、发送持有、确认释放）防的是：**编码器/发送端还没用完，槽就被新帧顶掉**。预览链路没有这两个环节，所以它的替换策略不能直接搬到正式链路——这正是 M09 的核心修正。

### 丢帧语义：为什么"整帧丢 + 记缺口"

【本项目事实】策略文档对正式队列的冻结方向（`../superpowers/plans/2026-10-15-fpga-remaining-strategy.md` §5 F6）：

- "编码/发送持有的槽不能被覆盖；**满队列丢整帧并记录原因/采集序号缺口**，左右配对可识别缺帧"；
- "对相机入口提供可计算的最大等待上界，测 FIFO 高水位；**持续吞吐不足不能用加深 FIFO 长期掩盖**"；
- "ready 丢失/复位后的未完成响应按控制器合同清理，不让旧响应进入新会话"。

为什么不是"丢最新、保住旧的"或"覆盖最旧"？因为对下游（匹配/深度/NPU）来说，**它必须能知道"哪一帧缺了、为什么缺"**——左右路配对时钟一旦对不上，"缺帧"会伪装成"位移"，直接污染几何。序号缺口（capture_seq）就是这份"缺货清单"。

### 预览的"替换 READY"为什么不能上正式线

【本项目事实】显示缓存的做法是"新完整帧释放旧 READY、只保留最新"；整合的独立审阅指出它"**不保留完整采集序号缺口**"，不能照搬到正式传输（`../DeepSeek独立检测与现行方案整合_2026-10-16.md` M09/§3.4）。正式链路必须"记录原因/序号/会话、禁止覆盖在用槽"——因为正式数据的目标是**可配对、可验收**，而不是"屏幕上看起来一直在动"。

**两条算账提醒**：

1. "平均够"必须换成"最坏"：RAW 回退（压缩不生效时 S≈R）会把 2R+2S 推到 622–778MB/s 量级；预览/显示读取还要另加。
2. FIFO 深度不是"根治"手段：FIFO 只能吸收**有界**停顿；持续吞吐不足要靠减少访问次数、提高效率或分流，而不是把 FIFO 越挖越深（策略 F6 明文）。

## 硬件实现视角：`ddr_frame_store.v` 的"三槽账本"

【本项目事实】把 10-11 后端的真实实现拆开看（`../../fpga/csi2/src/mem/ddr_frame_store.v`）：

- **域与接口**：单 DDR 用户时钟域；原生 PAXI 直接握手（`paxi_aw*/w*/ar*/r*`）；256bit 数据、mask 0（整字写）。
- **地址**：槽基址=槽号×`FRAME_WORDS`×8（PAXI 地址单位，步长 8）；默认 `FRAME_WORDS=16200`（=960×540×1B/32B），偏移位宽按帧长自适应（本尺寸 17bit）。
- **写与发布**：写满一帧后不直接发布——先把**末字**读回比较（围栏 fence，8×32bit 分段比较以打断长路径），比较通过才置 READY、`published_count+1`；短帧/LAST 不符/取消 → `error_count`/`drop_count+1`，槽回 FREE。
- **读**：带背压的读返回（`rd_valid/rd_take`）；读返回缓冲让"消费者停顿"时数据保持。
- **替换**："Newest complete frame replaces only READY, never READING"——新完整帧只覆盖 READY；正在被读取的 READING 槽绝不动。
- **就绪丢失（ready loss）**：清空槽、重置写状态；只有在"有活动写入"时加一次 `drop_count`——**它不是逐帧丢弃账本**（整合 §3.4 的精确修正）。
- **仲裁**：读/写之间用 `write_turn` 轮转，避免一方长期饥饿。

这套"三槽账本"证明了两件事：① 帧槽所有权可以用很小的状态机落地；② **它面向的是"预览/显示"语义**——正式队列还需要"编码/发送持有 + 序号缺口记录"（M09）。

## 决策点与判决框架

**决策点：正式帧队列的"持有与丢帧"语义怎么定？**

| 选项 | 内容 | 代价/收益 |
|---|---|---|
| A. 沿用预览"替换 READY" | 最新完整帧顶掉旧 READY | 简单；但丢失序号缺口记录、不区分编码/发送持有——**正式链路不可用** |
| B. 正式持有队列（当前冻结方向） | 写入→验证→编码持有→发送持有→确认释放；满队列丢整帧+记缺口 | 可配对、可验收、可恢复；代价=状态机与计数/元数据成本 |
| C. 加深 FIFO/缓冲来"兜底" | 靠更大缓冲吸收拥塞 | 对持续吞吐不足无效（只能吸收有界停顿）；掩盖问题、增加面积 |

- **权衡维度**：数据可配对性（缺帧可识别）；所有权安全（不覆盖在用槽）；恢复行为可预期；成本与验证面。
- **当前选择**：B。理由：正式链路的目标是验收与配对，M09/策略 F6 已把它冻结为合同方向；A/C 作为正式方案均被否证。
- **何时应重开**：① 联调发现持有状态机与队友引擎/驱动语义冲突（重对齐）；② 压缩格式引入槽头 len 语义变化（长度/缺口口径更新）；③ 实测吞吐/资源不足且分层优化（预取/仲裁）有量化收益；④ ready-loss 清理合同在真实控制器上被证明需要代际适配器（补排空逻辑）。

## 常见误区

- **"FIFO 加深一点就没事了"**：FIFO 只能吸收**有界**停顿；持续吞吐不足时它只会把问题推迟暴露。**正确做法**：先量化最坏吞吐（2R+2S/RAW 回退），再决定结构优化（分流/预取/仲裁）。
- **"写进 DDR 就算保存好了"**：未通过"完整结束+围栏读回"的帧不发布；发布之后进入 READY 也不是最终状态（正式队列还要编码/发送持有）。**正确做法**：按所有权状态机记账，任何环节都可以拒绝"半成品"。
- **"新帧替换旧 READY 是通用最佳实践"**：那是预览/显示语义；正式链路必须留下序号缺口并保护在用槽。**正确做法**：把"显示缓存策略"与"传输队列策略"分开设计（F6 的原文要求）。
- **"drop_count 就是丢帧账本"**：就绪丢失时它只在有活动写入时加一，**不等于每次事件逐帧计数**，也不是完整丢帧语义；模块已有 `frame_id/slot_id` 但缺正式持有状态。**正确做法**：读计数前先读定义（整合 §3.4）。
- **"左右配对各丢各的，没关系"**：缺帧若不可见，会被下游误判成位移/错位。**正确做法**：从队列层就记录"原因/序号/会话"，让配对端能识别缺帧（策略 F6）。

## 自测题

<details><summary>1. 为什么片内 ERAM/FIFO 不能替代帧缓存？</summary>

容量量级不够：PH1P100 ERAM 合计约 750KB（还要分给各模块），单帧 960×540 灰度就约 506KB，完整 RAW10 帧约 2.5MB。FIFO 只适合短时缓冲/跨域，无法承担"整帧排队+所有权"。
</details>

<details><summary>2. `ddr_frame_store.v` 的槽状态与替换规则是什么？</summary>

FREE→WRITING→READY→READING（读完释放）；发布条件=帧长正确+末字围栏读回比较通过；新完整帧**只替换 READY 槽，绝不覆盖 READING**；短帧/LAST 异常/取消/就绪丢失都不发布残帧。
</details>

<details><summary>3. 正式队列比预览队列多哪几段生命周期？</summary>

多了"编码持有、发送持有、确认释放"三段（写入→完整验证→编码持有→发送持有→确认释放），并额外要求"满队列丢整帧+记录原因/序号/会话、禁止覆盖在用槽"。
</details>

<details><summary>4. 2R+2S 是怎么来的？RAW 回退最坏是多少？</summary>

"原帧/压缩帧双暂存"时，每路都有写原帧、读原帧（编码）、写编码帧、读编码帧（发送）四股流量（R=读、S=写），双路合计约 4×155.52=622.08MB/s；RAW 回退时 S≈R、上界不变，+25% 约 777.60MB/s（不含预览与访问低效）。
</details>

<details><summary>5. 满队列时为什么"丢整帧"而不是"覆盖最旧"？</summary>

正式链路必须保留"哪帧缺了、为什么缺"的序号缺口（capture_seq），让左右配对可识别缺帧；覆盖最旧会静默改变配对关系、把缺帧伪装成位移，破坏下游几何。丢整帧+记录原因/序号是唯一可验收的降级方式。
</details>

<details><summary>6. 就绪丢失（ready loss）时后端做了什么、还欠什么？</summary>

当前：清空槽并重置写状态，有活动写入时 `drop_count+1`；欠：不区分代际/事务的迟到旧响应（模块注释要求"控制器同时复位或清空旧读返回"，否则需排空/代际适配器）；也不是逐帧丢弃账本。
</details>
