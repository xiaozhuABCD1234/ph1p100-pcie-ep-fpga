# 第 02 章 时钟复位与余量

> 本章回答两个问题：**电路按什么节奏工作**（时钟/复位/跨域），以及**"够不够快"这个结论是怎么算出来的**（setup/hold、WNS/TNS、余量口径）。
> 事实标记：【本项目事实】可追溯到项目文件路径；【通用原理】来自公认外部资料；【设计候选】【待验证】【未决】表示尚未实现/未板验/未拍板。第 01 章已建立"七站"与 G0–G5 的概念，本章不再重复。

## 10 分钟速读卡

- **本质一句话**：时钟是同步电路的"节拍器"——所有寄存器在节拍下同时取样；而"够不够快"不是感觉，是一条可计算的账：`周期 = 数据延迟 + 开销 + 余量`，余量可以是负数。
- **为什么重要**：读时序报告是 FPGA 开发最高频的判决现场。"零违例""余量 0.000ns""探索线 0.300ns"这三个数字的含义完全不同，混用就会做出错误判断。
- **本项目怎么用**：DDR 用户域从 200MHz（周期 5ns）换到约 166.7MHz（周期约 6ns）时，多出来的约 1ns 就是"周期预算"；历轮时序优化（0.000/0.001/0.008/−0.177ns）都在这本账上（`../../docs/RGB565时序裕量优化_2026-10-15.md`）。
- **一个记忆锚**：时钟=节拍；PLL=把节拍调快调慢的乐器；复位=让全乐队从同一小节开始；余量=预算减支出的余额，余额不足就得省钱（改结构）或换更慢的曲子（降频）。

## 本章要回答的问题

1. 时钟在电路里究竟"做什么"？分频、倍频、相位分别是什么意思，PLL（锁相环）为什么是 FPGA 的标准资源？
2. 复位为什么要"异步置位、同步释放"？多个时钟域各有自己的复位时会发生什么？
3. setup（建立）和 hold（保持）在检查什么？余量（slack）是怎么算出来的？
4. WNS/TNS、周期检查（period）、组数/覆盖率各代表什么？为什么"零违例"不等于"余量充足"？
5. 为什么"余量 0.000ns"是薄、"0.300ns 探索线"不是器件保证？这两个数字在本项目里怎么用？
6. 拿到一份时序报告，怎样在几分钟内判断它值不值得信任？

## 直觉：全场只有一个节拍

乐队演奏时，每位乐手看的是指挥的手；只要所有人都在同一拍上出声，合奏就成立。同步电路里，这个"指挥"就是**时钟（clock）**：它是一根周期性的方波，每来一个上升沿，所有接到这个时钟的**寄存器（FF）**同时做两件事——把输入取进来（取样），把上一拍的结果送出去。

这里有个关键直觉：**时钟不"执行"任何逻辑**。两个寄存器之间的组合逻辑（加法、比较、查表）永远在自由地算，时钟只决定"哪一瞬间算的结果被正式收下"。于是"快慢"问题就变成了：**在下一个沿到来之前，上游算出的结果能不能稳定送到下游的取景框里。**

【通用原理】这个模型叫同步设计（synchronous design）：用统一节拍把"计算的传播时间"与"何时收下结果"解耦。它可靠性好、工具支持充分，是 FPGA 的默认范式；异步电路（不用全局时钟、用握手约定节奏）存在但工程上少用（见 `延伸资源` 第 5 条）。

### 分频、倍频与相位

节拍从哪里来？FPGA 内部有一个或多个**PLL（锁相环，Phase-Locked Loop）**：输入一个参考时钟（本项目的 `sys_clk50m` 就是板卡给的 50MHz），PLL 通过"倍频/分频/调相"生成项目需要的所有频率。

- **倍频/分频**：输出频率 = 参考频率 ×（倍频系数 ÷ 分频系数）。【本项目事实】1333 候选的 PLL 配方是 `PLL0_REFCLK_DIV=3 / FBK=80 / CLK2=2`，物理 CK = 50×80÷3÷2 ≈ 666.67MHz（`../../workflow/runs/20261017_153201_T01_ddr1333_integration/dev-plan.md` §1.4）。
- **相位（phase）**：两个同频时钟可以错开若干度，用来把取样沿挪到数据稳定的窗口中央。DDR 接口大量使用相位关系（`ddr` 相关细节见第 09–11 章）。
- **锁定（lock）**：PLL 输出稳定之前会拉低 lock 信号，这段时间输出频率不受控。所以"等 PLL 锁定"是复位流程的第一步。

## 原理：复位——让所有人从同一小节开始

上电瞬间，每个寄存器的初值是未知的（芯片制造决定的随机值）。**复位**的作用是把整个电路强制推到一个已知、一致的状态（计数器清零、状态机回待命、FIFO 指针归位）。

朴素做法是"一个全局复位线接到所有寄存器"。但真实系统里：

- **不同时钟域**（时钟域＝由同一个时钟驱动的所有寄存器集合）必须各自复位、各自释放，否则"这个域已开始跑、那个域还没醒"，跨域交接就会出现无意义的握手。
- **复位的释放时刻**如果正好贴着时钟沿，寄存器可能进入**亚稳态（metastability）**——输出既不是 0 也不是 1，而是中间值悬停一小段时间。亚稳态不是"错值"，但会让下游在它悬停期间读到什么全靠运气。

【通用原理】工业上的标准解法是**异步置位（assert）、同步释放（de-assert）**：复位拉低时直接生效（不依赖时钟，保证马上进复位态）；释放时先经过两级寄存器与本地时钟对齐，再交给电路。本项目大量使用这个模式：【本项目事实】`fpga/csi2/src/mem/capture_async_fifo.v` 的复位处理是"公共异步置位 + 各自时钟域内两拍同步释放"，其中同步链寄存器标了 `(* async_reg="true" *)`；DDR 帧缓存的 wrapper 也是"`run_rst_n = rst_n && ddr_ready` + 两级同步释放"（`../../docs/RGB565时序裕量优化_2026-10-15.md`）。

注意一个容易忽略的后果：**复位也是一条信号路径**。复位网络如果扇出很大、又参与数据路径的使能逻辑，它自己就可能成为时序瓶颈——本项目的真实案例见下文"数字"一节。

### 时钟域与跨域交接的直觉

两个域之间的信号怎么安全传？规则取决于信号的性质【通用原理】：

| 信号类型 | 推荐做法 | 直觉 |
|---|---|---|
| 单 bit 慢速控制（如 flag、lock） | 两级同步器 | 每个沿只能赌一次"这次读到的是稳定值"，两级把风险降到工程可接受 |
| 多 bit 数值/计数 | 格雷码 + 两级同步，或异步 FIFO，或握手 | 多 bit 不可能同时稳定，必须保证"要么读到旧值、要么读到新值"，不能读到半新半旧 |
| 连续数据流 | 异步 FIFO（双时钟 RAM + 格雷码指针） | 数据本身不需要"同步"，只有读写指针需要 |
| 低频控制事务 | 请求/应答（req/ack）握手 | 每次交接等对方回话，慢但简单 |

【本项目事实】项目对相机入口用的就是异步 FIFO：`fpga/csi2/src/mem/capture_async_fifo.v` 用格雷码读写指针 + 两级同步 + `(* dont_touch="true" *)` 的格雷码寄存器（防止工具优化掉这个"保平安"的结构），并带读预取一拍，保证反压时数据保持。跨域信号"说不清边界"是大多数玄学 bug 的来源，交接协议的细节见第 03 章。

## 数字：一条时序路径的收支账

现在进入正题。"够不够快"在静态时序分析（STA）里是一个确定性计算：

```text
余量（slack） = 周期 − 数据路径延迟 − 各类开销
> 0 ：来得及；< 0 ：违例（来不及）
```

- **周期**：时钟的倒数，`T(ns) = 1000 ÷ f(MHz)`。100MHz → 10ns；200MHz → 5ns。【本项目事实】DDR 1600K 的用户域是 200MHz，周期 5ns（`../../docs/RGB565时序裕量优化_2026-10-15.md`）。
- **数据路径延迟**：源寄存器 -> 组合逻辑（LUT 串、进位链）-> 网络的 Cell 延迟 + Net 延迟之和。
- **开销**：时钟偏斜（skew）、时钟不确定性/抖动（jitter）、建立时间要求（setup time）、输出延迟余量等。它们不吃数据路径的预算，但同样占周期。

在时钟沿之前要满足的是**建立（setup）**检查：数据必须"早到"，并在沿之前保持稳定至少 setup time。沿之后还要满足**保持（hold）**检查：数据不能"变得太早"，否则同一个沿会把新值抢走。setup 违例说明电路太慢（靠周期和结构解决），hold 违例说明路径太短（靠工具插延迟或改结构解决）——方向完全相反，不能混着看【通用原理】。

### 真实数字：本项目四轮时序探索的账

【本项目事实】下表数字来自 `../../docs/RGB565时序裕量优化_2026-10-15.md` 与 T01 集成 run 的 dev-plan §1.7（工作目录=D 盘候选工程，工具 TD；66/68 组统计口径见下文）：

| 候选 | 时钟周期 | 数据路径 | 其余开销合计 | 最终 setup 余量 |
|---|---:|---:|---:|---:|
| 002820 基线（6.2.2） | 5.000 | 4.559 | 0.441 | **0.000** |
| 103222（本域 ready，6.2.2） | 5.000 | 4.747 | ≈0.252 | 0.001 |
| 111134（TimingUltra，6.2.2） | 5.000 | （见报告） | — | 0.008 |
| 114913（实现期预留，6.2.2） | 5.000 | 4.887 | ≈0.290 | **−0.177**（nominal） |

读这张表要抓三点：

1. **0.000ns 为什么"薄"**：它不是"刚好通过"，而是"账面余额恰好为零"——数据路径 4.559ns 里 **77% 是布线 Net（3.465ns）**，只有 1.094ns 是逻辑 Cell，且是最差三级 LUT、扇出 32。任何轻微的布线重新分配、器件差异或环境变化都可能把它推成负数。报告展开式：`5.000 − 4.559 − 0.267(skew) − 0.064 − 0.110 = 0.000`。
2. **−0.177ns 是怎么来的**：114913 这一轮专门做了"实现期预留"实验——在布线阶段对三个时钟临时加 0.300ns 的 setup uncertainty（相当于把验收线人为收紧 0.300ns 去布线），布线完成后**恢复为 0** 再出 nominal 报告。于是同一份实现出现两个数：guard 报告 −0.477ns、nominal 报告 −0.177ns，差值恰为 +0.300ns——说明预留**确实生效且被正确恢复**。但 nominal 是负的：**这个候选没有通过**，因此没有生成位流（`deliverable=false`）。
3. **0.001/0.008ns 为什么也不算达标**：它们是正值，但远低于 0.300ns 的探索目标，同样归档为 `deliverable=false`。正余量 ≠ 满足约定目标（对照第 01 章同一结论）。

### WNS/TNS、组数与覆盖率

时序报告里天天见的名词，一次说清【通用原理】：

- **WNS**（Worst Negative Slack，最差负余量）：所有路径中最差的那条余量（若全为正，取最接近 0 的正值）。
- **TNS**（Total Negative Slack，负余量总和）：把所有负余量加起来。TNS 大幅为负说明"不止一条路径违例"而非单点问题。【本项目事实】白平衡 233658 那轮的最终 STA 是 `setup −1.849ns / TNS −24.474ns`——单看 WNS 只差 1.8ns，但 TNS 显示这是成片的问题（`../../workflow/README.md` 顶部摘要）。
- **周期检查（Period Check）**：单独核对时钟周期约束本身是否满足；`period 2.200ns` 表示相关时钟的周期检查有 2.2ns 余量。
- **组数**：报告把路径按时钟对分组统计（Max/Min 各一组），最后给出统计组数。【本项目事实】002820 是 66 组、探索候选是 68 组；T01 集成 run 明确要求"报告形状人工复核后显式设定组数，禁止按文件现有组数自证完整"（`../../workflow/runs/20261017_153201_T01_ddr1333_integration/dev-plan.md` §1.11）。
- **覆盖率**：报告里被约束、被分析的路径比例。【本项目事实】HDMI 并行输入路径 STA 无违例但覆盖率 96.40%（route 97.75% 差异未解）——这意味着**还有一部分路径没被这份报告扫描**，"无违例"只对已覆盖的 96% 成立（`../../workflow/runs/20261017_161109_decisions_compare_freeze/decision-register.md` M3）。
- **别只看前十条**：报告通常只打印最差 10 条路径。111134 那轮之后开发者特意注明"不能据报告只列十个 endpoint 就推算所有路径的最小余量"。要判断全局，必须看 TNS、组数、覆盖率，而不是冠军路径。

## 硬件实现视角：报告是证据，不是判决书

1. **确认真实执行**：综合/布线是否真的跑完（退出码、完成标记、非空产物三件套，第 01 章）；STA 是否绑定同一最终实现数据库。
2. **确认口径**：nominal（不加预留）还是带 guard？工具版本是什么？【本项目事实】历史 1600 数据产自 6.2.2，新 1333 候选由 6.2.3 生成——跨版本比较会混入工具因素，所以 T01 用"002820 原样复制 + 6.2.3 重建"的 1600ctl 控制候选来隔离变量（`../../workflow/runs/20261017_153201_T01_ddr1333_integration/dev-plan.md` §1.8）。
3. **读结构**：最差路径的 Cell/Net 比例、逻辑级数、扇出、跨区情况。数据路径若被布线占主导（如 77%），说明问题在物理布局，加流水线可能有用、加约束或换策略可能没用。
4. **定位归属**：最差路径在**自己的逻辑**里还是在**厂商 IP 内部**？【本项目事实】103222/111134 之后最差路径转为厂商 DDR IP 的状态机译码（如 fast-init → byte3 的 `dly_pdata[*]` 类内部寄存器），"最紧路径位于厂商 DDR 内部"正是策略文档写明的停止扩张信号之一（策略 §8 停止条件 4）。
5. **决定动作**：降频/换档、改结构、还是接受现状但如实记录。**不允许**通过放宽约束、删检查或改口径来制造"通过"（`../../workflow/README.md` §5.1）。

### 为什么"零违例"只是起点

读报告最容易犯的错，是把"违例数=0"直接当成结论。两类反例【本项目事实】：

- **零违例但余量薄/不够**：002820 原始 final 报告 66 组统计的违例端点均为 0（"零违例"成立），但 setup 只有 0.000ns（"薄"）且未达到 0.300ns 的优化目标（`../../docs/RGB565时序裕量优化_2026-10-15.md`）——**"零违例"与"够不够余量"是两个问题**。
- **同一实现、两种账面**：114913 的 guard 与 nominal 两份报告对同一物理实现给出不同的违例计数——guard（实现期预留 0.300ns）为 116 个违例端点计数、nominal（恢复名义口径）为 13 个（`docs/evidence/camera_rgb565_timing_20261015_114913.json`）；两者都不是"零违例"。**这些计数是报告条目数**（同一物理端点可能出现在多个报告组），读它看的是量级与口径，而不是"唯一端点个数"。

另一条结论同样来自这两份报告：**判别阈值要先写清**（"我接受什么口径的什么数"），再看数字——而不是反过来拿一个正数说服自己。

## 本项目实例：0.000ns 这条路径的故事

【本项目事实】002820 的最差路径是"DDR 初始化状态 → `u_reader/passed_frames[30].CE`"，展开为 `5.000−4.559−0.267−0.064−0.110=0.000ns`。它的问题不在数据多绕了几圈，而在**结构**：厂商 IP 的 `init` 状态译码是一个组合信号（`fpga/csi2/prj/ddr_frame_probe/vendor/ip/ddrmc_x32/src/rtl/init/ph1p_ddrphy_dram_init.v:232` 附近），wrapper 已经做了两级同步释放，却又把这个**组合 ready** 直接接进了 reader/store 的使能（CE）锥——等于让一个厂商内部的组合信号去驱动一大片用户逻辑的时钟使能。

103222 的修法是结构性的：内部 DDR 用户域使能改用已同步的 `usr_reset[1]`（异步清零、两拍释放），ready 只用于共同复位的异步置位。效果立竿见影：**reader 的 ready 使能不再出现在最差十条路径里**；但整体余量只到 0.001ns——因为下一个瓶颈已经换成了厂商 IP 内部路径。这正是"最差路径会搬家"的教科书案例：修一个瓶颈不等于毕业，必须重新定位全局最差。

后面的 111134（换 TimingUltra 策略，+0.007ns）与 114913（实现期预留 0.300ns，nominal 直接变负）都没能突破。三轮之后的结论不是"200MHz 不可能"，而是"这三套实际输入/实现没有达到目标"——诚实的边界，比乐观的总结合有价值。

## 决策点与判决框架

**决策点：余量按什么口径要求？何时接受"薄"，何时必须动结构？**

| 选项 | 内容 | 代价/收益 |
|---|---|---|
| A. 只要求"零违例" | 报告无负余量即可推进 | 最省事；但 0.000ns 也满足——留不住任何环境裕量 |
| B. nominal + 记录 0.300ns gate 如实评定 | 交付按 nominal；0.300 只作判读线，接受/拒绝都记录 | 本项目现行主口径；不吹不瞒 |
| C. 实现期预留 0.300ns 后按 nominal 验收 | 布线时人为收紧再恢复 | 已验证可行（差值恰为 0.300）；但 114913 实测表明"预留也不保证 nominal 达标" |
| D. 降频/换速度档 | 把周期从 5ns 放到约 6ns | 直接买到约 1ns 预算；代价是吞吐余量下降、需重做 IP 与集成 |

- **权衡维度**：风险落在哪一层（离线时序 vs 板上行为）；对手册口径的偏离程度；重做成本（IP 生成/集成/复测面）；可逆性。
- **当前选择**：B 为对比主口径；0.300ns 定位为"探索线、如实评定"（`../../workflow/runs/20261017_153201_T01_ddr1333_integration/dev-plan.md` §1.7；M1 评估口径=nominal）。A 明确不足；C 作为过程工具、不作交付口径；D 由频点决策走（第 10 章）。
- **何时应重开**：① 板测显示时序相关的异常（失稳、误码）；② 参数变化（新 IP/工具版本/器件批次）导致旧报告失效；③ 优化窗口出现且量化收益成立；④ 手册资格/组织方口径变化改变风险定价。改判前先问三个问题：**报告口径是什么？最差路径属于谁？如果它再坏 0.1ns，代价是什么？**

## 常见误区

- **"零违例 = 时序没问题"**：0.000ns 也是零违例。**为什么错**：余量是余额不是结论，余额为零时任何扰动都直接变负。**正确做法**：零违例后继续问"最差余量多少、什么口径、覆盖率多少"。
- **"正余量 = 可以交付"**：0.008ns 是正的但低于 0.300ns 目标，归档 `deliverable=false`。**为什么错**：交付标准是约定目标而不是数学符号。**正确做法**：把目标口径写进验收条件，逐次对照。
- **"换更强的综合/布线策略就能解决"**：TimingHigh→TimingUltra 只从 0.001 到 0.008ns。**为什么错**：策略是"同结构里更好的尝试"，结构瓶颈（组合信号驱动宽扇出使能、厂商内部路径）不会因此消失。**正确做法**：先定位结构，再决定策略/结构/降频。
- **"报告只列了 10 条路径，说明只有 10 条要管"**：报告是全量统计的摘录。**正确做法**：看 TNS/组数/覆盖率，并按需用工具复核组数（本项目 `tools/td/check_timing_margin.py` 强制显式组数）。
- **"两个时钟域频率相同就等价于同时钟域"**：同频不同源（不同 PLL 输出）依然是异步关系。**正确做法**：跨域一律按 CDC 处理（同步器/异步 FIFO/握手），并核对复位释放。
- **"复位只是开机的仪式"**：复位信号自身也占时序预算、也跨域。**正确做法**：复位同样纳入路径审查（本项目的 ready 组合信号进入 CE 锥就是教训）。

## 自测题

<details><summary>1. 时钟周期与频率怎么换算？200MHz 和 166.7MHz 分别是多少 ns？</summary>

`T(ns) = 1000 ÷ f(MHz)`。200MHz → 5.000ns；166.7MHz → 1000/166.7 ≈ 6.000ns。两者相差约 1ns，这就是 DDR 从 1600 档换到约 1333 档时"多出来的周期预算"。
</details>

<details><summary>2. 一条路径数据延迟 4.559ns、skew 0.267ns、其他 0.174ns，在 200MHz 下余量是多少？这个结果说明什么？</summary>

`5.000 − 4.559 − 0.267 − 0.174 = 0.000ns`。余量恰为零：名义上"通过"（无违例），但余额为零，任何轻微变化都可能变负——这就是"薄"的含义；同时 4.559ns 里 77% 是布线延迟，说明约束点在物理布线而非逻辑级数。
</details>

<details><summary>3. 为什么"正余量 0.008ns"的项目却不交付？</summary>

因为该项目（111134）事先设定的验收目标是最终 setup ≥ 0.300ns——0.300ns 是一条探索线（等待工具/走线波动的缓冲经验值），不是器件保证。0.008ns 虽然是正的，但低于约定目标，归档 `deliverable=false`，未生成位流。交付标准看"约定口径"，不看正负号。
</details>

<details><summary>4. 实现期预留 0.300ns 的实验想验证什么？guard −0.477 / nominal −0.177 两个数怎么解释？</summary>

验证两件事：① 预留是否真的生效；② 恢复是否干净。布线时给三个时钟临时加 0.300ns 用户 setup uncertainty，于是 guard 报告 = −0.477ns；恢复为 0 后 nominal = −0.177ns。两者差恰为 +0.300ns，说明预留生效且被正确恢复；而 nominal 仍为负，说明**该实现本身不达标**，所以没有生成位流。教训：预留能改变"记账方式"，不能凭空创造余量。
</details>

<details><summary>5. WNS 和 TNS 各是什么？`setup −1.849ns / TNS −24.474ns` 说明什么？</summary>

WNS=最差单条路径余量；TNS=所有负余量之和。−1.8ns 的单点若搭配接近 0 的 TNS，可能是孤立路径；而 TNS −24.474ns 说明违例路径成片——问题不是"一条路径差 1.8ns"，而是"一批路径都不够快"，处理方式（结构性改法）完全不同。
</details>

<details><summary>6. 拿到一份"时序无违例"的报告，你要核对哪些要素才愿意引用它？</summary>

① 是否绑定同一最终实现数据库（综合/布线/报告一次性）；② 工具版本与脚本；③ 口径（nominal/guard）；④ 组数与覆盖率（显式复核，不做自证）；⑤ WNS/TNS/period 数值与最差路径归属（自己逻辑还是厂商 IP）；⑥ 是否与旧证据混用不同输入。缺一项，这份报告的结论就只能缩小范围引用。
</details>
