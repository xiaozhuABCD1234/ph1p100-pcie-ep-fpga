## 10 分钟速读卡

- **本质一句话**：灰度是一条**三段定义的流水线**——Bayer RAW（每格只有一种颜色）→ 3×3 双线性去马赛克（补出 R/G/B 三分量）→ 按人眼亮度权重加权（`Y8`）。三段缺一，"灰度"就不再是"亮度"。
- **为什么重要**：灰度是三条预处理算法的公共入口（第 14/15 章都建立在它之上），也是双目匹配/深度这类下游最关心的"低带宽亮度表示"。语义不冻结，"模糊/亮度/对比度"这类问题就无法验收。
- **本项目怎么用**：语义冻结在 `../../parallel/algorithms/image_algorithms_ref.py`（3×3 双线性、**保 CFA 奇偶的边界夹取**、half-up 平均、RAW10 `>>2` 截断、Y8 公式）；T09 候选 RTL 把该语义做成 4px/beat 流式前端（`../../fpga/csi2/src/img/`），G1/G2 进行中、G3/G4 未做（截至本包撰写时点）。
- **一个记忆锚**：灰度像**给彩色照片"称重"**——先用去马赛克把三个分量复原齐，再按"绿色最重、蓝色最轻"的权重配比；**跳过任何一步，称出来的都不是亮度**。

## 直觉：从"每格缺两种颜色"到"称出亮度"

【通用原理】相机传感器前面贴着一张 Bayer 滤色阵列（CFA）：每个像素格子只"看到"红、绿、蓝中的一种。所以原始数据（RAW）不是一张彩色图，而是一张**每格缺两种分量的马赛克**。Bayer 的 2×2 单元有四种常见排布（相位 0–3），相位错了整幅图颜色就错——这一点第 08 章已经用"玫红事件"讲透；本章默认你已读过第 08 章，只取一条结论：**相位是硬约定，去马赛克是软估计，先硬后软**。

那么"灰度"要什么？只要一条**亮度**通道。最容易犯的错误是顺手做两个"看起来像灰度"的动作：

1. **直接取 RAW 的高 8bit**：每个像素拿它自己那一种颜色的 10bit 样本，截断成 8bit。这样得到的是"三种颜色混在一起的迷彩"，不是亮度——红衣服、蓝天、白纸都会被量化成不同的矩，互相对不上。
2. **只取绿色通道**：绿色占 CFA 一半、且人眼对绿最敏感，确实"最接近"亮度；但它仍只是**一种颜色的测量值**，不是三色加权定义出来的亮度，红/蓝饱和的场景会明显偏差，也无法与参考模型逐像素对拍。

项目采用的是第三种做法：**先补全三分量，再按定义加权**——这才是"灰度算法"，也是后面所有验证的口径【本项目事实】（`../../parallel/algorithms/image_algorithms_ref.py` 模块头"语义来源"；`../DeepSeek独立检测与现行方案整合_2026-10-16.md` §3.3）。

## 原理一：3×3 双线性去马赛克

### 缺什么补什么：三类像素位置，三种规则

【通用原理】最简单的双线性（bilinear）去马赛克：每个位置只需要补"它缺的分量"，用**同色邻居**的平均值补。按当前像素自身的颜色分三类：

| 当前像素 | 缺什么 | 补法 |
|---|---|---|
| 绿（G） | R 与 B | 取**水平或垂直**两个同色邻居的平均（方向由左右邻居判断） |
| 红（R） | G 与 B | G 取四个正交邻居平均；B 取四个**对角**邻居平均 |
| 蓝（B） | G 与 R | G 取四个正交邻居平均；R 取四个对角邻居平均 |

项目的参考实现把"方向判断"写得很小心：绿色像素的水平/垂直方向用**未经夹取的坐标**判定——在 `x=0` 这样的左边界上，若先夹取再判方向，方向会反转，整列绿色像素的 R/B 会对调。参考自检里专门钉住了两种退化情形：`left_green_direction_phase1`（相位 1 左边界）与 `border_color_aware_corner`（角点）【本项目事实】（`../../parallel/algorithms/image_algorithms_ref.py` 的 `demosaic_bilinear` 与 `selftest`）。

### 平均怎么也算"一半"：half-up

【通用原理】两个数的平均若除不尽，取"半进位"（half-up，四舍五入到整数）：`(a+b+1)>>1`——先加一半再右移，效果就是"0.5 进位"。四个数同理：`(s+2)>>2`。这两个式子是参考模型显式定义的"项目口径"，不是任意取整【本项目事实】（同上文件头"本文件显式定义、且 RTL/队友必须复用的口径"）。

### 边界：为什么"保持 CFA 奇偶"而不是随手夹取

图像边界没有邻居。三种常见处理：补零、镜像、复制（replicate）。**复制边界**最常用：把最近的合法同色邻居"复制"过来。但这里有个不显然的坑：

- 对红/蓝位置的**对角邻居**、对绿色位置的**水平/垂直邻居**，目标颜色与当前像素不同；如果直接取"几何上最近的像素"（普通 min/max 夹取），在角点/边列会取到**异色**像素——整列/整行通道错。
- 正确的是**保持 CFA 奇偶**的夹取：把坐标夹回图像内，再把它微调到与目标格点**同奇偶**的位置（左邻列 `0→列 1`、右邻列 `W-1→列 W-2`、上行 `0→行 1`、下行 `H-1→行 H-2`）。这等价于"在同色格点上复制"。退化情形（某维只有 1 像素、无处可挪）退化为该中心像素。

参考实现的 `_clamp_color` 就是这个语义，并用"纯色 CFA 全图逐点精确还原（`demosaic_coloronly_exact_all`）"自检验证：当每个 CFA 格点只放对应颜色的样本时（R=200、G=400、B=700），正确的去马赛克必须**全图每个像素**都恢复到 `(200,400,700)`——边框、角点一个都不能例外【本项目事实】（同上）。

## 原理二：三分量 → 一条亮度（Y8）

【通用原理】视频系统里的"亮度"（luma，记作 Y′）是三色分量的加权和，权重来自人眼感光度：绿色最重、蓝色最轻。两套常用系数：

- Rec.601（标清时代）：`Y′ = 0.299R′ + 0.587G′ + 0.114B′`；
- Rec.709（高清时代）：`Y′ = 0.2126R′ + 0.7152G′ + 0.0722B′`。

（出处见本章延伸资源的维基条目；两套系数"都对"，但属于不同标准，不能混用——混用就是另一种映射，对拍会对不上。）

【本项目事实】项目选择 601 路线，并把系数**定点化**成 8bit 整数权重：

```text
0.299 × 256 ≈ 76.5 → 77
0.587 × 256 ≈ 150.3 → 150
0.114 × 256 ≈ 29.2  → 29
77 + 150 + 29 = 256        ← 权重和恰好 256
Y8 = (77×R8 + 150×G8 + 29×B8 + 128) >> 8     ← +128 是"半值"
```

三个性质值得记住：

1. **权重和 = 256**：所以"灰色输入"（R=G=B）输出还是同一个值——公式不会把白色压暗或把黑色抬亮。
2. **+128 是 half-up**：`>>8` 本身是向下取整，`+128`（256 的一半）把它变成"四舍五入"。
3. R8/G8/B8 来自 **RAW10 每分量 `>>2`**——注意这里**没有** +2：它是**截断**（truncation），不是四舍五入。参考模型头注明确写着"截断不是四舍五入"；两处规则不同、都必须冻结，不能顺手统一。

极端值校验（可手算）：R=G=B=1023（10bit 满量程）→ R8=G8=B8=255 → `(256×255+128)>>8 = 255`；R=G=B=0 → `128>>8 = 0`。参考自检 `y8_weights_sum_256 / y8_white_255_raw10 / y8_black_0` 正是钉这三件事【本项目事实】（同上 `selftest`）。

## 数字：一条可手算的例子

【本项目事实】取一个 10bit RGB 像素 `(R,G,B)=(100,150,200)`（已去马赛克、已 `>>2`）：

```text
Y = (77×100 + 150×150 + 29×200 + 128) >> 8
  = (7700 + 22500 + 5800 + 128) >> 8
  = 36128 >> 8
  = 141            （36128/256 = 141.125，向下取整）
```

再回头看"直接取高 8bit"的问题：对同一张纯色 CFA 图（R=200、G=400、B=700），做法 a 会输出"三个不同值按相位交替的迷彩"；正确的流水线输出是**全图同一个**亮度值（由去马赛克+加权算出）。这就是"逐像素比对"能一眼分辨两种做法的原因。

## 硬件实现视角：4px/beat 的灰度前端

【本项目事实】T09 候选实现把上述语义做成单时钟域、4 像素/拍的流式前端（`../../fpga/csi2/src/img/`）：

```text
RAW10 4px/beat + s_sof/s_eol/s_eof/s_abort
        |
        v
bayer_raw10_demosaic4        （3 个 RAW10 行 bank + 2 个行窗口读取器）
        |  4 × RGB8 lane
        v
4 × rgb8_gray_stream          （每 lane 一份 Y8 乘加：sum[15:8]）
        |
        v
Y8 4px/beat（= 灰度结果；其余两算法分支见第 14/15 章）
```

- **输入打包**：一拍 40bit = 4 个 RAW10 样本，`lane 0（最左像素）= bit[9:0]`（与项目接收链的解包约定一致；T09 记录里"打包方向写反"是曾修掉的一类真实缺陷）【本项目事实】（`../../fpga/csi2/src/img/bayer_raw10_demosaic4.v` 头注；`../../workflow/runs/20261017-011744-rk-fpga-align/algo/change-report.md` §1/§4）。
- **行窗口**：算第 y 行需要 y−1/y/y+1 三行；3 个行 bank 按行号循环写入，两个扫描读取器同序旋转，保证每 bank 每拍至多一次访问；生产行 y 在输入行 y+1 流入时装配，末行后固定冲刷（`algo_rowwin3.v` / `algo_rowwin_reader.v`）。
- **配置与支持范围**：`cfg_phase`（相位 0–3）一次锁存；冻结支持 `W%4==0、8≤W≤2048、2≤H≤2048`；`W=4`/`H=1` 只由软件参考覆盖（RTL 拒绝并置 `cfg_error`）。
- **握手与异常**：`s_eol` 必须恰在每行最后一拍、`s_eof` 恰在最后一拍；`s_abort`（或活动期内的 `s_sof`、错位 sideband、超长帧）→ 中止帧：不产生 `eof`，发一次 `abort` 标记；停顿（`m_ready=0`）时数据与 sideband 保持（见第 03 章）。
- **Y8 乘加**：`rgb8_gray_stream.v` 用一组常量乘法（77/150/29）与加法完成 `77R+150G+29B+128`，再取和的高 8 位（等价 `>>8`）——常量乘法让综合器自己选实现，不需要查找表；流水级数与中间位宽属实现细节，随该 run 的修复轮演进（以 run 记录为准）。

## 决策点与判决框架

**决策点：灰度路线怎么定义？**

| 选项 | 内容 | 代价/收益 |
|---|---|---|
| A. "假灰度"（取高 8bit/取绿色） | 零成本、一行代码 | 输出不是亮度；红蓝场景失真；与参考不可对拍——**不能作为算法语义** |
| B. 3×3 双线性→RGB→Y8（当前选择） | 固定、可复现、可流水线 | 语义完整、可逐像素核验；代价=行缓存+边界规则+去马赛克逻辑 |
| C. 更高质量去马赛克（方向自适应等）/RK 侧完整 ISP | 边缘伪彩更少、质量上限高 | 复杂度、资源与验证成本高；与"三算法公共前端"的分工冲突，本阶段不选 |

- **权衡维度**：语义可验证性（能否逐像素对拍）；硬件成本；与下游（匹配/深度/压缩）的对接一致性；照明与场景泛化。
- **当前选择**：B。理由：整合 §3.3 已把该口径冻结为"算法共同口径"；风暴中心不是画质极限，而是"有一个确定、可复核、可并行的亮度定义"；策略 F4 也要求灰度首版选"固定、可复现的 Bayer→亮度路线"，"缩放/边界规则先冻结，不新增 AWB/CCM"（`../superpowers/plans/2026-10-15-fpga-remaining-strategy.md` §5 F4）。
- **何时应重开**：① 真实 RAW 图集证明双线性伪彩严重影响匹配/压缩收益（评估方向自适应或换成 RK 处理链）；② 相机几何/相位冻结值变化（流水线必须随冻结值同步复核）；③ 下游明确需要不同亮度的定义（例如特定标准系数）——则属于"重定义"，须整体重冻结并重跑逐像素验证。

## 常见误区

- **"灰度就是取高 8bit"**：那只是"某一种颜色的截断值"，丢掉两种分量与亮度权重；红/蓝物体会明显失真。**正确做法**：去马赛克补全三分量，再按冻结公式加权。
- **"边界随手夹一下就行"**：普通坐标夹取会取到异色邻居（角点整列/整行通道错，`gray_clamp` 类负对照正是针对此）。**正确做法**：保 CFA 奇偶的复制边界，用纯色 CFA 全图逐点自检。
- **"`>>2` 和 `+128>>8` 都是移位，规则一样"**：前者是截断、后者是 half-up；混用会带来系统性偏差且对拍失败。**正确做法**：按参考文件显式口径分别冻结。
- **"画面看着是灰的就算通过"**：观感无法区分相位错、边界错、舍入差。**正确做法**：独立 oracle+冻结向量+逐样本比对，并跑负对照证明测试能拒绝错误实现。
- **"RGB565 预览能显示灰度，就说明灰度链好了"**：预览采样器是 4×4 取 2×2 的调试路径，与正式全分辨率路径不是一回事（整合 §2 M03）。**正确做法**：正式路径单独验收，两者不互相背书。

## 自测题

<details><summary>1. 为什么"直接取 RAW 高 8bit"不能算灰度算法？</summary>

RAW 每个格点只有一种颜色的样本；取高 8bit 得到的是"三种颜色交替的截断值"，不是三色加权定义的亮度。对红/蓝场景会明显失真，且与参考模型无法逐像素对拍。灰度语义要求先补全 R/G/B（去马赛克）再加权。
</details>

<details><summary>2. 3×3 双线性去马赛克里，绿色像素和红/蓝像素分别怎么补缺失分量？</summary>

绿色像素缺 R、B：R/B 分别取水平或垂直两邻居平均（方向由左右邻居决定，且用未夹取坐标判定）。红/蓝像素缺 G 与另一色：G 取四个正交邻居平均，另一色取四个对角邻居平均。平均用 half-up：`(a+b+1)>>1`、`(s+2)>>2`。
</details>

<details><summary>3. 计算：`(R8,G8,B8)=(0,128,255)` 时 Y8 是多少？</summary>

`(77×0 + 150×128 + 29×255 + 128) >> 8 = (19200 + 7395 + 128) >> 8 = 26723 >> 8 = 104`（26723/256≈104.4，向下取整）。验证权重和 256：灰色输入时输出恒等。
</details>

<details><summary>4. 为什么边界夹取要"保持 CFA 奇偶"？</summary>

因为目标邻居的颜色与当前像素不同：直接夹取会在角点/边列取到异色像素，破坏该位置的通道语义（整列/整行错）。保持奇偶的夹取等价于"在同色格点上复制"；纯色 CFA 全图逐点精确还原的自检就是它的判据。退化维度（1 像素）退化为中心像素。
</details>

<details><summary>5. 为什么 `>>2` 是截断而 `+128>>8` 是 half-up？两者能统一吗？</summary>

参考实现显式规定：RAW10→8bit 用 `>>2`（截断，无 +2）；Y8 加权用 `+128` 后 `>>8`（四舍五入）。两者规则不同、都必须冻结；擅自统一会造成系统性偏差并与参考逐像素对拍失败。
</details>

<details><summary>6. 什么是"逐样本比对+负对照"？为什么它比"看着对"更可信？</summary>

逐样本比对=把 RTL/实现的每个输出像素与独立 oracle 的期望值逐一比较；负对照=故意改坏一个语义点（如舍入/边界）的变体必须被测试拒绝。观感无法区分相位/边界/舍入级别的错误，而这两种检查可以给出可重放的证据。
</details>
