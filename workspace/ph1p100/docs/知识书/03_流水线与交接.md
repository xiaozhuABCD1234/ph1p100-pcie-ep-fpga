# 第 03 章 流水线与交接

> 本章回答：为什么"多插几级流水"不一定更快？数据在两个模块之间到底怎样才算"交接成功"？相机为什么不能被反压？跨时钟域为什么必须换一套接法？
> 事实标记：【本项目事实】可追溯到项目文件路径；【通用原理】来自公认外部资料；【设计候选】【待验证】【未决】表示尚未实现/未板验/未拍板。时钟与余量的"收支账"见第 02 章。

## 10 分钟速读卡

- **本质一句话**：流水线用"切割长路径"换频率，牺牲的只是单笔数据的**延迟**；而模块之间的交接，只有 `valid && ready` 同时成立的那一拍才算数——这一拍之后双方各自负责保持自己的承诺。
- **为什么重要**：本项目几乎所有数据面问题（丢帧、错位、偶发坏帧、CDC 玄学）都会落在"交接协议"上；判断一个模块是否真的可集成，先看它的 ready/valid 是否守约。
- **本项目怎么用**：相机入口用异步 FIFO（格雷码+两级同步+读预取）跨越 MIPI 域到用户域；`fpga/csi2/src/mem/ddr_frame_store.v` 在 ready 丢失时要清槽、计 drop 并等控制器合同清理；"停顿必须保持 data 与全部 sideband"写进了策略文档（策略 §3）。
- **一个记忆锚**：交接=快递签收：包裹在手（valid）＋对方伸手接（ready）＝一次交接；对方没伸手，你就得**保持包裹原样**，还不能把寄件人信息（sideband）弄丢。

## 本章要回答的问题

2. 一次"交接"究竟在什么时刻发生？valid 和 ready 各自承诺了什么？
3. 下游停顿时（stall），上游必须保持哪些东西不变？只保住 data 够不够？
4. FIFO 解决什么问题、解决不了什么问题？异步 FIFO 为什么能跨时钟域？
5. 为什么相机数据不能被任意反压？消费不及时时正确的动作是什么？
6. 跨时钟域传递单 bit / 多 bit / 连续流，各用什么手法，各自的代价是什么？

## 直觉：流水线是"分工"，不是"加速魔法"

把一批货物从 A 送到 B：一个人搬完全程（取货、打包、送走）要 3 小时，每小时只能送 1 件。若把流程切成三段，三人各负责一段——单件从 A 到 B 依然是 3 小时（**延迟没变**），但每小时可以送 1 件（**吞吐没变**？见下）。真正的变化出现在"每段本身更快"的时候：分段后，每段的工作量变小，**每段可以在更短的节拍内完成**——于是同一条长路径被切成两段短路径，时钟可以打得更快，吞吐随之上升。这就是流水线（pipeline）的全部秘密：

- **延迟（latency）**：一笔数据从进到出要经过几拍/多少时间；
- **吞吐（throughput）**：稳态下每单位时间能处理多少笔；
- 加流水级：延迟通常增加，吞吐只有在"频率真的提上去了"时才增加。

【通用原理】这是教科书式的分工模型（见 `延伸资源` 的流水线条目）。映射到同步电路：每一级＝一段组合逻辑 + 一组寄存器；"节拍加快"＝第 02 章的周期预算账。**所以"流水级数多"既不等于"快"，也不等于"好"**——每级都要消耗寄存器、布线资源和功耗。

### 一个数量级例子

【本项目事实】显示链 1080p60 的像素时钟是 148.5MHz，像素率 148.5M pix/s；而双路 1080p30 采集只需处理 124.416 Mpix/s（需求预算）。再看另一种账：一个 8×4 的合成帧经过三层流水，延迟多 2 拍——对这种尺寸，2 拍的延迟完全无所谓；但对"低延迟闭环控制"（比如相机->处理->显示->再拍）14 拍就可能致命。**先问清应用要的是延迟还是吞吐，再决定砍不砍流水。**

## 原理：valid/ready 是一次"签约"，不是一个信号

数字设计里模块之间最常见接口是 **ready/valid 握手**（也叫 AXI-Stream 风格接口）【通用原理】：

```text
拍号          0    1    2    3    4
valid         1    1    1    1    0
ready         1    0    0    1    -
data          A    B    B    B    -
实际交接      A    -    -    B    -
```

- **发送方承诺**：`valid=1` 时，`data` 及相关 sideband 必须**稳定存在**，直到这一拍被接收；`valid=0` 表示"本拍没有有效数据"。
- **接收方承诺**：`ready=1` 表示"本拍我能收"；`ready=0` 表示"现在别给我"。
- **交接（握手）发生的唯一时刻**：`valid && ready` 同时为 1 的那一拍。除此之外的时间，双方各守各的承诺。
- **stall（停顿）**：`valid=1 && ready=0` 的每一拍，发送方都必须"原地保持"。
- **sideband（边带信息）**：随数据一起流动的辅助信息——帧号、行号、Bayer 相位、错误标志、`last/keep` 掩码等。**停顿保持时必须连 sideband 一起保持**，延迟（打拍）时也要一起延迟，否则数据回到下游时就会"张冠李戴"。

【本项目事实】这条纪律写在本项目策略文档里：处理层用 ready/valid 时，**"停顿必须保持 data 与全部 sideband，不丢掉行列/Bayer 位置"**（策略 §3，两层接口约定）。接口还应带 `keep`/像素有效掩码、帧/行标记与错误信息（`../../当前必读/01_FPGA主线学习手册_由浅入深.md` §10.1）。

### 三条容易违反的纪律

1. **valid 不能"等 ready 到了才产生"**：真实系统中 valid 必须由数据本身到达驱动。若 valid 的生成依赖 ready，就形成组合环（valid ← ready ← valid），轻则时序紧张，重则双方互等【通用原理】。老手册的原话："valid 不能等 ready 到了才临时产生，否则在某些组合中双方可能互等。"
2. **ready 不能"拍脑袋"**：ready 若由浅组合逻辑产生（尤其跨模块直接串成链），它就是时序报告里的常客。**ready 是路径**，不是免费的信号。
3. **协议要写清"谁先动"**：没有数据的合法停顿、`last` 何时有效、错误帧怎样中止——这些必须在接口文档里冻结，否则两个模块各自"合理"的实现会对接不上。

## 数字：缓冲区的账——FIFO 能撑几拍，撑不住怎么办

**FIFO（先入先出队列，First-In First-Out）** 是"能存一点、按顺序取"的短缓冲。它解决的问题是**有界的速度波动**：下游偶尔忙一拍、上游偶尔挤两拍，FIFO 吸收掉这个抖动。

它的容量账很直观【通用原理】：设下游瞬时停顿为 `k` 拍、上游持续速率不变，则需要 `k` 拍深度的余量；若下游的**平均速率**长期低于上游，任何有限 FIFO 都会被填满——这不是深度问题，是速率问题。

**填满之后的行为，才是真正的设计内容**：

| 缓冲满时的选择 | 结果 | 适用场景 |
|---|---|---|
| 反压上游（拉低 ready） | 上游 stall，数据不丢 | 上游可以被反压（如算法流水、DDR 读） |
| 丢新数据 | 丢的是"迟到的"那笔 | 尽力服务型通道（如统计/日志） |
| 丢整帧并计数 | 丢的粒度=帧，下游能识别缺口 | **不可反压的连续流（相机）** |

【本项目事实】本项目对相机入口采用第三种：`fpga/csi2/src/mem/ddr_frame_store.v` 在 `ddr_ready` 丢失时：清空全部槽位状态、`write_state` 归 IDLE、`drop_count` 自增一次（仅在有活动写入时），并**重置 reader 与未完成读响应**；等 ready 恢复后从新帧边界重新开始。注意其代码注释写明：**"Recovery without that flush needs a controller-specific drain/epoch adapter"**——不清理未完成响应的"恢复"是伪恢复，旧响应会串进新会话。

### 异步 FIFO：把"跨时钟域"变成"只用指针跨域"

数据字可以在两个时钟域之间"原地不动"（用双端口 RAM：写端口用 wclk、读端口用 rclk），真正需要跨域的只有**读写指针**。指针跨域的两个安全做法【通用原理】：

- **格雷码（Gray code）**：相邻计数值只差 1 bit，两级同步器某个瞬间读到"旧值或新值"时，语义仍然是一个合法的中间计数——不会读出"半新半旧"的跳变值。
- **两级同步器 + 保守空满判定**：满/空的计算故意保守，宁可虚报"满"也不虚报"空"（虚报空会丢数据，虚报满只降性能）。

【本项目事实】`fpga/csi2/src/mem/capture_async_fifo.v` 就是这个模式的教科书实现：写指针/读指针先转格雷码，分别用两组同步器各打两级；满判定用"高 2 bit 取反"的格雷码比较；读侧带**预取一拍**（registered read prefetch），被注释说明是为了"permit inferred dual-clock RAM and hold data under backpressure"；格雷码寄存器显式标注 `(* dont_touch="true" *)`（防工具把它优化掉，SWUG106 §4.3.6 要求保 clock 域输出稳定）。读数据在 `r_valid=1 && r_ready=0` 时**保持**——这正是"stall 保持"纪律的实现。

## 硬件实现视角：把协议做进结构里

1. **ready 抖动的代价**：ready 若由组合逻辑长链生成，握手链本身就会成为时序瓶颈。常见替代是"把 ready 注册一拍"（带 skid buffer 的弹性缓冲）——把组合路径换成面积，换频率。**本项目真实案例**：002820 的最差路径恰是"DDR 初始化组合 ready → reader 使能（CE）"（详见第 02 章实例），修复方式就是让内部使能改用已同步的 `usr_reset[1]`，本质上把"组合 ready 直连使能"化成"同步域内的既定状态"。
2. **数据通路的延迟一致性**：接收链上游（解包/裁剪）延迟 N 拍，帧号/行号就必须同样延迟 N 拍；任何一处少打一拍，都会在拼接处产生一行错位。行缓存（line buffer）与窗口寄存器是邻域算法的标准手段（第 14 章）。
3. **帧边界锁定**：模式/算法选路、LUT 切换只在合法的帧边界生效（第 15 章的"换帧锁定"）；否则同一帧里前后算法不一致，输出无法判读。
4. **复位与恢复**：MIPI 域可能**停钟**（相机没出流时接收时钟可能不存在）。停钟域的恢复要按"时钟回来→同步释放→重新对齐"处理；跨域 FIFO 的复位也必须在**两个域各自**完成，组合不起来就是悬空指针。
5. **权限与"未完成响应"**：DDR 控制器有 outstanding（未完成）读事务。反压丢失时若不清 pending，旧响应会注入新会话。处理方式只有两条：**控制器合同支持的清理（flush/reset）**，或**专门的 drain/epoch 适配器**——没有第三条捷径。

## 本项目实例：从相机到 DDR 的交接链

【本项目事实】把第 02 章的"节拍"和本章的"交接"拼起来，本项目的数据面长这样（路径均可在仓库核实）：

```text
相机(MIPI 域，不可反压)
   │  字节流
   ▼
CSI 解析/对齐（pe/字节边界）
   │
   ▼
capture_async_fifo.v   ← 异步 FIFO：格雷码指针+两级同步+读预取
   │  （跨到 DDR 用户域）
   ▼
ddr_frame_store.v      ← 写槽/围栏校验/发布；ready 丢失→清槽+drop_count
   │  （PAXI 256bit 写 DDR）
   ▼
DDR 读（显示/后续传输；READING 槽不会被新帧覆盖）
```

- **入口侧**：相机不能反压（见下文），所以 FIFO 满时**唯一正确的动作是"让这一帧失效并计数"**，等下一个可靠的帧边界恢复（老手册 §10.2："缓存满时的首版策略是标当前帧无效、计数并在可靠的新帧边界恢复。不能静默丢几个字节后继续……发布一张'尺寸正确'的坏图"）。
- **DDR 槽状态机**：`fpga/csi2/src/mem/ddr_frame_store.v` 的每槽四态 `FREE/WRITING/READY/READING`；写完整帧后经过"栅栏（fence）"——把最后一个 256bit 字**读回来比对**，一致才置 READY；**新完整帧只替换 READY 槽，永不覆盖 READING**（代码注释原话："Newest complete frame replaces only READY, never READING"）。这正是第 12 章"预览替换策略不能用于正式传输"的伏笔。
- **丢帧账**：`drop_count` 只在"ready 丢失且确有活动写入"、"围栏校验失败（坏帧）"或"主动 abort/写长度不符"时 +1，**不是**每次 ready 抖动都记一笔，也不是逐帧完整账本（`../../docs/DeepSeek独立检测与现行方案整合_2026-10-16.md` §3.4 对此有精确修正）。读计数要按这个语义读。
- **为什么要这么谨慎**：项目口径是"一整帧要么完整发布、要么整帧作废"；坏帧不能进入 READY 槽（否则显示/编码/传输端会拿着半张图干活）。

### 为什么相机不能任意反压

【通用原理 + 本项目事实】PCIe 或压缩模块可以通过拉低 ready 暂缓输入；但相机已经按自己的时序把 MIPI 字节流发出来了，**它不会因为 FPGA 的 FIFO 满了就停下来等你**（老手册 §10.2）。因此接收入口的约束是硬性的：

- 接收入口必须**及时消费**（保证采样窗口内的字节不丢）；
- 允许的停顿上界由 FIFO 深度 + DDR 吸收能力决定，必须**可计算**而不是"大概够"；
- 消费不及时的后果按"整帧无效"处理，而不是"静默丢字节继续拼一张尺寸正确的图"；
- 正式队列要记录缺口（采集序号），让下游（RK）能识别"这帧缺了"。

## 决策点与判决框架

**决策点：相机入口与下游之间，交接用什么结构？下游变慢时加 FIFO 还是改结构？**

| 选项 | 内容 | 代价/收益 |
|---|---|---|
| A. 同步 FIFO / 直连 | 同域短缓冲或直接握手 | 最省资源；只适用于同域且可反压的场合 |
| B. 异步 FIFO（格雷码+两级同步+预取） | 连续流跨域的标准解 | 资源中等、通用；需要守"指针只转格雷码、满空判定保守"的纪律 |
| C. 往返握手（req/ack） | 每次交接等回话 | 简单可靠；吞吐低，适合低频控制/寄存器访问 |
| D. 加更深的 FIFO | 用容量吸收抖动 | 成本低；**只能吸收有界抖动**，长期速率倒挂加多少层都会满 |
| E. 改结构（提升消费能力/分流/降负载） | 从根上消除倒挂 | 成本最高；一旦速率差是结构性的，这是唯一正解 |

- **权衡维度**：抖动是有界还是长期（有界→容量，长期→结构）；吞吐/延迟要求；资源与频率预算；恢复语义（丢了之后"从哪继续"）。
- **当前选择**：B 用于相机→用户域连续流；C 用于低频控制（如 I2C 事务的完成判定）；DDR/传输侧按帧粒度所有权管理（D）；**明确不用"加 FIFO"掩盖长期倒挂**（策略 §8 停止条件 3：加 FIFO 不能解决长期速率倒挂）。
- **何时应重开**：① 实测丢帧计数/高水位显示结构性倒挂；② 时钟域或带宽参数变化（新 IP/新档位）；③ 需要更低延迟（帧同步、闭环显示）；④ 资源/频率预算变化使"注册 ready/skid buffer"更划算。

**决策卡（第二问）：停顿恢复后"从哪继续"？**

- 选项：（i）字节级续传（风险：错位后几乎必然坏帧）；（ii）整帧作废+下一帧边界重建（本项目选择）；（iii）后备方案：从 FIFO 快照恢复（代价高、语义复杂）。
- 当前选择：（ii）。理由：相机流不可重放，帧边界是唯一可靠的"重新开始点"；整帧作废保证下游永远拿到"完整或者明确标记坏"的帧。
- 何时应重开：若未来出现"必须零丢帧"的场景（如标定连续采集），需要另设计"入口带宽预留+高水位预警"而不是改恢复语义。

## 常见误区

- **"流水级数越多越快"**：加级只增加延迟；频率是否提升要看路径是否真的被切短、工具是否认同。**正确做法**：以最终 STA 报告为准，而不是以"我插了几级"为准。
- **"valid 和 ready 随便写一个先后都行"**：valid 依赖 ready 会形成互等环。**正确做法**：valid 由数据到驱驱动，ready 由容量状态驱动；两边都用寄存器化输出最稳。
- **"stall 只需要保持 data"**：帧号/行号/相位/掩码是数据的一部分语义。**正确做法**：把 sideband 与 data 绑成一个"包"一起打拍、一起保持（本项目的 `fpga/csi2/src/mem/capture_async_fifo.v` 数据宽度 258bit 就是 data+sideband 一起跨域）。
- **"FIFO 是无限缓冲"**：任何固定深度都会被长期速率差填满。**正确做法**：算清"允许的停顿上界"，超界就按整帧作废/改结构。
- **"两个域频率一样就可以直连"**：同频不同源仍是异步关系，边沿可漂移；且两域复位释放时刻不同。**正确做法**：跨域一律用同步器/FIFO/握手，并各自复位。
- **"多 bit 信号打两拍就行"**：多 bit 位间延迟不同，可能采到半新半旧组合。**正确做法**：多 bit 走格雷码/FIFO/握手（第 02 章 CDC 表）。

## 自测题

<details><summary>1. 给某模块插入两级流水后时钟没变，但每级组合更短所以频率从 150MHz 提到 200MHz。延迟和吞吐分别怎么变？</summary>

延迟增加约 2 个时钟周期（每级半拍到一拍不等，取决于寄存策略）；吞吐从 150M 笔/s 提到 200M 笔/s。结论：吞吐收益来自"频率真的上去了"，不是来自"级数多"本身；若频率没变，加级只是白花寄存器。
</details>

<details><summary>2. 拍号 0–4 的 valid=`11110`、ready=`10011`，哪些拍发生了交接？第 1、2 拍发送端必须做什么？</summary>

交接发生在 `valid&&ready` 的拍：拍 0（1&1）和拍 3（1&1）；拍 4 valid=0 无交接。拍 1、2 是 `valid=1 && ready=0` 的 stall——发送端必须保持 `data` 与全部 sideband 原样，直到被接收。
</details>

<details><summary>3. 为什么异步 FIFO 只把"指针"做跨域处理，而不是把数据本身同步过去？</summary>

数据字放在双口 RAM 里，写用 wclk、读用 rclk，物理上"不搬家"；真正需要跨域的是读写指针——用格雷码+两级同步让本域看到"合法的旧值或新值"。这样每个 bit 不需要被同步，只有指针需要；且格雷码保证相邻值只差 1 bit，读到的中间态仍是合法计数。
</details>

<details><summary>4. 相机 FIFO 满时，"静默丢弃少量字节继续接收"为什么危险？正确动作是什么？</summary>

丢字节后帧内样本错位，但帧长/尺寸字段仍可能"看起来正确"，下游会把一张坏图当成好图发布（项目明确禁止）。正确动作：把当前帧标记为无效、计 drop、丢弃该帧，在下一个可靠的帧边界（如新帧开始）恢复接收。
</details>

<details><summary>5. `fpga/csi2/src/mem/ddr_frame_store.v` 的围栏（fence）读回校验有什么意义？新帧"只替换 READY、不覆盖 READING"在保护什么？</summary>

围栏把写入的最后 256bit 字读回来逐位比对，一致才把槽置 READY——证明"写完整帧并落盘"而不只是"发完了命令"。只替换 READY 保护的是**正在被读的槽**（READING）：显示/传输可能正读该槽，覆盖它会造成画面撕裂或传输坏帧——这也是"预览替换策略不能用于正式传输"的结构原因（第 12 章展开）。
</details>

<details><summary>6. 下游偶发慢 3 拍和长期慢 30% 两种情形，方案该怎么选？</summary>

偶发慢 3 拍：加深缓冲区即可吸收（有界抖动→容量）。长期慢 30%：任何有限缓冲都会被填满，必须改结构——提高消费能力（并行/提频）、分流（减少下游负载）或降低供给（帧率/分辨率）。判断依据是高水位统计与丢帧计数，而不是感觉。
</details>
