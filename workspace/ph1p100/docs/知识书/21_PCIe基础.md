# 第 21 章 PCIe 基础

> 本章是传输篇开篇：把"FPGA 怎么把帧送到主机"的物理层之上、协议层与寄存器窗讲清楚——从链路枚举、BAR 到 TLP 报文与 4KiB 规则。DMA 的授权/完成/回收语义见第 22 章；帧内容的字节格式（R10F）见第 23 章；帧从哪来见第 12 章。
> 事实标记：【本项目事实】可追溯到项目文件路径；【通用原理】来自公认外部资料；【设计候选】【待验证】【未决】表示尚未实现/未板验/未拍板。

## 10 分钟速读卡

- **本质一句话**：PCIe 是一条**点对点高速"快递通道"**——主机（RC）先"登记住户"（枚举）、给设备发"收件地址窗"（BAR），之后 FPGA（EP）把帧数据切成 TLP 包裹，以 Memory Write **主动"邮寄"**到主机内存。
- **为什么重要**：本项目最终交付路径（FPGA→RK）走的正是它；而且"链路通"只到枚举层，离"数据单向搬通"还有好几层要单独证明。
- **本项目怎么用**：FPGA=EP、RK=RC；数据面=EP 主动 MWr 推帧＋门铃；控制面=BAR0 寄存器窗（MAGIC 门槛 0x50434946）；统一路径选择见 decision-register M2-A（`../../workflow/runs/20261017_161109_decisions_compare_freeze/decision-register.md`）。
- **一个记忆锚**：**门牌（BDF）、信箱（BAR 窗）、包裹（TLP）、明信片（Posted MWr 不等回执）**——四件套认全，章就懂了。

## 本章要回答的问题

1. RC / EP 各是谁？"枚举"在枚举什么？
2. 配置空间、BAR、寄存器窗三者是什么关系？
3. 一帧数据在线上是怎么被切分并"寄"过去的（TLP / MWr / MPS / 4KiB 规则）？
4. DW-valid 与 byte keep 差在哪，为什么是硬核适配的经典坑？
5. 为什么说"link 通 ≠ DMA 通"？本项目现在卡在哪一层？

## 直觉：一个"快递系统"

把 PCIe 当成一栋大楼的快递系统：

- **RC（Root Complex，根复合体）**＝大楼前台兼管理员：主机侧总线树的根，负责登记与转发（本项目＝RK3588）。
- **EP（Endpoint，端点）**＝楼里的住户：具体设备（本项目＝PH1P100 FPGA）。
- **枚举（enumeration）**＝前台挨家挨户登记：给每户发**门牌号 BDF**（Bus:Device.Function），问清楚要多大"信箱"，然后分配地址。
- **BAR（Base Address Register，基地址寄存器）**＝住户在登记时声明的"信箱尺寸需求"；前台分配后，这个窗口就映射到系统地址空间里。
- **TLP（Transaction Layer Packet，事务层包）**＝包裹。寄实物走 **Memory Write（MWr）**；要回执的查询走 **Memory Read（MRd）**。

关键直觉：MWr 是**"明信片"**——投出去不等回执（Posted）；MRd 是**"挂号信"**——必须等 Completion 回执（Non-Posted）。数据面用前者，因为一帧要寄两万多个包裹，回执成本不可接受。

## 原理：从枚举到 TLP

### 角色与枚举

【通用原理】PCIe 是树形点对点拓扑：RC 是根，下面可以挂 Switch/EP。上电后 RC 逐级扫描：读每段的 Vendor/Device ID、分配 BDF、按 BAR 需求分配地址窗、协商链路参数（如 MPS）。本项目设备在 RK 侧登记为 `0x1edb:0xabcd`，节点 `/dev/ANLOGIC-PCI0_{control,user,frame}`（`../../workflow/runs/20261016_2110_pcie_unified_path/pcie-unified-path-assessment.md` §1.2，你方接口核对记录）。

- **BDF 必须与实际枚举一致**：队友侧 TLP 构造头里 BDF 目前**写死 `01:00.0`**（评估 §5 R4）；如果实际 RK 分配的号不同，构造出的报文会被 RC 拒收或路由失败。这是上板第一梯队检查项。
- **枚举成功的可观察判据**（评估 §6 的 L0 级）：RK 能看到设备、链路速率协商到 Gen2×2、BAR0 偏移 0x40 能读回 MAGIC=`0x50434946`、PIO 读写回环通过。

### 配置空间与 BAR：设备的"收件地址窗"

- **配置空间（configuration space）**：每个功能一块标准化的 4KiB 寄存器区，放身份信息（Vendor/Device ID、类代码）与控制位；RC 通过配置读写事务访问它。它是"注册信息"，不是数据通道。
- **BAR**：设备声明"我需要一段多大地址窗"；RC 分配一段系统地址给它。此后 CPU/驱动读写这段地址，就变成对设备的**寄存器窗（PIO）**访问。
- **本项目实例**：BAR0 就是这样一个寄存器窗——0x40 MAGIC（读回 `0x50434946`＝"PCIF" ASCII）作为"你在跟对的人说话吗"的门槛；0x44 CTRL 控制位；0xB0/0xB4 推帧目标地址（64bit）；0xB8/0xBC 门铃地址；0xC0/0xC4/0xC8/0xCC 帧数/状态/错误码/上帧 MWr 数（评估 §4.2；依据 `ep_bar_win.v`，队友仓库只读引用）。**地址由主机给、EP 不写死物理地址**——这是"授权式 DMA"的基础（第 22 章）。

### TLP：包裹格式与寄送规则

【通用原理】一次 MWr 由头（本项目 4DW＝16B 头＋载荷）组成，头里带 Requester ID（BDF）、Tag、目标地址、长度与字节使能。三条必须记死的规则：

1. **MPS（Max Payload Size）**：链路两端协商的单包最大载荷（128/256/512B 等）。本项目推帧恒定用 **128B/笔**（`PAY_DW=32`）——MPS≥128B 时恒合法，是保守选择；RK 侧实际协商值未确认（评估 §5 R5）。
2. **4KiB 边界**：一个 Memory Request **不得跨 4KiB 地址边界**。若目标起点不按 4KiB 正确对齐，每 4KiB 都会有一笔 128B 的跨界包——速度可能看不出问题，但这是规范性问题，主机/交换机可以合法地拒绝或出错。
3. **字节使能（FirstDWBE/LastDWBE）**：只对头 DW 与尾 DW 有效，用来标记 DW 内哪些字节有效。载荷必须按 DW 组织；"半字节"要靠字节使能表达。

### C2H：EP 主动写主机内存

方向命名：**C2H＝Card to Host**（FPGA→主机），H2C 反之。

- 本项目数据面是 **EP 发起 Posted MWr，把帧字节写进主机驱动的 DMA 缓冲**；门铃也是同一族——**单 DW、LastDWBE=0** 的一笔 MWr，写在 mailbox 页里，通知"第 N 帧推完了"。
- Posted 写之间**不保序超越**（同一通路上数据先于门铃到）；门铃后主机轮询可见性规则见第 22 章。
- 头 DW0（含 Fmt/Type/Requester ID）在本项目 256bit 拍里放在 **[255:224]**，拍内整体字节序为"倒序"约定——**必须全链路逐字节对照实测固化**（评估 §4.6 的 C8 约定，**未测**）。

## 数字：一帧要几笔 MWr？

【本项目事实】以 1080p RAW10 帧、128B/笔为例（评估 §4.5，口径=需求计算）：

```text
传输单元 = 2,592,768 B（633×4096，见第 23 章）
每笔载荷 = 128 B
每帧 MWr ≈ 2,592,768 / 128 = 20,256 笔（对齐式）
      或   2,592,128 / 128 = 20,251 笔（旧式）
双路 30fps ≈ 20,256 × 2 × 30 ≈ 1.22 M 笔/s → 平均间隔 ≈ 0.8 µs/笔
门铃：每帧 1 笔（单 DW）
```

作为对照：队友 640×480 通路每帧 307,200B → **2,400 笔**（自述板级"错误寄存器恒为 0"，**外部自述未复现**，评估 §1.1）。

## 硬件实现视角：硬核、TL 用户口与两个"坑"

- **硬核（hard core）与用户口**：EP 核把物理层/链路层/事务层做进硬核；用户逻辑通过"TL 用户口"注入自定义 TLP。本项目推帧 TLP 走用户口、**最低优先权**，与 BAR 完成包做包级仲裁（评估 §1.1，基于队友 `pcie_ep_engine.v` 的只读核对）。
- **坑 1：DW-valid ≠ byte keep**。PH1P EP 引擎在 256bit 数据上给的是 **8bit DW-valid**（标记哪些 DW 有效），而 AXI 侧习惯用 **byte keep**（字节级有效）。两者混用会在"尾字节/部分 DW"场景下寄出多余或缺失的字节——这正是你方接口核对文档逐条列出的适配点（见 `../../workflow/runs/20261016_2110_pcie_unified_path/pcie-unified-path-assessment.md` §1.3 引注的接口核对记录）。
- **坑 2：TLP 计数位宽**。队友现推帧引擎的每帧 TLP 计数是 **12 位**，而 1080p 需要 20,256 笔——**不够**，属于参数化清单里的必改项（评估 §5 R2）。
- **纪律**：以上均为评估发现与适配清单，**不是已验证结论**；改完要走联调分级判据 L0→L6（评估 §6），每一级独立验证。

## 决策点与判决框架

**决策点：数据面统一到"队友推帧通路"还是"自建 C2H"？**

| 选项 | 内容 | 代价/收益 |
|---|---|---|
| A. 逐模块引入队友 PCIe 后端（推帧＋门铃＋mailbox） | 复用最贵的不确定性（EP 核/链路/寄存器窗/TL 用户口/字节序/反压） | 需跨仓库纪律（版本、位定义、参数化回流）——**已选** |
| B. 自建 C2H 固定块硬核支路 | 接口自主、按 C2H 合同实现 | 重走 EP 核/credit/时序未知区；与 A 同族（都是 EP 发起 Posted MWr），无额外收益 |

- **权衡维度**：落地成本与不确定性、既有板级记录、内容层自主性、跨仓库漂移风险。
- **当前选择**：**A**——我方 csi2 主线＋逐模块引入；HDMI 保留为调试出口；自建计划转为"核对清单"并入统一通路（评估 §2.2；decision-register M2）。原 C2H 固定块计划（PCIT 32B 块）作为 L1 首件在此通路上完成。
- **何时应重开（改判触发）**：①联调证伪"队友通路可复用"（如主机实收证据不足且无法补齐）；②优化窗口（第二引擎/参数化返工有量化收益）；③队友接口漂移到达（按 addendum 模式重对齐）。触发处理入口=decision-register M2 重开条款。

## 常见误区

- **"链路起来了＝数据能通"**：枚举/链路训练只证明 L0 层可用；帧要过地址授权、TLP 分包、4KiB 规则、字节序、门铃可见性，才叫搬通。**正确做法**：按 L0—L6 分级判据逐级验收。
- **"BAR 越大越强"**：BAR 是"信箱尺寸"，不是带宽；带宽由链路速率/宽度与一次能寄多少货决定。**正确做法**：区分控制窗（BAR）与数据面（MWr）。
- **"（4KiB 跨界）反正能跑"**：这是**合规性**问题而不是性能问题；规范禁止的报文可以"幸运地工作"到某天不工作。**正确做法**：地址对齐到 128B/4KiB 规则，先修后联调。
- **"MWr 发出去了＝主机收到了"**：Posted 无回执；"完成"要靠门铃＋主机核验（第 22 章）而不是"我们发出去了"。**正确做法**：把"完成"定义为**主机可确认的状态**。
- **"DW-valid 和 byte keep 是一回事"**：一个是"哪个 DW 有效"，一个是"DW 内哪些字节有效"，粒度不同。**正确做法**：尾拍/非满载荷场景逐字节对照实测。

## 自测题

<details><summary>1. RC 与 EP 分别是什么？本项目里各是谁？</summary>

RC=根复合体（主机侧总线树根，管理枚举与转发）；EP=端点设备。本项目 FPGA=EP、RK3588=RC（评估 §1.4/§4.1）。
</details>

<details><summary>2. 为什么说"link 通 ≠ DMA 通"？</summary>

链路/枚举/BAR 只到 L0（能看见设备、能 PIO 读写）；数据面还要求目标地址授权、分包与 4KiB 规则合法、字节序正确、门铃可见与主机核验通过。`workflow/README.md` §4 把"PCIe link 不是 DMA"列为重要边界；本项目 L1 起才是数据判据（评估 §6）。
</details>

<details><summary>3. 20,256 笔/帧怎么来的？为什么是 128B/笔？</summary>

2,592,768B（633×4096 传输单元）÷128B/笔=20,256。128B 是 `PAY_DW=32` 的恒定选择：只要 MPS≥128B 就恒合法，避免依赖 RK 侧协商值（评估 §4.5/§5 R5）。
</details>

<details><summary>4. 4KiB 规则在本项目踩到了什么问题？修法是什么？</summary>

原驱动把推帧目标设为"槽基址+16B"，而 128B/笔递增会在每个 4KiB 边界产生一笔跨界 MWr（评估 §5 R1）。修法：槽像素区起点对齐 128B（`pixel_off=128`，`dst=phys+128`），已随 T07 rk-align-backend 补丁落盘；RK 侧未编译/加载，联调前必须确认（M2d；rk-change-list §1）。
</details>

<details><summary>5. DW-valid 与 byte keep 的区别？为什么要小心？</summary>

DW-valid 是 256bit 数据上 8bit 的"哪些 DW 有效"标记；byte keep 是"DW 内哪些字节有效"的字节级掩码。两者混用会在末拍/部分 DW 场景寄错字节。属于硬核适配的经典坑（见 `../../workflow/runs/20261016_2110_pcie_unified_path/pcie-unified-path-assessment.md` §1.3 引注的接口核对记录）。
</details>

<details><summary>6. MPS 越协商越大越好吗？</summary>

不一定。MPS 是链路两端的最小值协商，越大单包效率越高但依赖对端与路径能力；本项目用 128B 恒定值换取"恒合法"，代价是包数多、开销大——这是**保守选择**而非最优选择（评估 §4.5/§5 R5）。
</details>
