# FPGA 方案知识书 · 写作规范

> 本文件把本 run 冻结的 `fpga-design-guide.md` §1–§5 展开为**可执行写作细则**，供所有写作包（KB1–KB8）与收束包（KBZ）使用。
> 与冻结指南冲突时，以 `workflow/runs/20261017_162355_fpga_knowledge_book/fpga-design-guide.md` 为准；本文件只细化，不放宽。

## 1. 目录与文件命名

| 文件 | 角色 | 责任包 |
|---|---|---|
| `README.md` | 书首页：目的/读者/阅读路线/目录/进度/维护规则/与旧教材关系 | KB0 建；KBZ 终版 |
| `_写作规范.md` | 本文件：写作与核验细则 | KB0 建；KBZ 终版 |
| `_全书大纲.md` | 27 章＋3 附录冻结大纲 | KB0 建；KBZ 核对 |
| `01_….md` … `27_….md` | 正文章节（每包只写自己包内章） | KB1–KB8 |
| `90_决策索引.md`、`91_术语表.md`、`92_延伸资源总表.md` | 附录 | KBZ |

- 命名细则：章文件 `NN_中文短标题.md`；`NN` 为两位章号（01–27）；标题≤14 字；不含空格与正斜杠；文件名取大纲章题。
- 编码 UTF-8（无 BOM）；换行 LF；Markdown（GFM）。不得写 CRLF 或混合换行。
- 文中引用项目文件一律用相对路径，从 `docs/知识书/` 出发：
  - 同目录文件：`文件名.md`；
  - `docs/` 内文件：`../文件名.md`；
  - 项目根下：`../../当前必读/…`、`../../workflow/…`、`../../docs/superpowers/…`。
- 正文中的**来源署名/定位说明**允许使用项目根相对写法（如 `workflow/…`、`docs/…`，须可从项目根解析）；**可点击链接与文件引用**仍按上述 `../` 规则从本书目录出发（不得混用）。
- 引用的**项目路径必须先核实存在**（写包时逐一核对），禁止引用未创建的文件路径。

## 2. 每章固定结构（10 节，缺一不可）

1. `## 10 分钟速读卡`：四项——本质一句话 / 为什么重要 / 本项目怎么用 / 一个记忆锚；总长 6–10 行，可整段可列表。
2. `## 本章要回答的问题`：3–6 条编号问题；正文应当逐一回答。
3. 正文小节（`##`/`###`）：必须按 **直觉 → 原理 → 数字/公式 → 硬件实现视角 → 本项目实例** 的渐进顺序组织；层次名可润色但顺序不得颠倒；首次出现的术语先给白话定义，再给正式名（中英对照）。
4. `## 与本项目方案的对应`：表格，列为 `结论 | 依据`；依据写项目文件相对路径或【通用原理】；≥5 行；硬件相关章至少 1 条"证据边界"（到哪一层、不能证明什么）。
5. `## 决策点与判决框架`：有决策点则必写，含四要素——选项 / 权衡维度 / 当前选择及理由 / 何时应重开（触发条件）；确无独立决策点时写一行说明并指向相关章。
6. `## 常见误区`：≥3 条；每条写明"误区 → 为什么错 → 正确做法"。
7. `## 自测题`：≥5 条；答案紧随本节之后（`<details>` 折叠均可）；答案必须与正文一致，含数字的必须可验算。
8. `## 延伸资源`：表格，字段固定为 `标题 | 类型(视频/文档/论文) | 语言 | 体量(时长/页数) | 推荐理由(≤40字) | 链接 | 核验状态 | 备用检索词`；每章 3–8 行。
9. `## 术语增量`：表格或列表，三项——术语（中英）/ 一句白话 / 首次出现章号；只列本章新增，供 KBZ 汇总。
10. `## 版本记录`：表格或列表——版本（如 初稿 r0）/ 日期 / 一句变化。

- 每章建议篇幅 120–350 行；不为凑量注水；单章自洽（可独立阅读），跨章引用只写"见第 N 章"。

## 3. 事实分级标记（用到即标）

- 【本项目事实】= 能指向项目文件/证据的陈述；**必须同时给路径**；数字须与来源一致。
- 【通用原理】= 来自公认外部资料的技术陈述；深度内容在"延伸资源"表给出处。
- 【设计候选】【待验证】【未决】= 尚未实现 / 未板验 / 未拍板的方案或口径。
- 使用规则：可能被误读为"已完成"的地方就标；拿不准时宁标不猜；同一句不要堆多个标记，按最主要一层标。

## 4. 外部资源与链接核验（操作规程）

**选择标准**
- 每章 3–8 个；中文资源优先（B 站/中文博客/知乎专栏/中文官方文档），英文权威源（JEDEC 摘要、Micron/AMD/Intel/TI 官方文档、论文）作深入补充。
- 视频优先"能在一次 10–30 分钟内讲清一个概念"的整段课程或高赞教程；不选标题党、带货视频。
- 标题、作者、时长"拿不准就留约"，宁缺勿编。

**核验操作（每包开发执行）**
1. 对资源表每条候选链接发起一次真实网络请求（本项目用会话联网工具；工具不可用时按降级规则）。
2. 记录：URL、请求日期、返回页面标题（与登记标题比对）、结果（通过/超时/失效）。
3. 按结果写核验状态字段：
   - `在线核验通过 yyyy-mm-dd`——实际请求成功，且页面标题/作者与登记一致；
   - `无法在线核验（原因）`——联网工具不可用时使用；**必须**给出精确检索词（他人可复现找到）；
   - `已失效→备选`——原链接失效时替换新链接或降级为检索词。
4. 全部记录写入本 run 的 `link-check-KB<n>.json`（字段：chapter/url/title_expected/title_returned/status/checked_at/proposed_state/note）。
5. 不得虚构 URL、标题、作者、时长；推荐理由只写为什么值得看（≤40 字），不搬运内容。

## 5. 篇幅与文风

- 每章 120–350 行；正文用中文，术语首次出现给中英文对照。
- 数字给单位与来源；比较关系用表格；公式给出可手算步骤（如带单位约简）。
- 一句一事；先直觉后形式化；避免口号、夸张和"看起来大概没问题"式表述。
- 引用他人材料（含教科书、维基、博客）单处≤2 句并注明来源；项目文档一律改为路径引用，不复制大段正文。

## 6. 禁止写法清单

- 不把设计候选、配置值、需求计算写成"已实测/已通过"；不把仿真/软件/离线结果写成硬件通过。
- 不把组织方口径写成已批准（JPEG/LZ77 替代问题＝未决）；不写队友/用户未确认事项为已承诺。
- 不引用不存在的文件路径；不引用未实际核对的外部链接（降级标注除外）。
- 不大段复制外部资料（单处≤2 句，注明来源）或项目文档正文（改路径引用）。
- 不用含糊词掩盖未测（"基本满足""应该没问题""大致通过"）。
- 不预判未决结果（DDR 频点终选、E2 数据、组织方口径）：写"现状＋裁定规则"，不写"已定为"。
- 不写绝对化保证（"一定""永远不会""保证跑得动"）；写条件、边界与触发。
- 不在正文堆未定义缩写；首次使用先白话定义。
- 不跨章抢写：本应属别章的主题只做"见第 N 章"；需要引用尚未写作的章时同样写"见第 N 章"（**不加"（待写）"标记**），已写/未写一律以 `README.md` 进度表为准。
- 不修改 `README.md`、`_写作规范.md`、`_全书大纲.md` 与其他包的章节文件；**唯一例外＝规划者授权的有界修订**（如 README 中本包章节的目录/进度行与"当前快照"句，见 `README.md`"维护规则"；终版复核归 KBZ）。
- 不做"静默改文件"：冻结后任何修订都要走下一次修订轮，并在"版本记录"留痕。

## 7. 单章写作→冻结流程（写给每个写作包）

1. 读冻结输入（requirement/dev-plan/input-index/fpga-design-guide）与本章"建议引用材料"，**核实引用路径存在**。
2. 先列"本章要回答的问题"和要点映射（对齐 `_全书大纲.md` 本章边界），再写正文。
3. 按第 8 节自检清单逐项自查。
4. 逐条核验外部链接并写 `link-check-KB<n>.json`。
5. 生成 manifest（本章文件 SHA256＋引用项目路径清单＋链接核验记录＋读过的来源笔记）。
6. 停止修改、冻结，交三维测试；修复轮更新"版本记录"与 manifest。

- [ ] 项目事实对核 ≥8 处（逐条列出路径）；数字与来源一致。
- [ ] 至少 1 条决策卡（有决策点时必写）。
- [ ] 交叉引用只写"见第 N 章"，且 N 在全书规划内（不添加"（待写）"标记；状态以 README 进度表为准）。
- [ ] 延伸资源 3–8 行，核验状态字段齐全、可复现。
- [ ] 术语增量、版本记录已写；常见误区 ≥3、自测题 ≥5 且答案正确。
