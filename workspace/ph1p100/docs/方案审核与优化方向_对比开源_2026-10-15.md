# 方案审核与优化方向（对照优秀开源方案）

> 记录日期：2026-10-15。**本文是对当前方案的审核与优化建议，不是实测结论，也不是已授权执行计划。** 依据为现有代码、项目文档与公开资料；开源项目性能均为作者报告且平台不同，不能当作本板验收结果。证据等级沿用项目约定：当前器件原文事实 / 跨平台参考 / 推测候选 / 编译 PnR 证据 / 硬件实测，互不替代。本文未改动任何 RTL、约束、PLL 或电气设置。

## 1. 审核对象与范围

- 全链路目标：双 IMX415 → FPGA（MIPI CSI 接收 / 预处理 / 压缩 / DDR 缓存 / PCIe EP）→ RK3588（解码 / ISP / 标定 / 双目匹配 / 深度 / NPU）。
- 当前已实现：单 A 路 IMX415 软 D-PHY 接收 → RAW10 解包 → 960×540 RGB565 预览（固定白平衡 + 相位 3）→ DDR 三缓冲 → 1080p60 HDMI（原生 OSERDES DDRX5 / LVDS33_E）。
- 尚未实现：三预处理硬件分支、压缩 RTL、PCIe C2H 图像 DMA、双路同步、标定/深度/NPU 整队联调。
- 现有风险记录入口：[闪点候选原因排查](闪点候选原因排查_2026-10-14.md)、[HDMI速率核对](HDMI彩点_换线换屏后与速率规格核对_2026-10-13.md)、[RGB565白平衡闭环](RGB565白平衡闭环_2026-10-14.md)、[GitHub强相关项目调研](GitHub强相关项目调研与借鉴建议_2026-10-12.md)。

## 2. 总体审核结论

**做得好的**

- 验证方法学扎实：分层验证、独立参考模型、故障注入、证据哈希、每条结论标证据等级。
- 软 D-PHY + CSI 包层已能真实出图；DDR 三缓冲 + HDMI 1080p60 已跑通；单 A 路 RAW10→预览→显示闭环。

**主要风险**

| 维度 | 审核发现 | 性质 |
|---|---|---|
| 显示输出 | LVDS33_E 输出 1485Mbps、串行 742.5MHz，**超本地手册保证值**（332Mbps / 650MHz）；活动彩点未定位 | 高 |
| 时序余量 | 候选全局 setup **0.000ns**；行缓存→黑电平→乘法→饱和路径为第一轮失败点，现靠加寄存压住 | 高 |
| 采集分辨率 | 预览 960×540，且 `bayer565_capture.v` 只用 **4×4 块的首个 2×2**，等于丢 3/4 像素 | 中高（影响深度质量） |
| 交付进度 | 压缩、PCIe C2H DMA、三算法、双路同步、标定/深度/NPU **均未实现**；队友交付未确认 | 高（时间） |
| 软 PHY | 手动 tap=46，自动扫描回落 32；无温度/长稳下的 tap 稳定性证据 | 中 |
| 颜色 | 固定增益 + 标称黑电平 50，无 AWB/CCM/gamma；换照明仍可能偏色 | 中 |

**一个关键判断**：按[赛题条款与验收矩阵](赛题条款与验收矩阵.md)，压缩帧传输的硬性通道是 **MIPI/PCIe 二选一，HDMI 不是硬性交付项**。HDMI 目前只是本地调试便利——**不要把评分交付绑在一个超出器件保证速率的模拟接口上**。这是最重要的架构级优化方向之一。

## 4. 优化方向与原理

### A. 显示/HDMI：把交付与调试解耦（最高优先）

- **方向**：HDMI 定位为**调试口**而非交付路径；交付的「压缩帧传输」走 PCIe。若仍需清晰预览：优先取得厂商针对本板/本速率的书面支持或官方工程；否则考虑 720p 或半速率预览，或外置 HDMI 发送方案。
- **原理**：赛题要求 MIPI/PCIe 传输压缩帧，HDMI 不是评分项；而 1485Mbps 超本地手册保证值，[hdl-util/hdmi](https://github.com/hdl-util/hdmi) 也独立指出 LVDS 3.3V 直驱在高翻转时易失败。**不要用超出保证的模拟接口承载评分交付**（风险隔离原理）。

### B. 接收前端：让采样窗口可复现、可监测

- **方向**：把 tap=46 从「实测点写死」升级为**带每 lane 眼图/误码统计的校准流程**，记录温度/长稳下的 tap 稳定性；补齐 lane deskew、CRC/ECC 计数。
- **原理**：软 D-PHY 正确性依赖采样相位裕量；固定 tap 在温度/器件差异下会漂移。参考 [gatecat/CSI2Rx](https://github.com/gatecat/CSI2Rx) 的「每层有计数」。当前 `rpj/camera_peer/uisrc/03_ip/mipi_csi_2/mipi_csi2_rx_ph1p.v` 为软 PHY + CSI 包层结构。

### C. 颜色管线：从「固定增益」升级为「最小 ISP」

- **方向**：按 `BLC（暗场实测）→ 去马赛克（双线性→Malvar/边缘感知）→ WB（固定或自动）→ CCM 颜色矩阵 → gamma` 组织；换照明时重新校色。
- **原理**：固定增益只能修「当前照明」的白平衡，不能修传感器色彩空间（需要 CCM）与暗部（需要 BLC/gamma）。RK3588 硬件 ISP 正是这套顺序，可作参照。
- **质量问题**：`fpga/csi2/src/cam/bayer565_capture.v` 注释「from each first 2x2 cell of a 4x4 block」= 丢 3/4 像素。若走灰度立体，建议用**全分辨率灰度或 2×2 平均（binning，提升 SNR）**；低分辨率只用于 NPU 彩色链。

### D. 压缩：换成「Bayer 感知」的无损编码（战略级）

- **方向**：从通用 LZ77/LZSS 改为 **预测（颜色+空间 DPCM）+ 熵编码（自适应 Golomb-Rice / LOCO-ANS / JPEG-LS 类）**，多条像素并行；保留 RAW 回退与块头。
- **原理**：RAW Bayer 强项是**局部空间相关 + 通道相关**，不是长距离重复；字典匹配（LZ77/GZIP）收益有限且搜索带宽大。[OMLS/2024 论文](https://pmc.ncbi.nlm.nih.gov/articles/PMC11510722) 证明「compression-first + 预测 + Golomb-Rice + 16 像素并行」可到 40Gbit/s，且**先压缩再去马赛克**避免 3× 膨胀。
- **吞吐校验**（项目已有复算）：双路 RAW10 需 155.5MB/s、RAW12 需 186.6MB/s（留 25% 余量≈194/233MB/s）。单核 GZIP≈128MB/s **不够** → 要么双核、要么换更省带宽的预测+熵编码、要么降低需传输的数据量。

### E. PCIe/DMA：按描述符与环形队列组织（战略级）

- **方向**：BAR 控制 + FPGA 作 requester 的 C2H Memory Write；按 MPS/4KiB 边界/尾字节分 TLP；DMA 块池 + 环形队列，先轮询后 MSI。
- **原理**：把「帧已产生」与「主机已收全」分开，明确所有权/流控/超时/link reset，避免提前复用缓冲。参考 [verilog-pcie](https://github.com/alexforencich/verilog-pcie)、[LitePCIe](https://github.com/enjoy-digital/litepcie)。

### F. 双目与深度：先保证「可匹配的输入」，再谈算法

- **方向**：匹配输入用**原始或同一版本的灰度旁路**，左右**不做各自直方图均衡**；先离线（RK+OpenCV）跑通标定/校正/匹配/深度，再接实时。
- **原理**：立体匹配要求左右经过**同一**处理/曝光/校正；任何单眼自适应（HE/AWB）都会破坏对应关系（左右一致性硬约束）。

### G. 同步：硬件同步，不是帧号配对

- **方向**：走主从（共享 XHS/XVS）或 FPGA 统一曝光触发；以「对应行/帧的曝光观测」为证据。
- **原理**：赛题「＜1ms」未定义测量对象；帧号相等 ≠ 曝光同步。

### H. 时序/资源：主动造余量

- **方向**：对已知最紧路径（DDR-ready→`last_word` 使能、行缓存→乘法→饱和）**先加流水级再综合**；把全局 setup 0.000ns 视为红灯。
- **原理**：PnR 结果随布局波动，0 余量不可长期稳定；同一最终 DB 重导入仍有覆盖差异，不能从一次通过外推。

### I. 验证方法学（已是强项，继续）

- **方向**：继续用独立 Python 参考模型（如 Project F 的 TMDS 模型）、分层测试、故障注入；工具 exit 0 不算通过。
- **原理**：编译 / PnR / 电气兼容 / 接收正确 / 同步达标是**五种不同证据**。

## 5. 建议优先级

1. **立即**：颜色 G3 板验（当前 `camera_rgb565_wb_20261015_002820`）→ 决定是否补 BLC/CCM/gamma。
2. **本周**：把 HDMI 从交付路径解耦（PCIe 为主线）；接收 tap 稳定化。
3. **本周-下周**：压缩选型从 LZ77 转向 **Bayer 预测+熵编码**，先做软件参考模型 + 真实图集比率/吞吐。
4. **并行**：PCIe C2H DMA（先固定数据）；RK 离线标定/匹配/NPU。
5. **警惕**：不在没有隔离证据时同时改曝光/相位/PHY/IO 标准；不靠「条纹干净」宣告 HDMI 问题解决。

**不建议现在做**：为彩点强行降分辨率或盲改 IO 电平标准；在压缩格式未定前从零同时开发 JPEG 和 LZ77；把深度/匹配塞进 FPGA（既定分工在 RK，且时间紧）。
