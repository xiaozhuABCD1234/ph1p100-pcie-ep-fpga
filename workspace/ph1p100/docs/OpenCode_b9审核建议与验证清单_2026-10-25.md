## 3. 已确认的问题

### B9-01：状态包与帧出队互锁（优先）

源码：[b9 a1_uart_export.v](D:/fpga/ph1p100/workflow/runs/20261020-0209_singleA_aplus_closedloop/T10.b9-rawstore/r0/changed-src/a1_uart_export.v:299)。

三个条件共同形成互锁：

```verilog
// L299：定时到期后保持待发请求
if (sts_tick) sts_want <= 1'b1;

// L302–303：状态包只能在描述符队列为空时开始
if ((sts_tick || sts_want) && (estate == E_IDLE) &&
    (dq_cnt == 2'd0) && tx_ready && !tx_valid_r) ...

// L335：有待发状态包时，描述符队列又不能出队
if (dq_cnt != 2'd0 && sstate == S_IDLE && !sts_want) ...
```

可达过程：第一帧正在发送→第二帧描述符入队→状态定时到期→第一帧完成→`sts_want=1 && dq_cnt>0`。之后状态包等队列空，队列等状态请求消失，两者都不前进。后续 tick 不能解锁。

**实际离线结果：**

| 配置 | exported | 结束状态 | UART busy | 发出字节 | 后续观察 |
|---|---:|---|---:|---:|---|
| `STS_DIV=64` | 1 | `E_IDLE/S_IDLE/want=1/count=1` | 0 | 45 | 再观察 3,000 周期仍为 45 |
| `STS_DIV=0` | 2 | `E_IDLE/S_IDLE/want=0/count=0` | 0 | 90 | 两帧完成 |

复现通过正常接口输入，无 force、无内部状态注入；两种配置使用同一原始 RTL。测试采用 `UART_DIV=1`、每帧 1 B 合成载荷、44 B 头，以加速暴露仲裁问题。**它不是有效压缩流/CRC 验收，也没有覆盖真实 DDR、1080p 带宽或板级时序。**

复现命令（依赖本机现有 ModelSim 和 Python；仅在审查目录生成仿真产物）：

```powershell
python D:/fpga/ph1p100/work/b9-opencode-audit-20261025/run_repro.py
```

预期标记：`REPRO_CONFIRMED unchanged_b9_status_queue_deadlock` 与 `CONTROL_CONFIRMED same_two_frames_complete_without_status`。这两条表示旧缺陷复现和对照成立，不表示新修复通过。

**建议修法供审核：**

1. 在帧边界统一计算 `status_due = sts_tick || sts_want`，由同一仲裁决定“发状态”或“开下一帧”。
2. 队列非空不能阻止状态获得帧间发送机会；状态获准时，帧不得同时出队。
3. 必须处理 tick 当拍：只删除 `dq_cnt==0` 条件仍不够，因为该拍 `sts_want` 是旧值，可能同时启动两个状态机。
4. `accepted_pop` 必须来自实际仲裁结果；保留最后一个 UART 字节完成后的安全交接，保持帧头与载荷连续。

帧间仲裁修复解决此处互锁，不能保证所有 DDR 故障下仍每秒输出状态。若要求在任意业务停机时都有诊断，需另审独立诊断通道或有明确封装的传输复用。

### B9-02：描述符队列指针越界和计数覆盖

同一 exporter：L138 数组是 `dq[0:1]`；L139 指针 `dq_wr/dq_rd` 却是 2 位；L279/L344 自增后会取到 2、3，超出数组。L280 和 L345 在同一 always 中分别对 `dq_cnt` 非阻塞赋值，同拍 push/pop 时后者覆盖前者，计数不能正确保持。

建议采用 1 位环绕指针，并按真正接受的 push/pop 集中更新计数；明确“满队列且同拍出入”的接受策略，不擅自改变容量语义。

可参考此前已独立验收的[描述符局部修复候选](D:/fpga/ph1p100/workflow/runs/20261024-221529_fpga-sim-integration-recovery/T10.a1-uart-descriptor-fix/candidate/a1_uart_export.v:89)。**只移植适用的队列修复，不能整文件覆盖**：该候选没有 b9 的状态 v3 扩展及同样的仲裁逻辑，pop 条件也必须适配 B9-01。

这两项是源码确认的问题；本次新增动态复现针对 B9-01，未声称用上述 2 帧 TB 验证了队列第三次访问或同拍计数。

LED 依据：[p2_a1_board_top.v](D:/fpga/ph1p100/workflow/runs/20261020-0209_singleA_aplus_closedloop/T10.b9-rawstore/r0/td/src/p2_a1_board_top.v:417)。

| 观察 | 可支持的结论 | 不能直接推出 |
|---|---|---|
| LED0 闪 | 自由计数器所用 clk_a1 有活动 | 业务复位已释放、DDR 就绪、整条流水线正常 |
| LED1 对应逻辑非零 | 累计 exported 非零 | 当前仍在发送、PC 已完整收到 |

| LED3 对应逻辑非零 | 累计 cap_frames 非零 | 当前仍持续采集 |

实际“亮”对应高或低仍需板级 LED 极性确认。LED0 的计数器不受 `a1_rst_n` 复位，不能拿它替代业务复位观测。

历史采集必须分时段：

- `captures_pwr2/com8_60s.bin` 实际为 0 B，证明该窗口静默，不能独自证明 exporter 停在帧内或已停钟。
- 旧 `result-r0.md` 早期“下载后一直无状态包”的结论应按后续成功采集补充时间线。

## 6. 为什么暂不采用帧内强插

现协议是 **44 B A1U1 头＋连续的 stream_len 字节压缩载荷**。[decode_frame.py](D:/fpga/ph1p100/workflow/runs/20261020-0209_singleA_aplus_closedloop/T10.b9-rawstore/r0/board/decode_frame.py:43)按此长度取数据并检查流 CRC、解压；插入 177 B 会改变载荷。独立状态解析器只扫描状态包，没有对图像帧做去除插包和重组。

压缩载荷可以包含 `A5 5A`，只按 magic 重新同步不能形成无歧义协议。仅强制启动现状态 FSM，还可能与帧 FSM 同拍覆盖 `tx_byte_r`、各自推进索引。

审核可比较三条路线：

| 路线 | 作用与边界 | 建议 |
|---|---|---|
| 修复帧间统一仲裁 | 直接处理已复现互锁，保留现接收协议；帧内部真等待仍会延迟诊断 | 当前优先 |
| 现有 ChipWatcher/CWC | 可对已映射计数器取增量，辅助定位；当前 CWC 未映射全部内部状态 | 可利用现有能力，先核对映射 |
| 独立诊断或有封装的帧内复用 | 可设计成业务阻塞时仍可诊断；需明确类型、长度、序号、校验、转义/分块及接收端重组 | 另作方案评估，不当作简单插几字节 |

当前 CWC 没有映射 `estate/sstate/sts_want/dq_cnt/raw_wr_state/raw_rd_state/a1_busy`，不能承诺直接读出这些任意内部信号。若下一候选增加探针，优先包含仲裁、UART busy、DDR AR/R 等待和业务复位状态，并使 CWC/bit 与候选绑定。
