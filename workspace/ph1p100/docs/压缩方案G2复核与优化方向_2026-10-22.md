# 压缩方案 G2 复核与优化方向（2026-10-22）

> 历史快照说明：本文件记录当日较早的 r0-b/S2 评审。后续 cmem/smem/bm/htab 的 ERAM 迁移已完成，最新真实布线资源为2974 Slice/26 ERAM，时序为-0.436 ns。当前路线与计划见 [G2流水收敛规划](superpowers/plans/2026-10-22-a1-g2-pipeline-closure-plan.md)；以下103.88%资源和“未布线”等描述仅属于旧候选。

本次为只读技术评审。依据现有 RTL、综合原始报告和仿真结果，不启动旧 dispatch，不修改 RTL、约束、任务状态或修复计数，不运行综合、布线或硬件操作。

结论：建议保留“Bayer 重排/可选预测 + LZ77/fixed-Huffman + stored 回退”的算法路线，优先优化存储实现和流水调度。目前没有证据表明必须换压缩算法；已有证据明确显示大缓存未使用 ERAM，且候选码流缓存 cmem 展开为大量寄存器。仅补掉当前 -0.092 ns 不能保证资源和布线验收通过。

## 2. 更重要的工程问题：存储映射

S2 同一 syn_1 的原始 gate.area：

| 指标 | 数值 |
|---|---:|
| Slice 预测 | 74464 / 71680 = 103.88% |
| 寄存器 | 68075 |
| ERAM | 0 / 300 |
| DRAM LUT | 10352 |
| core 寄存器 | 67500 |

报告第 46 行说明 Optimize-Gate 的 LUT/Slice 数不是最终值，需要 Optimize-place 才能更准确。因而这里是资源风险信号，不能直接宣称最终布局一定放不下。该 area 文件未单独列入现有 manifest；它与 timing 位于同一 syn_1，数值同时出现在该会话 run.log 中，正式验收应补充其候选绑定。

`syn_1/run.log:415` 明确发出 SYN-5114：`cmem_syn_101` 可能需要 65536 个寄存器。还有两组精确相符的差额：

- core：gate seq 67500 − RTL seq 1964 = **65536**。
- 全设计：gate reg 68075 − RTL DFF 2539 = **65536**。

这恰好等于 `cmem[0:4095]` 的 4096 × 16 bit 容量。cmem 是寄存器膨胀的主要来源，有日志和数值两方面证据。不能由此把全部逻辑 LUT 都归给 cmem；具体 LUT/选择器节省仍须综合确认。

历史也提供了对照：r4 留存 gate.area 为 **2335 FF、4 ERAM、Slice 17.43%**；r5 最后一次 S3 留存 gate.area 为 **67941 FF、0 ERAM、Slice 98.60%**。r5 结果文档同时记录该阶段引入 candidate packer 三级流水、cmem 写 FIFO 和尾字排空。r5 的 S3 实验随后回退到 S2，不能把 S3 数值直接当成其冻结 S2 数值；但 r4 与目前 S2 的巨大资源差异足以要求回看这段存储写法变化。可复用 r4 的成功映射作为对照，不建议整体回退丢弃后续流水成果。

源码提供了一个强假设：cmem 虽然已有同步读，但写入同时来自 FIFO 排空和尾字状态分支，形成多个描述上的写入口。这可能妨碍映射到期望的 RAM 结构；需要单写口实验确认具体原因。

源码位置：`upstream/ph1p100-pcie-ep-fpga/rtl/ep_side/codec/a1_deflate_core.v:198,458,1022,1287,1296,1305`。

## 3. 建议的优化顺序

| 优先级 | 方向 | 实现边界与风险 | 验证信号 |
|---|---|---|---|
| 1 | 整理 cmem 为一个写端口，验证 ERAM 映射 | 所有写来源汇成唯一 we/addr/data；FIFO 和尾字仍保持原顺序；独立整理 RAM 读写进程，采用 PH1/TD 支持的模板或封装。统一写口本身不保证 ERAM 推断成功 | cmem 不再展开 65536 FF；ERAM 数与实例相符；功能/码流/吞吐不退化 |
| 2 | 完成并验证 frame_top 读地址寄存，必要时将 smem 组织为明确的同步分 bank RAM | 工作区已有 rd_addr 修改，先核其实际结果；若仍是 DRAM 巨大选择网络，应检查 RAM 模板、bank 组织及地址宽度。仅复制同值寄存器可能再次被综合合并 | 读地址到 dq 的逻辑深度/扇出下降；全量违例报告可定位余项；最终布线 setup/hold 满足 |
| 3 | 再评估 bm_a/b 与 htab 的存储接口 | bm_a/b 有组合读和多个用途的读访问，不能只加 ram_style 就假定能用 ERAM；需列每拍端口需求，必要时拆读口/复制 RAM/预取。htab 要保留同址写旁路与 distance-1 行为 | 有端口与延迟合同；有实际 RAM 实例；保持启动间隔、回退和字节一致性 |
| 4 | 减少无效深度/冗余位宽 | 可审计 4800B 块与 8192 地址间的空洞、htab 字段和缓存上界。必须先证明全部访问范围与溢出规则，不能直接把数组缩成 4800 | 最大索引、边界/尾块/abort/reset 均有证据；不能改变既有压缩语义 |

当前最小、最有证据支持的下一项实验是 cmem 单写口与 ERAM 映射验证。若正在执行 r0-c，它的范围仍由原授权控制；本评审不把 cmem 改动塞入锁定 core 的 r0-c，也不自动新增轮次或重置旧预算。

## 4. 吞吐约束需要按最紧用例计算

已有 P2 comp 用例：153600 B / 355261 cycles。在 187.5 MHz 下为 81.067159 MB/s。

保持 77.76 MB/s 时，周期上限为：

`floor(153600 × 187.5 / 77.76) = 370370 cycles`。

所以该用例仅允许再增加 **15109 cycles，约 4.253%**。1080p p1d1 从 4677945 到 6250000 cycles 的余量约为 33.606%，不能据此认为全部用例都有三分之一余量。

这意味着 ERAM 改造应争取“增加固定延迟、保持流水启动间隔”，不能简单给每个字节增加一个等待周期。块间少量填充也必须实测其累计开销。

降频估算同样需要纠偏：维持 P2 comp 的现有周期数时，150 MHz 只能得到 **64.853727 MB/s**；满足该用例 77.76 门槛需要至少 **179.850881 MHz**。历史按 1080p p1d1 推算的 150 MHz ≈83.1 MB/s，只适用于那个用例，不能证明整个现有验收集仍达标。P2 comp 目前本身也未达到 97.2 MB/s。

## 5. 建议收口方式

后续若启动实施，先冻结当前真实候选与证据，列出每块缓存的容量、端口、读延迟、写冲突和目标存储资源；用一个有界实验确认 cmem 映射确实改变，再决定扩大到 smem/bm/htab。

综合后的第一轮检查应同时看：RAM 实例和资源、全量负 slack 端点、功能与码流等价、最紧吞吐用例。最终 G2 仍需同一冻结候选的 Routed、非负 setup/hold、最终资源与实际 CDC/check_timing 报告。报告脚本使用 catch 跳过命令不能替代实际检查成功。

不建议继续凭最差 10 条路径宣布 core 全闭合、靠 seed 重跑，或直接采用 150 MHz 作为现有吞吐门槛下的兜底方案。也没有必要在存储实现问题尚未解决时重写整套压缩算法。

原始报告的 STNS 是 setup 总负裕量；HWNS/HTNS 均为 0，但也仅属于综合阶段，不能替代布线后的 hold 验证。
