# 导师复核与提交前并行推进建议

> **后续方向更新（2026-10-15）：** 用户明确选择以 Bayer 预测＋熵编码替换 LZ77 研发主线，认为符合赛事创新导向。后续 FPGA 策略以[独立策略指引](superpowers/plans/2026-10-15-fpga-remaining-strategy.md)为准；下文有关保留 LZ77 为主线的建议保留为本轮决定之前的审查历史。算法替代的规则接受口径仍单列确认，不阻塞独立研发。

> 2026-10-15。对象：`方案审核与优化方向_对比开源_2026-10-15.md`、当前实际工程和提交计划。本文是独立审查与执行建议，不代表已变更正式架构、硬件档位或队友承诺；未修改生产 RTL、约束或位流，未下载硬件。
> 用户本轮补充：队友有充足识别经验，最近忙其他事项，马上可以参与。应降低对 NPU 入门难度的估计，但驱动、DMA、RAW 解码、标定和深度的实际完成状态、开始日期仍未提供。

## 1. 导师判断：架构可以继续，交付顺序必须纠偏

**FPGA 负责采集、预处理、压缩和传输，RK 负责识别与深度，这一分工合理。当前成果有真实工程价值，但整队交付风险高，尚不能评为完整、成熟、优秀的竞赛系统。**

现阶段最明显的失衡，是本地彩色显示、闪点和时序探索投入较深，而三算法、硬件压缩、图像 DMA 和 RK 实流输入尚未闭环。后续应围绕“真实帧经过 FPGA 硬件处理/压缩，经 PCIe 在 RK 正确恢复并进入 NPU”建立主线；双路同步与真实深度是用户明确要求，也要提前准备，不能拖到最后两天才暴露风险。

新审核稿有价值，尤其是区分电气与 STA、把 HDMI 定位为调试、提前准备 RK 离线软件。不过，它仍接近“值得研究的技术方向清单”，没有充分服从赛题合规、当前代码状态和仅剩的工程时间。**不能把其中所有优化同时纳入提交前必做。**

建议按三个层次管理：

- **赛题基础：** CSI 高清采集、三种 FPGA 硬件预处理、JPEG/LZ77 硬件压缩、高速压缩帧传输、RK NPU、量化报告。
- **用户完整目标：** 在上述基础上完成双路、同步证据、实拍标定/匹配/深度；允许深度按已认可边界低于采集分辨率/帧率。
- **可延期提升：** 双路 4K、完整 ISP、AWB/CCM、边缘感知去马赛克、自研 Bayer 熵编码、复杂 DMA 队列、HDMI 画质进一步优化。

单路基础闭环是阶段性里程碑，不是取消双目目标。双路 1080p30 是研发目标，也不等于已满足所选赛事场景的全部 60fps 等要求。

## 3. 对新审核稿的逐项裁决

| 建议/结论 | 裁决 | 修订建议 |
|---|---|---|
| HDMI 与评分交付解耦 | 保留，优先级高 | PCIe 原本就是已确认主通道；现在需要改变任务依赖和投入，不必重建总架构。HDMI 色彩/闪点不阻塞独立压缩、DMA、RK 软件 |
| 从 LZ77 换成 DPCM＋Golomb-Rice 等 | **不能作为当前基础压缩的替代路线** | PDF 物理 19、25 页仍明确 JPEG/LZ77。没有组织方明确接受前，Bayer 熵编码只能列拓展；论文性能优良不能代替合规性 |
| Bayer 压缩比通用 LZ77 更适合 | 可研究，尚不能直接判本项目优胜 | 要比较真实 RAW10 图集、最差膨胀、硬件资源/周期和解码成本；packed RAW 字节组织也会影响字典压缩效果。当前不再开多个新编码方向 |
| OMLS 是可借鉴 FPGA 开源方案 | 降低可直接移植预期 | 本轮打开的仓库入口主要是 PC 的 C++/Python 编解码和向量生成；不能由论文有 VHDL 实现推定仓库已有完整可移植 RTL。40Gbit/s 是另一器件、16×8bit 像素并行的作者结果 |
| 128MB/s 单 GZIP 核不够双路 | 算术成立，但缺少阶段划分 | 双路 1080p30 RAW10 为 155.52MB/s；单路为 77.76MB/s。先完成单路压缩实测，再评估双引擎/并行，不应因此现在就放弃合规编码 |
| 立即颜色板验，然后补最小 ISP | 板验保留，后半句限时 | 做一次有对照的颜色验收；色彩足以支撑识别时停止扩张。先验证 RK 固定软件 ISP，不同时维护两套复杂颜色链 |
| 丢 3/4 像素意味着深度质量差 | 需要区分支路 | 当前代码每 4×4 取首个 2×2，使用 4/16 个传感器样本、输出一个 RGB 像素，确实有抽样/混叠风险；但这是预览支路，不能直接推论尚未实现的正式 RAW 深度输入质量 |
| 深度用全分辨率，低分辨率仅用于 NPU | 不接受这一刚性限制 | 用户已允许深度低分辨率/低帧率首版。固定几何后以测距误差、有效像素比例和实测 fps 决定，例如从 640×360 或 960×540 试起，具体尺寸待实测冻结 |
| RAW Bayer 做 2×2 平均即 binning | 表述必须更准确 | 邻近 2×2 含 R/G/G/B，直接平均不是保留 Bayer 的同色 binning。灰度聚合与 Bayer 降采样要分别定义；传感器 binning、FPGA 抽样、RK resize 不是同一操作 |
| 任意独立 AWB/HE 都会破坏对应 | 方向保留，去掉绝对化 | 独立自适应处理可能破坏光度一致性、降低匹配效果，但不必然破坏几何对应；首版固定曝光/增益并旁路独立 HE，按误差评估后再引入增强 |
| 曝光同步优于帧号配对 | 保留并补前提 | 共享 XHS/XVS 与模组连接、方向和寄存器模式必须核实；rolling shutter 要比较对应行、相同读出/曝光参数。不能假定 IMX415 支持任意 FPGA 单脉冲触发 |
| 每 lane 眼图/误码/温度校准 | 降为分阶段可靠性任务 | 先读现有 CRC/头错/超时/丢帧计数并扫 tap 有效窗口；数字 tap 窗口不是模拟眼图，包 CRC 错误率不是直接 BER。每 lane 独立校准意味着接口/训练逻辑改造，不是顺手补功能 |
| 补齐 CRC/ECC 计数 | 防止重复实现 | 当前生产候选已接入 `csi_rx_packet_integrity` 并有 CRC/头错/超时/好坏帧计数。应补板上读取与几何参数冻结，而不是重写已存在层 |
| 紧路径先加流水 | 改成证据驱动 | 002820→103222→111134 的最差路径已经改变。先判断用户逻辑还是厂商校准/复位语义，再定措施；流水、寄存复制都不是无条件安全修复 |

HDMI 的跨平台文章只能支持“物理层风险值得排查”，不能支持“本板彩点已证明来自物理层、排除 RTL”。已有板卡资料显示耦合电容，也不能照抄文章再加一次。建议“如需另立调试降档方案则评估”和“不擅自改变已确认 60Hz 主线”可以共存；原审核稿应写出条件，避免前后像相反指令。本文不执行降档。

## 4. 新审核稿漏掉的三个关键工程问题

### 4.1 显示缓存的丢帧策略不能直接充当传输队列

当前 `ddr_frame_store.v` 在新帧 VERIFY 成功后，会释放旧 READY 槽，保留正在 READING 的槽。这是“尽量显示最新完整帧”的合理预览策略。

**正式压缩/DMA 若要求连续帧或可追踪成对输入，不能原样复用此策略。** 队列必须明确帧生产、压缩、发送、完成后的所有权；任何丢弃都有原因计数和序号缺口。可以复用 DDR 接口、CRC 和部分槽管理，但要单独定义传输排队/有界丢帧合同，不能让“显示正常”隐藏被替换的 READY 帧。

### 4.2 容量扩展不等于持续带宽达标

当前 store 使用单个 256bit 命令、单笔未完成读与逐字握手。具体 PAXI 并非标准 AXI。81001 字容量验证解决地址范围问题，不证明这一访问模式能承受双路采集＋编码＋发送＋预览。

先用合成帧/固定负载测每段持续 MB/s、最长不可服务时间、FIFO 高水位和丢帧。若不足，再按厂商真实接口优化批量命令、预取、仲裁和输出缓冲；不能先用“DDR 总线很宽”判定足够。相机无法反压，队列满要按整帧失效处理，禁止静默漏像素。

### 4.3 真实帧导出和接口冻结优先于进一步美化屏幕

现在缺少可供 RK 解码、压缩比测试、完整性比较和真实标定使用的标准帧文件。应把“可导出一张带元数据和 CRC 的真实 RAW10 帧”列为近期独立产出；调试导出可慢，正式实时通道仍按 PCIe 建设，不用低速导出冒充赛事通道验收。

接口草案仍有分辨率、stride、字节序、DMA 地址宽度、缓冲所有权等空项；旧文档又混有封存 RAW12。必须用一个现行表写清：

- RAW10 packed 与 unpacked uint16 的区别、Bayer 相位、裁剪起点/方向、width/height/stride。
- camera_id、session_id、采集序号、模式版本、有效字节数、时间戳频率、CRC 和错误标志。
- 压缩格式及版本、分块/复位规则、未压缩回退标记、RK 解码成功条件。
- BAR/DMA 的目标地址、容量、忙/完成、实际长度和超时；由主机驱动分配/映射合法 DMA 缓冲，不能拿用户态虚拟地址直接给 FPGA。

先冻结互通必须字段，不扩展成复杂通用协议。第一次 C2H 用一个或少量明确归属的缓冲、轮询完成即可；环形队列/MSI 后补。最小版仍要处理地址合法性、MPS/4KiB 边界、尾字节、反压、复位及超时。

## 5. 收敛后的近期路线与带宽依据

建议继续沿用已跑通的 RAW10 接收，不恢复 RAW12，不在此时同时切换传感器模式、PHY、颜色链和传输协议。

```text
真实 RAW10 → 完整性/几何检查 → 正式帧缓存 → JPEG/LZ77 硬件编码 → PCIe → RK 解码
               └→ 固定灰度输入 → 灰度 / 高斯 / 前帧 HE 并行计算与验证输出
RK 解码 → 固定软件颜色处理 → NPU
       └→ 同几何的左右灰度 → 校正 / 匹配 / 深度
RGB565 + HDMI 继续作为已有调试支路
```

三算法首版保留已定义的灰度、3×3 高斯、前帧 HE；并行计算、帧边界选结果用于验证，避免同时存三份整帧造成无必要带宽。若赛事另要求同时展示/传输，按组织方口径补充。HE 同值连续更新和多像素同 bin 冲突要专门检查，第一帧恒等 LUT、坏帧不发布新 LUT。不要为了降低 HE 难度，默默改变当前吞吐/并行宽度。

正式 1080p 数据面要在现有 4K RAW10 上明确 ROI 或其他经过验证的形成方式；ROI 会改变视场/主点，需记录裁剪坐标，不能把 960×540 插值放大标成真实 1080p。也不为取得 1080p 贸然启用可能改变线上格式的传感器 binning。

按 packed RAW10、每路 30fps、十进制 MB 计算：

| 输入 | 有效数据量 | 25% 设计余量后 |
|---|---:|---:|
| 单路 1920×1080 RAW10 | 77.760 MB/s | 97.200 MB/s |
| 双路 1920×1080 RAW10 | 155.520 MB/s | 194.400 MB/s |
| 双路 1920×1080 Gray8 | 124.416 MB/s | 155.520 MB/s |
| 双路 3840×2160 RAW10 | 622.080 MB/s | 777.600 MB/s |

以上未含帧/块头、PCIe 报文和非图像开销。编码器输入仍承受原始数据量，输出变小不能弥补编码器输入处理太慢；按不可压缩/RAW 回退估算队列，不能先假定压缩节省 30%。25% 是工程预算，不是赛事条款。

若沿用“原帧写入→压缩读取→压缩暂存写入→PCIe 读取”，DDR 逻辑流量约 `2R+2S`。双 1080p RAW10 在 S≈R 的保守情形约 622.08MB/s，25% 后 777.60MB/s，另加预览/元数据/实际访问效率。串流编码可减少搬运，但必须先证明输出膨胀与反压可吸收，不在无数据时重构已有缓存。

单路 960×540 RGB565、30fps 写入仅约 31.104MB/s；预览闭环成功不能外推全尺寸双路带宽。双路 4K 原始帧一帧 10,368,000B，也放不进旧方案的 4MiB 帧槽；它是带宽、容量、并行度共同提升，不能只改 width/height。

压缩近期只选一个合规方向：优先有限时间验证既定 LZ77 候选或成熟 LZ77/DEFLATE 核，记录算法来源/许可和本人贡献。自定义 LZSS 式封装与 GZIP 不兼容，不能软件用 zlib、硬件输出另一种 token 却声称互通。2 天内得不到软件往返、真实图集初测和可信硬件周期/资源路径，就召开一次 JPEG 备选评估；不要继续无期限搜论文。替换编码器要同时评估颜色输入、深度质量和联调代价。

## 6. 真正可以并行的工作：拆依赖，而不是让一个人同时调四块 RTL

| 工作线 | 负责人建议 | 现在即可开始的输入 | 第一份可验收产物 | 集成前真正依赖 |
|---|---|---|---|---|
| A：真实 RAW 帧与完整性 | 你主导上板，Codex准备工具/复核 | 当前单 A 候选、现有诊断 | 一张真实 RAW 帧＋元数据；WC/行数/错误计数/fps 日志 | 实际相机及正确数据面 |
| B：PCIe C2H | 你负责 FPGA，队友负责 RK 驱动 | 合成计数/随机块，不等相机 | RK 收块逐字节/CRC 一致；复位恢复及有效 MB/s | 可共同使用的 FPGA/RK 硬件窗口 |
| C：合规压缩 | Codex辅助参考/仿真，你确认实现与工具结果；队友对接解码 | 合成块与格式定义，随后加入真实 RAW | 编码→RK 解码一致；含头大小、最差长度、周期记录 | 上板只等选定模块和构建，不等 HDMI 完美 |
| D：三算法 | Codex辅助参考/仿真，你负责集成 | 固定小图/全尺寸向量 | 三分支像素对照、边界、HE计数/LUT换帧 | 真实帧用于最终算法输出证明 |
| E：RK NPU 和离线深度 | 队友 | 文件输入、测试图和一致的 RAW 解码约定 | 板上 NPU 检测输出/耗时；离线校正/视差/深度流程 | 实拍标定与实流验证最终依赖真实双目 |
| F：同步与标定准备 | 你负责硬件，队友负责标定脚本 | 模组接线资料、固定支架/标定板 | 主从配置/测量方案，标定采集质量检查脚本 | 真正同步/标定验收依赖双路对应实拍 |

这些是团队工作线，不是建议你每天开六个主任务。你每天一个主要硬件产出，另加一个不依赖硬件的短工作块；TD 编译期间做向量、接口和记录。新模块先独立构建，统一集成入口，避免多人改同一顶层或同时覆盖同一候选。

队友识别经验充足，建议其加入后的第一工作日先交“RK环境＋NPU静态文件推理＋驱动构建条件”，第二工作日与 FPGA 对接固定块收取。NPU 软件应支持文件输入与实时输入共用预处理，之后只替换输入源。**不能把“识别调试很快”当成“PCIe/RAW/深度都很快”。** 本表是建议，尚无其日期承诺，也未代发消息。

并行工作的停止边界：离线左右图可证明软件流程，不能证明本相机标定/同步；合成帧可证明 DMA/编码互通，不能证明实拍压缩率或采集质量；模块各自通过后仍须整链路回归。

## 7. 从提交日期倒排：留出真正的联调与失败空间

按既有记录，11-04 提交，11-01 至 03 留给报告/视频；10-31 冻结。10-15 到提交相差 20 天；从 10-16 到 10-31 只有 16 个完整研发日，按每天 4–6 小时约 64–96 小时，另加今天剩余时间。工具运行、上板等待、复测和理解也占用这个预算，不能只算写 RTL 的时间。

下表是带退出条件的建议窗口，不保证日期自动完成。旧路线里把“不修好当前卡点就不能做下一项”泛化到全队，会造成长时间串行；应仅阻塞真正依赖它的集成，独立工作线照常推进。

| 日期窗口 | 你主要推进 | 队友/独立软件并行 | 检查点与未通过时的动作 |
|---|---|---|---|
| 10-15～16 | 收束当前时序结果；一次颜色板验；读 CSI 分类/几何；冻结 RAW10 和最小帧/DMA 接口 | 队友加入后先核内核/驱动与静态 NPU；压缩参考/三算法向量可同时准备 | **不能把 CCM/AWB/闪点根因全解决设为下一项前置。** 导出真实帧成为近期重点 |
| 10-17～19 | 优先 PCIe 固定块 C2H；单 A 完整 RAW 缓存；选定一个压缩实现路径 | 解码参考、文件输入 NPU、三算法独立仿真；准备同步/标定工具 | 10-19 应拿到“RK正确收固定块”和“压缩可逆＋周期/资源依据”；缺任一即列最高风险，停止新增提升项 |
| 10-20～23 | 单路真实帧→硬件编码→PCIe→RK 解码；三算法按已验模块接入/展示 | RK NPU 接实时源；用实拍 RAW 复核颜色/压缩比率；双路模块离线准备 | **10-23 是单路完整链路检查点。** 若未通，后续双目时间明确受压，须当日重排，不能仍承诺原全功能日期 |
| 10-24～27 | B路启用、共享同步条件实测、双路配对及有界丢帧处理；不再加新颜色功能 | 用本机实际双目帧重新标定/校正/匹配；NPU与深度分开测fps | 10-27 应有同步/配对证据、真实标定结果和可解释的深度；静态异步演示不能标成动态同步深度 |
| 10-28～30 | 量化全部链路；连续运行/停启/掉线恢复；修复确定缺陷 | 距离误差、有效深度比例、NPU耗时、报告图表和录制预演 | 长稳失败当天要有重测空间；提交材料从此同步整理，不等最后一晚 |
| 10-31 | 冻结可复现工程、位流、RK程序/模型、标定参数，列实际未达项 | 双方按同一流程复现，备份提交素材 | 冻结后只修阻塞缺陷，每次重新验证；不引入新压缩器或4K模式 |
| 11-01～03 | 报告、视频、提交检查、必要复测 | 统一版本、指标口径、来源和分工 | 材料必须对应实际运行版本；不能用局部成功拼成不存在的整链路 |
| 11-04 | 提交并保存回执 | 配合核对 | 完成以平台回执为准 |

建议的时间控制：颜色/WB一次板验及必要记录先占半个工作日；HDMI/时序每轮实验写清假设、上限和停止条件。对厂商 DDR 内部瓶颈，不承诺靠再跑多轮策略一定达到 0.3ns，也不通过放松约束制造余量；确需改目标或 IP 参数，单独评估吞吐和证据后再决定。

取舍顺序：先停 AWB/CCM/Malvar、第二压缩器、复杂 UI、4K 和无期限 HDMI 优化；保留三算法/硬件编码/PCIe/NPU。用户要求的双目深度继续推进，可先降低深度计算负载和显示频率，不能默默删掉。若 10-23 主通道仍不通，应向用户明确报告全目标延期风险，并作实际范围决策；“先保基础”也不能掩盖第25页评分对双路等仍存在的要求。

## 8. 让报告和验收更精简，但保留关键证据

建议日常只维护一个现行状态表：`工作包｜负责人｜下一检查日期｜已验证版本｜产物链接｜阻塞｜下一动作`。历史材料保留为索引，不批量迁移或删除。入口不再层层叠加互相冲突的旧状态。

每个可交付版本必须保留源码/IP/约束与位流身份、关键功能回归、最终STA/必要CDC、错误计数和板验记录；新候选通过的实际参数应绑定验证。未改模块的证据按变更影响复用，日常探索无需为了一个局部假设重复制作整套“交付包”。文档数量、测试数量、哈希数量都不能直接作为功能完成度。

量化报告至少分开这些量：

| 类别 | 最小记录 |
|---|---|
| 采集/传输 | 原始FS数、有效帧、拒收/队列丢帧、RK成功解码帧、各段实际fps与有效MB/s |
| 压缩 | 原始字节、含帧/块头总字节、节省比例 `1-S/R`、平均/最差图、RAW回退率；不能把缩图/降位宽算编码收益 |
| 延迟 | 采集/缓存/编码/传输/解码/NPU分别定义测量点；不同设备时间基未同步时不能直接相减 |
| 同步 | 测量对象/共同时间基、均值/最大/分位、失锁/丢帧后的配对恢复；SOF差值与曝光证据分列 |
| 深度 | 实际分辨率/fps、标定版本/基线单位、极线误差、多个已知距离的偏差、无效像素比例 |
| NPU/资源 | 板上推理与预处理时间、模型/输入版本；实际LUT/寄存器/ERAM/DSP/PLL及最终时序 |

RK 与 FPGA 不要各自维护互不相容的文件格式。先用一份小型合成 RAW10 共享向量检验解包、相位/方向、CRC和解码，再替换成真实帧。识别能工作不代表颜色链准确，CRC一致不代表光学图像正确，静态深度图也不代表动态同步合格。

## 9. 近期三件事和导师要求

1. **冻结最小互通接口，并准备可导出的真实 RAW10 帧。** 这是压缩、RK、标定共同可用的输入；同时读取已有 CSI 分类/几何，不再用预览截图代替数据证据。
2. **立刻开启 PCIe 固定块与合规压缩独立工作线。** 两者都不需要等待颜色完全正确；先各自正确，再在 10-23 前争取真实单路联调。
3. **队友加入后的第一份交付要可运行。** NPU文件推理、驱动构建条件和收帧程序框架比“识别应该很快”更能降低风险；双目脚本和支架/标定板准备也从现在开始。

导师的要求是：每一项优化先回答它关闭哪条验收缺口、耗费多少天、失败如何回退。若答不出，就暂不进入提交前主线。把已做好的接收/缓存基础转成能在 RK 使用的真实数据，再用真实数据评价压缩、识别与深度；不要把局部调得越来越精细误当成系统越来越接近完成。
