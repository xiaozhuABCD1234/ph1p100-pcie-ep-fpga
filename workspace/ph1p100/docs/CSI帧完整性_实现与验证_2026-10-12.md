## 1. 为什么需要继续修改

上一版142857解决了WC之外字节泄漏、RAW10的DT/VC分流和尾字节解包，但没有校验CSI CRC16。DDR CRC32只能证明收到的灰度数据写入、读回一致，不能证明这些数据在进入FPGA时就正确。

还有一个更隐蔽的问题：960×540预览的最后一个像素可能先于原始相机帧的末行、CRC或FE到达。旧打包器在预览`pixel_last`之后立即发footer，因此可能已经将帧发布，随后才发现原始输入有错。

本轮把“预览数据收齐”和“相机原始帧有效结束”分开。后者到来之前，已写入DDR的数据只占用写槽，不允许成为READY。

```text
CSI头/载荷/CRC → RAW10解包 → 预览像素 → START / DATA
      │                                    │
      ├─ 输入出错 ───────────────→ ABORT ────┤ 同一个异步FIFO
      └─ 有效FE + 预览收齐 ─────→ FOOTER ───┤
                                           ↓
                              DDR写槽 → fence → READY
```

ABORT和FOOTER与数据共用FIFO，按同一顺序跨域。没有通过另一路异步“坏帧脉冲”撤销已经发布的帧。

CRC16使用初值FFFF、反射多项式8408、无最终异或；按接口字节顺序处理，接收footer低字节在先。跨word的CRC也按WC字节位置收集。参考来源中，AMD官方[PG260](https://docs.amd.com/r/en-US/pg260-mipi-csi2-tx/MIPI-CSI-2-TX-Controller)说明CSI-2长包载荷CRC16多项式为x16+x12+x5+1、头使用ECC。这是跨平台协议参考，不能证明安路软PHY或本机相机链路已通过实测。测试参考使用MSB 1021与显式位反转，避免直接复刻RTL的8408循环；CRC32期望另用Python zlib生成。

## 4. 仍需保留的边界

- 实际相机WC、OB/EBD包清单、RAW10行数及FS/FE编号语义未抓取。板级默认`IMAGE_WC=0 / EXPECTED_LINES=0 / CHECK_FRAME_ID=0`，只要求RAW10 WC五字节合法、帧内一致、非空及预览完整。精确行几何和编号检查在模型中开启验证，板上仍未冻结；缺少预览采样范围之外的原始行，或错编号FE，当前板级参数可能不拒绝，不能声称已证明整帧几何完整。
- 当前接收接口以每包PHY重新同步为前提，不承诺连续HS背靠背包；ECC只检测并丢弃，不纠错。
- 无FE不发footer；包超时、下一FS或帧超时负责恢复。绝对帧超时需要byte clock继续运行，时钟停止时不会自动计时，但也不会因此生成有效footer。
- footer阻塞时可能丢弃随后到达帧；后来帧的abort还可能保守撤销尚未发出的上一有效footer。这是可用性限制，不会把坏帧发布为READY；下一可完整接收的帧可以恢复。
- 完整1080p RAW10的16位偏移容量问题尚未修；当前仅518400B灰度帧。扩大store/checker/reader地址应作为下一数据面工作包。
- D39为粘滞标志，首次亮起需读取分类计数，不能区分每一种错误，也不能证明HDMI输出无误码。
- HDMI 1485Mbps/通道的板级额定保证缺口、局部时钟警告及STA覆盖差异仍存在，内部正裕量不能替代板外或长期稳定性证据。
