# 写者永久停 S_TAIL 修复与上板验证（2026-10-28）

## 1. 现象

一次 `CTRL(0x44)=0x165`（bit2=1，传感器重触发）后，B 路 `0xE0` 冻结、
`0x174=0x18`（S_TAIL + A_IDLE），`0x1A0=518400`、`0x1A4=0`、verdict 仍 `0x20`；
A 路继续 30 fps，`0x128`（B 的 CSI 包计数）仍在涨。只有重下位流+重启才能恢复。

## 2. 根因链

1. bit2 边沿把两路 XCLR 同时拉低 134.2 ms，相机帧中途停流；
2. 抢到 DDR 写口的一路把 `busy` 一直拉住（`busy=(a_st!=A_IDLE)`，含 A_W），另一路在
   `A_AW` 等到 `aw_tmo_evt`（65535 拍 = 655 us）；
3. `aw_tmo_evt` 原来只撤 `awvalid`、清 `mid_frame`、回 `A_IDLE`，**不改 `s_state`**。
   若此时已在 `S_TAIL`，`A_IDLE` 里只有 `mid_frame=1` 才会再发突发 →
   `beat_vld` 永远卡 1 → `data_ready=\sim beat_busy=0` →
   `tail_app` 永不触发 → `apos` 冻死 → 永久停在 S_TAIL；
4. 旧看门狗条件 `(a_st==A_IDLE) && mid_frame && !burst_ok_ddr` 此时 `mid_frame=0`，
   且 `S_TAIL` 下 `burst_ok_ddr` 恒 1，两重原因都不计数；
5. 另有一个隐藏 bug：`self_flush_cnt` 从未复位，仿真里恒 X → `self_flush=x` →
   `wdt_active=x`，`if (x)` 按假处理 → 看门狗永远不计数（板上初值随机）。

## 3. RTL 改动（`rtl/ep_side/ddr/cam_r10f_writer.v`）

| 改动 | 作用 |
|---|---|
| `aw_tmo_evt` 分支加 `self_flush_cnt <= 8'hFF` | 根因修复：aw 超时立即走已有自愈，不再留 S_TAIL 死锁 |
| `self_flush_cnt` 补复位 | 看门狗从「恒 X / 随机」变为确定可用 |
| 看门狗判据通用化：`s_state!=S_SYNC && a_st==A_IDLE && !self_flush`，用 `apos/cpos/pop/beat_taken/frame_close` 判前进，`WDT_LIMIT=0xC0_0000`（125.8 ms） | 兜住 S_TAIL/S_PAY/S_HDR/S_WAIT 等所有 A_IDLE 停滞 |
| `self_flush` 时清 `beat_vld/bcnt/breg/pack/wlane` | 只回 S_SYNC 不够：`beat_vld=1` 会让下一帧连 S_HDR 都进不去 |

另：`rtl/ep_side/cam/ui_imx415_reg.v` 恢复为 **27MHz/891Mbps** 的 4K 表
（`SYS_MODE=0x05、VMAX=2250、HMAX=1100`）。此前工作区 HEAD 用的是
`0x08/VMAX=4503/HMAX=533` 那套，板测两路 FIFO 溢出
（`0x1A0=0x45cbc + 0x1A4=0x38c44 = 518400`）、verdict `0x4/0x5`、ARM 被拒。

## 6. 残余风险

1. `A_W` 中途断粮仍不在看门狗判据内（判据要求 `A_IDLE`）。若 XCLR 恰好落在
   128 拍突发中途且 tail 补不上，可能永久停在 A_W；本轮板测未复现（实测是 S_TAIL+A_IDLE）。
   要补需放宽为「`A_W` 且 `WDT_LIMIT` 拍无 `beat_taken`」，并处理已接收的 AW 事务。
2. 看门狗自愈的帧不走 `frame_close`，`err_cnt`/`lat_wdt` 不锁存，板上只能从
   `0x170/0x174` 回 `S_SYNC` + 帧流继续间接判断。
3. `ddr_wr_arb` 的 `busy` 含 `A_W`：一路相机彻底死时会长期占口，另一路每 655 us 自愈一次
   但拿不到端口，属仲裁层后续工作。
